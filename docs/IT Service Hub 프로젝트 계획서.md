# IT Service Hub 프로젝트 계획서

Oct 26, 2026 · @장호

## 1. 프로젝트 개요

IT Service Hub는 사내 직원의 IT 장애 접수, 담당자 처리, IT 자산 이력 관리를 하나로 묶은 웹 서비스이며, 5인이 3주 안에 완성하는 포트폴리오용 팀 프로젝트다.

- **배경**: 단순 문의 게시판은 흔하므로, 티켓 상태 관리, 권한, 자산-장애 연결, 외부 시스템 알림까지 갖춘 업무 시스템 형태로 차별화한다.
- **핵심 가치**: 직원이 장애를 접수하면 담당자 배정, Slack 알림, 처리 이력 누적, 장비별 고장 이력 확인까지 한 흐름으로 이어진다.
- **기술 환경**: Spring MVC(XML 설정), JSP, MyBatis, Oracle, Maven, WAR 배포(Tomcat). Spring Boot는 사용하지 않는다.
- **팀 규모와 기간**: 5인, 3주

## 2. 목표 및 범위

3주 안에 "얕은 기능 여러 개"보다 "끝까지 동작하는 핵심 흐름"을 완성하는 것을 목표로, 기능을 네 단계로 나눈다.

| 단계 | 포함 기능 | 비고 |
| --- | --- | --- |
| 필수 | 티켓 접수·배정·상태 전이·이력, 자산 CRUD, 티켓-자산 연결, 역할별 권한 | 1\~2주차 완료 |
| 핵심 연동 | Slack Incoming Webhook 알림 | 구현이 가장 가벼워 우선 적용 |
| 시간이 남으면 | 통계 대시보드, GitHub Issue 단방향 생성 | 티켓에서 Issue를 만드는 방향만 지원 |
| 제외 | GitHub Webhook 수신(양방향 동기화), 외부 서비스 장애 모니터링, 해결 문서 추천 | 공인 URL·추가 개발 부담이 큼 |

**성공 기준**

- 요청자가 티켓을 등록하면 담당자에게 Slack 알림이 가고, 처리 완료까지 상태와 이력이 기록된다.
- 특정 장비에서 발생한 장애 이력을 자산 상세 화면에서 조회할 수 있다.
- 모든 기능이 역할(요청자·담당자·관리자)에 따라 접근 제어된다.

## 5. 티켓 상태 전이 규칙

&#91;embedded content: 티켓 상태 전이 · 6개 상태\]

허용된 전이는 접수, 배정, 처리중, 완료, 종료의 한 방향이며, 되돌아가는 경로는 요청자의 재요청(완료에서 처리중) 하나뿐이다. 접수 단계의 티켓만 요청자가 취소하거나 담당자·관리자가 반려할 수 있다. 정의되지 않은 전이는 서비스 계층에서 차단하고 테스트 코드로 검증한다.

## 6. 외부 API 연동 설계

외부 연동은 Slack 알림(필수 연동)과 GitHub Issue 단방향 생성(선택) 두 가지이며, 외부 호출이 실패해도 티켓 처리는 정상 진행되도록 분리한다.

| 연동 | 호출 시점 | 방식 | 실패 시 처리 |
| --- | --- | --- | --- |
| Slack | 티켓 접수, 담당자 배정·변경, 긴급 우선순위 | Incoming Webhook으로 JSON POST, 긴급 건은 별도 채널 | 로그 기록 후 재시도 N회, 티켓 처리는 계속 |
| GitHub | 담당자가 "Issue 생성" 버튼 클릭 | REST API로 데모용 저장소에 Issue 생성 후 번호·URL을 티켓에 저장 | 오류 메시지 표시, 티켓 상태는 변경하지 않음 |

**설계 원칙**

- **비동기 처리**: 알림 발송이 화면 응답을 지연시키지 않도록 별도 스레드 풀에서 실행한다. XML 설정에서 `task:annotation-driven`과 executor를 등록한다.
- **타임아웃**: HTTP 클라이언트에 연결·응답 타임아웃을 명시한다.
- **호출 이력 테이블**: 성공·실패, 응답 코드, 오류 메시지를 `API_CALL_LOG`에 기록해 트러블슈팅 근거로 쓴다.
- **키 관리**: Webhook URL과 토큰은 `properties` 파일로 분리하고 `.gitignore`에 등록한다. 팀 내 공유 방식은 별도로 정한다.
- **직접 등록 필요**: Spring Boot가 없으므로 HTTP 클라이언트(RestTemplate 등)와 Jackson 의존성, 빈 설정을 XML로 직접 구성한다.

**제외 항목**: GitHub Webhook 수신은 외부에서 접근 가능한 공인 URL이 필요해 개발·발표 환경 부담이 크므로 이번 범위에서 뺀다.

## 8. ERD 초안

핵심 테이블은 아홉 개이며, 티켓이 요청자·담당자·자산을 모두 참조하는 구조다. 컬럼명은 Oracle 예약어(DATE, TIME 등)를 피해서 짓는다.

| 테이블 | 주요 컬럼 | 관계 |
| --- | --- | --- |
| MEMBER | member\_id(PK), login\_id(UK), password, name, role, dept | 티켓·자산의 소유자·담당자 |
| CATEGORY | category\_id(PK), name | 티켓 분류 (PC, 네트워크, 계정, 소프트웨어 등) |
| ASSET | asset\_id(PK), asset\_no(UK), type, model, status, owner\_id(FK→MEMBER) | 사용자에게 지급 |
| TICKET | ticket\_id(PK), title, content, category\_id(FK), priority, status, requester\_id(FK), assignee\_id(FK), asset\_id(FK, null 허용), created\_at, closed\_at, version | 중심 테이블 |
| TICKET\_COMMENT | comment\_id(PK), ticket\_id(FK), writer\_id(FK), content, created\_at | 티켓 1 : N |
| TICKET\_FILE | file\_id(PK), ticket\_id(FK), orig\_name, saved\_name, file\_size | 티켓 1 : N |
| TICKET\_HISTORY | history\_id(PK), ticket\_id(FK), changed\_by(FK), type(상태/배정), from\_value, to\_value, changed\_at | 티켓 1 : N |
| API\_CALL\_LOG | log\_id(PK), target(SLACK/GITHUB), ticket\_id(FK), success\_yn, response\_code, message, called\_at | 외부 호출 이력 |
| GITHUB\_LINK | ticket\_id(PK, FK), issue\_number, issue\_url | 티켓 1 : 0..1 (선택 기능) |

**설계 포인트**

- `TICKET.version` 컬럼으로 동시 수정 충돌을 낙관적 락 방식으로 감지한다.
- 자산별 장애 이력은 `TICKET.asset_id`로 조회하며, 반복 장애 장비 통계의 기준이 된다.
- 기본 키 생성 방식과 페이징 쿼리는 Oracle 버전에 따라 달라진다(12c 이상은 IDENTITY와 OFFSET FETCH, 11g는 SEQUENCE와 ROWNUM 사용). 버전은 12번 미정 사항에서 확정한다.

## 9. 팀 역할 분담

레이어별이 아니라 도메인별로 나눠, 각자 Controller부터 JSP, Mapper까지 맡아 개인 기여가 분명하게 드러나도록 한다.

| 담당 | 범위 | 비고 |
| --- | --- | --- |
| A | 공통 설정(XML, MyBatis, 트랜잭션, 파일 업로드), 권한 Interceptor, 예외 처리, Tomcat 배포 | 1주차 초반에 설정을 먼저 완료해 공유 |
| B | 회원·로그인·역할 관리, 자산 CRUD, 사용자별 지급 현황 |  |
| C | 티켓 등록·수정·첨부파일, 티켓 목록·검색·페이징(동적 쿼리) |  |
| D | 상태 전이 검증, 담당자 배정, 이력 관리, 티켓-자산 연결, 댓글 |  |
| E | Slack·GitHub 연동, API 호출 이력, 통계 대시보드 | 부담이 크므로 대시보드는 마지막에 진행 |

**협업 규칙**

- XML 설정 파일은 충돌이 잦으므로 A만 수정하고, 다른 담당은 요청한다.
- Mapper XML은 도메인별 파일로 분리한다.
- Git은 기능 브랜치와 PR 리뷰로 진행하고, 리뷰 기록을 README에 남긴다.
- 공통 코드(상태값, 우선순위)는 Enum과 공통 상수 한 곳에서 관리한다.

## 12. 포트폴리오 산출물과 미정 사항

면접에서 "무엇을 만들었나"보다 "어떤 문제를 어떻게 풀었나"를 설명할 수 있도록 아래 기록을 남긴다.

**산출물**

- README: 프로젝트 소개, ERD, 상태 전이도, 아키텍처, 실행 방법, 역할별 기여
- 기능 명세서와 화면 목록, 시연 시나리오
- 트러블슈팅 기록(문제, 원인, 해결, 전후 비교)
- 테스트 코드: 상태 전이 검증, 권한 처리 중심의 JUnit 테스트
- 배포: Tomcat 기반 실행 환경(가능하면 AWS EC2)

**어필 포인트**

- **상태 전이 검증**: 허용되지 않는 전이를 서비스 계층에서 차단하고 테스트로 증명
- **권한 처리**: Interceptor 기반 역할별 접근 제어
- **동적 쿼리와 인덱스**: 조건 조합 검색 쿼리의 실행 계획 확인과 인덱스 적용 전후 비교
- **동시 수정 충돌 방지**: version 컬럼 기반 낙관적 락
- **외부 연동 안정성**: 비동기 처리, 타임아웃, 재시도, 호출 이력

**미정 사항**

- [ ] Oracle 버전(12c 이상인지 11g인지)과 개발 DB 공유 방식(개인 로컬 또는 공용 서버)
- [ ] 팀원별 Spring 경험 수준(공통 설정 담당 A 선정 기준)
- [ ] Slack 워크스페이스와 GitHub 데모 저장소를 누가 만들고 관리할지
- [ ] 선택 기능(통계, GitHub 연동)의 착수 여부는 2주차 말 점검 결과로 결정
- [ ] 발표·시연 형식과 일자

본 계획서의 일정과 분량 판단은 일반적인 개발 경험에 바탕한 추정이며, 실제 팀 역량에 맞춰 조정이 필요하다.
