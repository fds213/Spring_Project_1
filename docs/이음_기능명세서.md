# 기능명세서

## 1. 공통 규칙

### 1.1 계정 상태·역할·주소

| 항목 | 확정 규칙 |
|---|---|
| 직원 계정 상태 | 승인 대기(`REQUESTED`) → 승인되면 사번을 받고 바로 사용 중(`ACTIVE`), 반려되면 `REJECTED`, 승인 전에 직원이 요청을 취소하면 `CANCELED`. 사용 중 계정을 비활성화하거나 퇴사 처리하면 비활성(`RETIRED`)이 된다. 로그인은 사용 중 계정만 된다. 가입 요청은 따로 승인 대기·승인·반려·취소로 남는다(1.7). 원래 설계의 계정 생성 전(`APPROVED`)·자리 대기(`WAITING`)와 승인·계정 생성 1시간 기한은 구현하지 않음(요구분석서 3장 '이번 제외', 단순화 ①②). |
| 역할 | DB 값 직원·IT 담당·인사 담당·업체 관리자(`ROLE_EMP`, `ROLE_IT`, `ROLE_HR`, `ROLE_ADMIN`), 한 계정에 하나. 이음 운영자는 이음 운영 업체(`ieum0000`) 소속 계정에 운영자 역할(`ROLE_OPS`)을 둔다. 운영자 역할은 `ieum0000` 소속에만 줄 수 있고, 이음 운영 업체와 운영자 계정은 체험 신청이 아니라 초기 데이터로 만든다. 부서장과 결재자는 역할이 아니라 설정·상황으로 정한다. 업체가 사원 관리의 [역할 변경]에서 줄 수 있는 역할은 직원·IT 담당·인사 담당뿐이다(업체 관리자는 업체당 1명, 운영자는 `ieum0000` 소속만). |
| 메뉴와 역할 | 모든 직원의 기본 메뉴는 메인·공지사항, 기안 작성·결재함, '장애·문의 접수'·내 티켓·내 장비·이음 장애 문의, 근태·연차·일정·지문 시뮬레이터, 채팅·부서 게시판·익명 게시판·자료실·지도, 조직도다. 여기에 IT 담당은 티켓 처리·자산 관리, 인사 담당은 사원 관리·'근태·연차 관리'·휴일 관리·근태 단말기, 부서장은 가입 승인이 더 보인다. 업체 관리자에게는 이것을 모두(티켓 처리·자산 관리·사원 관리·가입 승인·'근태·연차 관리'·휴일 관리·근태 단말기)와 부서 관리·직급 관리·지점 관리·이용 결제가 보인다. 관리자 혼자이거나 IT·인사 담당을 아직 정하지 않은 업체도 이 기능을 쓸 수 있어야 하기 때문이다. 업체 관리자·인사 담당에게는 지문 시뮬레이터 링크 대신 근태 단말기 화면이 보이고, 시뮬레이터는 그 화면에서 연다. 역할은 메뉴를 따로 두지 않고 사원 관리 화면의 [역할 변경]에서 업체 관리자만 바꾼다(CFG-01). 운영자는 이음 운영 업체의 직원 기본 메뉴와 운영 전용 메뉴(업체 관리, 신청 현황, 비회원 접수, 회원 접수)를 함께 쓴다(요구분석서 2장·OPS-02). 업체별 계정은 업체 관리 상세에서 본다. 따로 두려던 업체 계정·운영 데이터 메뉴, 업체 관리자의 지원 허가 승인 메뉴, 구독 권한을 받은 사람의 이용 결제 메뉴는 구현하지 않음(요구분석서 3장: 범위 표의 OPS-01은 업체·문의 목록만이고, 지원 허가·위임 결제 권한은 '이번 제외'). |
| 화면 주소 | 업무 화면 `/<모듈>/<기능>`, 관리 화면 `/<모듈>/admin/<기능>`(관리 역할만), 운영자 `/ops/...`(운영자 역할만). 로그인 없이 여는 주소는 상품 소개(`/`), 체험 신청(`/trial`), 도입 문의(`/inquiry`), 로그인(`/login`), 직원 계정 만들기(`/join`: 승인 요청·상태 확인·요청 취소, 비밀번호 찾기 `/join/password`), 앱 설치 파일(`manifest.json`·서비스 워커), 지문 시뮬레이터 화면(`/attendance/simulator`)이다. 단말기 API(`/api/**`)는 로그인 세션 대신 `X-Device-Key` 단말기 키로 확인한다(1.9). 이용 결제 화면은 `subscription` 모듈에 둔다. `/`·`/login`·앱 설치 파일·`/attendance/simulator`는 그 주소만 열고, `/trial`·`/inquiry`·`/join`은 하위 주소(인증 링크·다시 보내기·비밀번호 찾기 등)까지 연다. 가입 승인(업체 관리자·그 부서 부서장)은 역할만으로 정해지지 않으므로 관리 화면 주소 밖(`/employee/join`)에 두고, 서버가 요청마다 그 사람이 맞는지 확인한다. 이용 결제(`/subscription/billing`)도 업무 화면 주소에 두고, 서버가 요청마다 업체 관리자인지 확인한다. |
| 로그인 | 업체 코드 + 사번 + 비밀번호. 같은 사번이 다른 업체에 있을 수 있으므로 업체 코드와 함께 사원을 찾는다. 비밀번호는 BCrypt로 저장한다. 로그인이 끊긴 화면 요청은 로그인 화면으로, AJAX 요청은 401로 응답해 화면이 다시 로그인하게 한다. 이메일 인증 전·사용 중지 같은 상태 안내는 비밀번호가 맞을 때만 보여 주고, 틀리면 같은 오류 문구를 보인다(남의 계정 상태가 드러나지 않게). 계정 잠김 안내만 예외다(1.5). |
| 운영자 심사 없음 | 체험 신청 즉시 업체·관리자 계정이 생기므로 운영자 화면에 계정 발급 기능은 없다. 운영자는 신청 현황에서 이메일 인증 상태(대기·완료)만 본다. |
| 업체 이용 상태 | 체험 중·유료·체험 만료·유료 만료 네 가지로 나눈다(만료 안내 문구가 체험과 유료에서 다르므로). 이용 상태는 저장하지 않고 요청마다 이용 기간(`SERVICE_PERIOD`)의 종류와 만료 시각으로 계산한다(체험 중 `TRIAL`, 유료 `PAID`, 만료 `EXPIRED`. 체험 만료와 유료 만료는 마지막 기간이 유료인지로 나눈다). 결제·만료로 로그인 중에도 바뀌므로 세션에 담아 두지 않는다. 이메일 인증 전인지는 이메일 인증 일시가 비어 있는지로 본다. 만료 3개월 뒤 업무 자료를 지우고 자료 삭제를 표시하는 것은 구현하지 않음(요구분석서 3장 '이번 제외'). |
| 요청 방식 | 데이터를 바꾸는 요청은 모두 POST로 보내고, GET 요청으로는 아무것도 바꾸지 않는다(인증 링크도 링크를 열면 확인 화면만 보이고 버튼이 POST로 인증한다). 만료 읽기 전용 검사는 GET·HEAD·OPTIONS가 아닌 요청을 쓰기로 보고 결제와 요구분석서 3.11의 예외만 통과시킨다(DEM-03). |

### 1.2 메일 발송

관련: 요구분석서 3.8

이메일(체험 인증, 문의 접수·답변, 비밀번호 찾기 코드)은 서버가 Spring JavaMailSender와 SMTP(팀 공용 Gmail 계정, 앱 비밀번호)로 보낸다. 발송 전에 기록을 남기고 트랜잭션 밖에서 보낸 뒤 결과(완료·실패와 사유)를 기록하며, 계정 정보는 저장소에 올리지 않는 설정 파일에 둔다. 결제 안내 메일(SUB-06)과 직원 이메일 인증 코드(ACC-04)는 구현하지 않음(요구분석서 3장 '이번 제외').

- 발송 기록은 `MAIL_OUTBOX`(메일 한 통)와 `MAIL_ATTEMPT`(보낸 시도)에 남기고, 메일 본문은 저장하지 않는다.
- 설정 파일(`config/mail.properties`)이 없거나 `mail.enabled=false`이거나 계정이 비어 있으면 메일을 보내지 않고 이메일 인증도 요구하지 않는다. 메일은 보내면서 인증 요구만 끄려면 `mail.require-verification=false`로 둔다. 인증을 요구하지 않으면 인증 전 로그인 거절과 직원 가입의 '인증 전 업체' 거절이 함께 꺼진다.

### 1.3 PWA 설치 안내

관련: 요구분석서 3.8

상품 홈페이지의 다운로드 버튼이 브라우저의 설치 창을 띄우지 못하면(이미 설치됨, 설치를 지원하지 않는 브라우저) 브라우저별 설치 방법을 안내한다. 설치한 앱 창 안에서 상품 소개·체험 신청·도입 문의 페이지가 열리면 로그인 화면으로 보낸다.

### 1.4 업체 코드 발급

관련: 요구분석서 ACC-03·3.11

- 업체 코드는 체험 신청 때 `ieum`+숫자 4자리(0001~9999)를 무작위로 뽑고, 결제해도 바꾸지 않는다. 이음 운영 업체는 `ieum0000`이다.
- 이미 있는 코드와 겹치면 다시 뽑는다(최대 10번).
- 업체 목록 정렬은 업체 코드가 아니라 내부 번호(`company_id`)·신청일로 한다.
- 업체 코드 컬럼에는 고유 제약이 있다. 먼저 있는지 조회한 뒤 저장하는 방식은 동시 신청에서 겹칠 수 있어 쓰지 않고, 고유 제약에 걸리면 다시 뽑는다.
- 10번 모두 겹치면 신청을 저장하지 않고 503과 '업체 코드를 더 만들 수 없어 지금은 새 체험 신청을 받을 수 없습니다. 도입 문의로 연락해 주세요.'를 보인다(번호 뽑는 부분을 바꿔 끼워 '계속 겹침'을 시험한다).
- 시연 데이터의 업체는 정해 둔 코드로 넣는다.

### 1.5 로그인 실패 제한

관련: 요구분석서 ACC-03

- 같은 계정(업체 코드 + 사번)의 비밀번호를 연속 5번 틀리면 그 계정을 10분 동안 잠근다. 잠긴 동안은 비밀번호가 맞아도 로그인되지 않고 남은 시간을 안내한다.
- 로그인에 성공하면 횟수를 0으로 되돌린다. 10분이 지나면 잠금이 풀리고 0부터 다시 센다.
- 없는 계정은 세지 않고 틀렸다고만 안내한다.
- 접속(IP) 기준의 제한은 두지 않는다.
- 구현: 로그인 계정 표(`USER_ACCOUNT`)의 실패 횟수(`FAILED_LOGIN_COUNT`)·잠금 해제 시각(`LOCKED_UNTIL`)으로 세고, Spring Security의 계정 잠금(`UserDetails.isAccountNonLocked()`)으로 잠김을 알리며, 로그인 실패·성공 처리기에서 횟수를 고친다.
- 잠김 안내는 1.1 '로그인'의 '상태 안내는 비밀번호가 맞을 때만' 규칙의 예외다. Spring Security는 잠긴 계정을 비밀번호를 확인하기 전에 거절하기 때문이다.
- 받아들이는 약점: 사번이 업체 안에서 순서대로라 동료가 일부러 5번 틀려 남의 계정을 10분 잠글 수 있고(10분 뒤 저절로 풀림), 잠김 안내로 그 계정이 있다는 것이 드러난다. 이 프로젝트 범위에서는 받아들인다.

### 1.6 업체 구분·개발 제약

관련: 요구분석서 1장·3.8·3.11

- 하나의 애플리케이션·DB에서 업체 코드로 소속과 자료를 구분한다. 서버는 업체를 로그인한 사용자 정보에서만 정하고 주소·입력값의 업체 값을 믿지 않는다(3장 업체 분리).
- 예외: 이음 장애 문의(OPS-04)는 업체가 이음에게 보낸 문의라 업체 내부 자료가 아니다. 운영자는 업체 업무 자료 가운데 문의 표만 모든 업체 것을 읽고 답변을 쓰며, 문의 원문·작성자·업체는 바꾸지 못한다. 업체·신청·결제·계정 목록은 운영 메뉴에서 본다(OPS-01). 운영자도 다른 업체의 업무 자료(결재·근태 등)는 볼 수 없다(지원 허가는 구현하지 않음(요구분석서 3장 '이번 제외')).
- Spring Framework 5.3(XML 설정)·Spring Security·JSP·MyBatis·Oracle로 만들었다.
- PWA는 `manifest.json`(시작 주소 로그인, 독립 창)과 서비스 워커(화면 틀 파일 캐시, 캐시 이름을 올려 갱신)로 구성하고, 발표 PC의 localhost에서 설치해 확인했다. 고정 HTTPS 서버 배포는 구현하지 않음(요구분석서 3장 '이번 제외').
- 읽기 전용과 자료별 권한은 PWA 화면뿐 아니라 서버에서도 검사한다. 만료 중 차단은 API 우회 요청도 거절한다.

### 1.7 상태 값 목록

관련: 요구분석서 전체

DB에는 영문 코드를 저장하고 화면에는 한글로 보인다. 구현하지 않은 것은 그 칸에 "구현하지 않음"과 근거를 적었다.

| 가입 요청 | 승인 대기 → 승인 또는 반려, 승인 전에 직원이 취소 | `REQUESTED`, `APPROVED`, `REJECTED`, `CANCELED` | ACC-04·05 |

### 1.9 지문 시뮬레이터 연동

관련: 요구분석서 3.4 근태·3.10

사용자 기준 요구는 요구분석서 3.10에 있다.

시뮬레이터는 단말기 역할의 화면(`/attendance/simulator`, 로그인 없이 연다)이다. 업체 관리자·인사 담당이 근태 단말기 화면(`/attendance/admin/device`)에서 단말기 키를 발급하고 단말기 사용자 번호를 직원에 연결한다. 직원도 근태 화면(`/attendance/my`)에서 자기 번호(숫자 4자리)를 연결·해제할 수 있다. 시뮬레이터는 `X-Device-Key` 헤더에 키를 담아 `GET /api/attendance/device`(직원 목록), `POST /api/attendance/punch`(출근·퇴근)를 보내고, 서버가 받은 시각으로 근태 기록에 저장한다.

| 구분 | 구현 |
|---|---|
| 기록 저장 | 업체·직원에 연결된 서버 근태 기록에 저장한다. 브라우저에는 단말기 키만 저장하므로 브라우저를 초기화해도 기록은 남는다 |
| 직원 연결 | 업체·단말기 사용자 번호·직원의 연결을 근태 단말기 화면에서 관리하고, 직원은 근태 화면에서 자기 번호를 연결·해제한다(`POST /attendance/api/device-link`, `…/delete`). 번호는 숫자 4자리이고, 같은 업체의 다른 직원이 쓰는 번호면 409다. 업체가 다르면 같은 번호를 써도 섞이지 않는다 |
| 업체 식별 | 단말기 키로 소속 업체를 서버에서 찾는다. 키가 없거나 틀리면 401 |
| 체크 판정 | 서버가 받은 시각으로 출근·퇴근을 나누어 하루 각 1건만 저장한다. 출근 중복('오늘 이미 출근했습니다'), 출근 없는 퇴근, 퇴근 중복은 409 |
| 거절 | 만료 업체는 403(읽기 전용 제한을 시뮬레이터로 우회하지 못하게), 등록되지 않은 번호는 404, 재직 중이 아닌 직원은 403 |
| 화면 | 그 밖의 직원은 사이드 메뉴의 '지문 시뮬레이터' 링크로, 업체 관리자·인사 담당은 근태 단말기 화면에서 연다 |

#### ACC-04 직원 계정 신청

관련: 요구분석서 ACC-04

| 항목 | 내용 |
|---|---|
| 사용자·권한 | 업체 직원(로그인 없음). 업체 관리자에게 받은 업체 코드가 있어야 한다. 가입 열기·닫기는 업체 관리자(고른 부서)와 부서장(자기 부서) |
| 화면·주소 | 직원 계정 만들기 `/join`(승인 요청·상태 확인·요청 취소, 하위 주소 포함, 1.1). 가입 열기·닫기는 가입 승인 화면(ACC-05)에 두고, 가입 승인처럼 관리 화면 주소 밖에서 요청마다 업체 관리자·그 부서 부서장인지 확인한다(1.1). 로그인 없이 쓰는 주소: 업체 코드 확인 `GET /join/api/companies/{업체 코드}`(열린 부서·직급), 승인 요청 `POST /join/api/companies/{업체 코드}/requests`, 상태 확인 `GET …/requests/{요청 키}`, 요청 취소 `POST …/requests/{요청 키}/delete`. 요청 키는 승인 요청 때 받은 무작위 값이고, 서버는 그 해시만 저장한다. 가입 열기·닫기는 `POST /employee/api/join/openings`(열기), `POST /employee/api/join/openings/{부서}/delete`(한 부서 닫기), `POST /employee/api/join/openings/delete`(모두 닫기, 업체 관리자만) |
| 입력 | 업체 코드, 이름(1~100자), 부서(가입이 열린 부서 목록), 직급(목록), 이메일(254자 이하), 비밀번호(8자 이상)·비밀번호 확인. 가입 열기는 부서와 열어 둘 시간(10분·30분·1시간·3시간·24시간) |
| 처리 | 가입 열기는 부서마다 끝나는 시각을 저장하고, 그 시각이 지나면 따로 닫지 않아도 닫힌 것으로 본다(1.8). 업체 코드 [확인]은 열린 부서만 돌려주고, 승인 요청을 받을 때 그 부서가 아직 열려 있는지 다시 확인한다. 아래 세부 순서대로 받는다. 요청 키를 만들어 돌려준다. 요청은 만료되지 않는다(승인 1시간 기한은 구현하지 않음(요구분석서 3장 '이번 제외')). |
| 결과·오류 | 업체 코드 [확인]은 없는 업체 코드, 이용 기간이 끝난 업체, 이메일 인증 전 업체(인증을 요구하지 않는 설정이면 거르지 않음, 1.2), 가입이 열린 부서가 없음을 구분하지 않고 '가입을 받을 수 없는 업체 코드입니다' 한 문구로 거절한다(업체 코드의 숫자가 4자리뿐이고 [확인] 횟수 제한이 없어, 사유를 나누면 로그인 없이 실제 업체와 만료 여부가 드러난다). 승인 요청 때는 그사이 닫힌 부서, 같은 이메일로 승인 대기 중이거나 계정이 있음을 사유를 알려 거절한다. 부서장이 열면 보낸 부서와 관계없이 자기 부서만 열리고, 다른 부서를 닫으려 하면 403으로 거절한다. 이미 받은 요청은 가입이 닫힌 뒤에도 승인·반려할 수 있다. 같은 이메일의 계정이 비활성이면 업체 관리자에게 다시 사용을 요청하라고 안내한다. 입력 오류는 400('이름을 확인해 주세요', '이메일 형식이 맞지 않습니다', '비밀번호는 8자 이상으로 정해 주세요', '가입이 닫혔거나 없는 부서입니다', '없는 직급입니다'), 같은 이메일·비활성 계정은 409로 알린다 |
| 상태 값 | `REQUESTED`(1.7) |
| 확인 기준 | 가입 요청·승인, 이메일 인증·직원 승인 |

세부

- 직급은 직급 관리(CFG-01)의 목록에서 고른다.
- 요청하면 '승인 요청을 하였습니다. 업체 관리자나 부서장이 승인하면 바로 계정이 만들어집니다.'를 표시하고 입력칸을 잠근다.
- 화면은 이 순서로 채운다.
  - ① 업체 코드를 넣고 [확인]을 누르면 서버가 그 업체를 확인하고(없는 업체 코드·이용 기간이 끝난 업체·이메일 인증 전 업체, 가입이 열린 부서가 없는 업체는 여기서 한 문구로 거절) 가입이 열린 부서 목록을 불러온다.
  - ② 부서·직급을 목록에서 고르고 이름을 적는다.
  - ③ 이메일을 적는다. 형식과 길이만 확인하고, 같은 이메일로 승인 대기 중이거나 계정이 있으면 승인 요청 때 거절한다. 직원 이메일 인증 코드는 구현하지 않음(요구분석서 3장 '이번 제외', 단순화 ①).
  - ④ 비밀번호·비밀번호 확인을 적는다. 업체 코드 [확인]을 마치고, 이메일 형식이 맞고, 비밀번호(8자 이상, 확인과 같음)를 적으면 맨 아래 [승인 요청] 버튼이 켜진다.
- [확인]의 횟수는 제한하지 않는다. 업체 코드를 알아도 가입이 열린 동안 승인 요청만 할 수 있고, 계정은 업체 관리자·부서장이 승인해야 생기며, 승인 전 요청은 자리를 세지 않는다.
- 상태 확인·요청 취소는 요청할 때 받은 무작위 키(요청 키)로만 할 수 있다(요청 번호나 이메일만 알아서는 남의 요청을 볼 수 없게).
- 키를 잃으면(다른 PC 등) 상태 확인·취소를 할 수 없다. 요청은 만료되지 않으므로 업체 관리자나 부서장에게 반려를 부탁한 뒤 같은 이메일로 다시 요청한다. 같은 기기에서는 브라우저가 키를 기억해 화면을 다시 열어도 이어서 본다.

#### ACC-05 계정 생성 승인

관련: 요구분석서 ACC-05

| 항목 | 내용 |
|---|---|
| 사용자·권한 | 업체 관리자(업체 전체), 부서장(본인 부서). 만료 중에는 승인할 수 없다(요구분석서 3.11). 부서장이 없는 부서는 업체 관리자만 승인한다. |
| 화면·주소 | 가입 승인 `/employee/join`. 관리 화면 주소 밖(업무 화면 주소)에 두고 요청마다 승인자가 맞는지 확인한다(1.1). 화면 내용 `GET /employee/api/join`, 승인 `POST /employee/api/join/requests/{요청 번호}/approve`, 반려 `POST /employee/api/join/requests/{요청 번호}/reject` |
| 입력 | 승인·반려. 역할은 승인 뒤 사원 관리의 [역할 변경]에서 업체 관리자가 정한다(CFG-01) |
| 처리 | 비밀번호(8자 이상)는 승인 요청(ACC-04) 때 받는다. 승인하면 요청 행을 잠그고(대기 중일 때만), 쓰지 않은 다음 사번을 배정하고, 사용 중 계정이 구매 인원(CFG-01)보다 적은지 확인한 뒤 사원을 만들고 계정을 바로 `ACTIVE`로 바꾼다. 사번은 업체별 일련번호 행을 잠가 같은 업체의 승인을 한 줄로 세우므로 동시에 승인해도 겹치지 않는다. 자리가 차면 승인을 거절한다(자리 대기는 구현하지 않음(요구분석서 3장 '이번 제외')). |
| 결과·오류 | 구매 인원이 차면 '인원이 가득 차서 승인할 수 없습니다'로 거절, 이미 처리된 요청은 409, 부서장이 다른 부서 요청을 처리하면 403. 반려하면 요청과 계정이 `REJECTED` |
| 상태 값 | 요청 `REQUESTED` → `APPROVED`(계정 `ACTIVE`) 또는 `REJECTED`(1.7) |
| 확인 기준 | 가입 요청·승인, 승인 한도 |

세부

- 승인되면 직원 화면에 '승인되어 계정이 만들어졌습니다. 업체 코드와 아래 사번, 요청할 때 정한 비밀번호로 로그인하세요.'와 사번이 보이고, 버튼이 [로그인하러 가기]로 바뀐다.
- 승인 요청은 그 부서의 부서장과 업체 관리자에게 함께 알린다(가입 승인 메뉴 배지).
- 승인 화면에는 요청자의 이름·부서·직급과 요청자가 적은 이메일을 보여 준다(이메일 인증은 하지 않으므로 본인인지는 승인자가 판단한다).

#### ACC-06 이메일 인증

관련: 요구분석서 ACC-06

| 항목 | 내용 |
|---|---|
| 사용자·권한 | 체험을 신청한 업체 관리자(로그인 없음) |
| 화면·주소 | 인증 링크 `/trial/verify#일회용 값`의 확인 화면(공개 주소, 1.1). `#` 뒤의 값은 서버로 오지 않아 접속 기록에 남지 않는다 |
| 입력 | 링크에 담긴 일회용 값. 확인 화면의 [인증하기]를 POST로 보낸다(1.1 요청 방식). |
| 처리 | 다시 보내면 이전 링크는 무효다. 인증하면 이메일 인증 일시를 저장한다(1.1). |
| 결과·오류 | 인증 전 로그인은 "신청할 때 적은 이메일을 아직 인증하지 않았습니다. 인증 메일의 링크를 누른 뒤 로그인해 주세요"로 거절한다. 24시간이 지난 링크, 1분 안의 두 번째·하루 여섯 번째 다시 보내기는 거절한다. |
| 상태 값 | 이메일 인증 일시(비어 있으면 인증 전, 1.1) |
| 확인 기준 | 이메일 인증·직원 승인 |

세부

- 인증 메일은 일회용 링크이며, 다시 보내면 이전 링크는 무효가 된다.
- 인증 전 로그인 시도는 "신청할 때 적은 이메일을 아직 인증하지 않았습니다" 안내와 함께 거절한다.
- 인증 링크는 24시간 동안 쓸 수 있다.
- 다시 보내기는 1분에 한 번·하루 5번까지이며, 신청 완료 화면과 인증 전 로그인 거절 화면(비밀번호가 맞았을 때)에서 할 수 있다. 첫 메일은 5번에 세지 않고, 1분 제한은 링크를 발급한 시각으로 본다.
- 다시 보내기는 요청 값으로 업체를 받지 않고, 체험을 신청했거나 비밀번호를 맞힌 세션의 업체에만 보낸다(남의 메일함으로 보내지 못하게). 메일 본문에는 업체명 같은 입력값을 넣지 않는다.
- 메일을 끈 환경에서는 인증 메일을 보내지 않고 인증 전 로그인도 거절하지 않는다(1.2).
- 링크를 열면 바로 인증하지 않고 "인증하기" 버튼이 있는 화면을 보여 주며, 버튼을 눌러야 인증된다(메일 보안 검사가 링크를 먼저 열어도 인증이 쓰여 버리지 않게).

#### ACC-07 비밀번호 찾기·변경

관련: 요구분석서 ACC-07

| 항목 | 내용 |
|---|---|
| 사용자·권한 | 사용 중 계정. 만료 중에도 허용한다 |
| 화면·주소 | 변경은 헤더의 [비밀번호 변경] 창에서 `POST /employee/api/password`로 한다. 찾기는 로그인 화면의 "비밀번호 찾기" 링크로 여는 `/join/password`(로그인 없음, 1.1)에서 코드 보내기 `POST /join/api/password/code`, 코드 확인 `POST /join/api/password/verify`, 새 비밀번호 `POST /join/api/password/reset` 순서로 한다 |
| 입력 | 찾기는 업체 코드·사번·인증 코드·새 비밀번호, 변경은 현재 비밀번호·새 비밀번호 |
| 처리 | 새 비밀번호는 BCrypt로 저장한다(1.1). 아래 세부 순서대로 처리한다. |
| 결과·오류 | 업체 코드·사번이 틀려도, 1분·하루 5번 제한에 걸려도 코드 보내기는 같은 안내를 보인다. 메일을 보내지 않는 설정이면 409. 코드가 틀리면 400(남은 횟수), 코드가 없거나 10분이 지났거나 5번 틀렸거나 없는 계정이면 410(다시 보내기). 새 비밀번호 단계의 인증이 10분이 지났거나 이미 쓰였으면 410(처음부터), 그사이 사용 중 계정이 아니게 됐으면 409. 변경은 현재 비밀번호가 틀리거나 8자 미만·지금과 같으면 400, 그사이 다른 곳에서 바뀌었으면 409 |
| 상태 값 | - |
| 확인 기준 | 비밀번호 찾기 |

세부

- 비밀번호를 잊으면 로그인 화면의 "비밀번호 찾기"에서 업체 코드·사번을 넣고, 계정에 등록된 이메일로 받은 인증 코드를 맞힌 뒤 본인이 새 비밀번호(8자 이상)를 정한다.
- 계정이 있는지 드러나지 않도록 업체 코드·사번이 틀려도 같은 안내('등록된 이메일로 인증 코드를 보냈습니다. 받은 6자리를 10분 안에 넣어 주세요.')를 보이며, 코드는 사용 중 계정에만 보낸다.
- 인증 코드는 6자리이고 10분 동안 쓸 수 있다. 1분에 한 번, 하루 5번까지 보내며, 다시 보내면 이전 코드는 쓸 수 없다. 5번 틀리면 그 코드는 무효가 된다. 정기 작업 없이 요청 때 시각으로 판단한다(1.8).
- 코드를 맞히면 새 비밀번호를 정할 때 쓰는 긴 무작위 값(resetToken)을 주고 10분을 다시 준다. 코드와 이 값은 해시로만 저장한다.
- 새 비밀번호를 저장하면 로그인 5번 실패 잠금도 풀고, 로그인 화면으로 돌아가 업체 코드·사번을 채워 준다.
- 변경(헤더 창)은 현재 비밀번호를 확인한 뒤 바꾸며, 이미 로그인된 다른 기기의 세션은 끊지 않는다(다음 로그인부터 새 비밀번호).

#### 지점 세부

관련: 요구분석서 3.4

- 장애 접수 때 자산의 지점(자산이 없으면 사원의 근무 지점)을 기본값으로 채우고 실제 장애 지점을 확인받아 저장하며, 나중에 자산이 옮겨져도 이미 접수한 티켓의 지점은 바뀌지 않는다.

#### 근태 세부

관련: 요구분석서 3.4 근태·3.10

- 출근·퇴근은 지문 시뮬레이터가 서버로 보낸 기록으로 남긴다(1.9).
- 근태 정정: 직원은 근무일로부터 7일 안에 '퇴근 누락'(출근만 있는 날의 퇴근 시각)과 '결근'(기록이 없는 근무일의 출근·퇴근 시각)을 정정 요청한다. 결근 정정은 근무일만 받는다(입사일 전·주말·휴일·승인된 종일 연차인 날은 받지 않음).
- 처리자는 요청자 부서의 부서장이고, 부서장이 없거나 요청자 본인이 부서장이면 업체 관리자다. 본인 요청은 본인이 처리할 수 없다. 승인하면 퇴근 누락은 그날 근태의 퇴근 시각을 채우고 결근은 그날 근태를 새로 만든다. 반려·취소면 근태는 그대로다.
- 요청하면 처리자에게, 승인·반려하면 요청한 직원에게 업무 알림이 간다.

#### 연차 세부

관련: 요구분석서 3.4 연차·반차, 3.9

- 새 직원은 15일로 시작한다. 경력·직급으로 일수를 정하지 않는다. 사원 표의 이전 경력 칸(`PRIOR_CAREER_MONTHS`)은 직원 정보로 남겨 두고, 연차 일수 계산에는 쓰지 않는다.
- 추가 부여는 근태·연차 관리(`/attendance/admin/list`)에서 업체 관리자와 인사 담당만 한다. 그 밖의 역할과 부서장은 줄 수 없다.
- 추가 부여는 `POST /attendance/admin/api/leaves/{직원 번호}/grants`로 하며, 연차 변동 기록(`LEAVE_LEDGER`)에 `LC_GRANT` 한 줄과 사유(필수, 500자 이하)를 남긴다. 잘못 준 것은 사유와 함께 음수 한 줄로 되돌린다. 한 번에 ±30일, 0.5일 단위이고, 재직 중인 직원에게만 주며, 되돌린 뒤 남은 연차가 0일보다 적어지면 거절한다. 본인 연차는 본인이 바꿀 수 없다(403).
- 입사기념일 새 주기 부여와 이월은 구현하지 않음(1.8).
