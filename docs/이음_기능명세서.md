# 이음(IEUM) 기능명세서

작성일: 2026-10-29 · 짝 문서: [요구분석서](./이음_요구분석서.md)

이 문서는 요구분석서의 요구를 화면과 서버에서 어떻게 처리하는지 적는다. 업무 정책·권한·범위는 요구분석서가 기준이며, 두 문서가 다르면 요구분석서를 따른다. 결재·근태·티켓·자산·지도·채팅 같은 업무 기능의 흐름은 통합 계획서(`사내_그룹웨어_IT_Service_Hub_통합_프로젝트_계획서.md`)에 있다(2.4). 코드 작성 규칙(패키지·트랜잭션·보안)은 AGENTS.md를 따른다.

> **읽는 법**: 요구 ID(ACC-04 등)는 요구분석서와 같다. "요구분석서 3.11"처럼 적은 장·절은 요구분석서를, 그냥 "1.1"·"3장"으로 적은 것은 이 문서를 가리킨다. 2장 표의 "-"는 해당 없음, "미정"은 팀이 정해야 하는 칸이다.

> **이번 구현 범위**: 11/13 마감까지 만드는 범위는 요구분석서 3장 '이번 구현 범위' 표가 정한다. 이 문서의 명세 중 그 표에서 미루거나 뺀 것(예: 직원 승인·계정 생성 1시간 기한, '계정 생성 전', 자리 대기)은 이번에 만들지 않고, 표의 단순화 ①②대로 만든다.

## 1. 공통 규칙

### 1.1 계정 상태·역할·주소 (팀 저장소 기준)

팀 저장소의 로그인 기본 틀(`feature/authTest`, PR #8로 develop에 들어감)과 프론트 공통 틀에 맞춘 값이다.

| 항목 | 확정 규칙 |
|---|---|
| 직원 계정 상태 | 승인 대기(`REQUESTED`, 요청 시각 보관) → 반려(`REJECTED`) 또는 계정 생성 전(`APPROVED`, 사번 배정) → 사용 중(`ACTIVE`) / 자리 대기(`WAITING`) → 비활성(`RETIRED`, 퇴사 등). 요청 만료는 저장하지 않고 요청 시각으로 판단한다. 저장소 DB에는 사용 중과 비활성만 있으므로 승인 대기·반려·계정 생성 전·자리 대기 값을 추가한다. 로그인은 사용 중 계정만 된다. 업체 관리자가 계정 생성 전 계정을 취소하면 반려(`REJECTED`)로 끝난다(CFG-02). 승인 뒤 1시간 안에 계정을 만들지 않은 계정 생성 전(`APPROVED`)은 끝난 것으로 보고 자리를 세지 않는다. 요청 만료처럼 값을 저장하지 않고 승인 시각으로 판단한다. |
| 역할 | 저장소 DB 값 직원·IT 담당·인사 담당·업체 관리자(`ROLE_EMP`, `ROLE_IT`, `ROLE_HR`, `ROLE_ADMIN`), 한 계정에 하나. 이음 운영자는 이음 운영 업체(`ieum0000`) 소속 계정에 운영자 역할(`ROLE_OPS`)을 둔다. 운영자 역할은 `ieum0000` 소속에만 줄 수 있고, 이음 운영 업체와 운영자 계정은 체험 신청이 아니라 초기 데이터로 만든다. 부서장과 결재자는 역할이 아니라 설정·상황으로 정한다. 업체가 역할 관리에서 줄 수 있는 역할은 직원·IT 담당·인사 담당뿐이다(업체 관리자는 업체당 1명, 운영자는 `ieum0000` 소속만). |
| 메뉴와 역할 | 직원 기본 메뉴에 IT 담당은 티켓 처리·자산 관리, 인사 담당은 사원 관리·근태·연차 관리·휴일 관리, 업체 관리자는 티켓 처리·사원 관리·가입 승인·부서 관리·역할 관리·이용 결제, 부서장은 가입 승인이 더 보인다. 운영자는 이음 운영 업체의 직원 기본 메뉴와 운영 전용 메뉴(업체 관리, 업체 계정, 신청 현황, 비회원 접수, 회원 접수, 운영 데이터)를 함께 쓴다(요구분석서 2장·OPS-02). 모든 직원의 기본 메뉴에는 이음 장애 문의가 있고, 업체 관리자에게는 지원 허가 승인이, 구독 권한을 받은 사람에게는 이용 결제(받은 권한만)가 더 보인다(OPS-04·SUB-01). 업체 관리자에게는 자산 관리·근태·연차 관리·휴일 관리·지점 관리도 보인다. 관리자 혼자이거나 IT·인사 담당을 아직 정하지 않은 업체도 이 기능을 쓸 수 있어야 하기 때문이다. |
| 화면 주소 | 업무 화면 `/<모듈>/<기능>`, 관리 화면 `/<모듈>/admin/<기능>`(관리 역할만), 운영자 `/ops/...`(운영자 역할만). 로그인 없이 여는 주소는 상품 소개(`/`), 체험 신청(`/trial`), 도입 문의(`/inquiry`), 로그인(`/login`), 직원 계정 만들기(`/join`: 승인 요청·상태 확인·계정 생성), 앱 설치 파일. 이용 결제 화면은 `subscription` 모듈에 둔다. `/`는 그 주소만 열고, 나머지 공개 주소는 하위 주소(인증 링크·다시 보내기·계정 생성 처리·비밀번호 찾기 등)까지 연다. 가입 승인(업체 관리자·그 부서 부서장)과 이용 결제(업체 관리자·구독 권한을 받은 사람)는 역할만으로 정해지지 않으므로 관리 화면 주소 밖(각 모듈의 업무 화면 주소)에 두고, 서버가 요청마다 그 사람이 맞는지 확인한다. |
| 로그인 | 업체 코드 + 사번 + 비밀번호. 같은 사번이 다른 업체에 있을 수 있으므로 업체 코드와 함께 사원을 찾는다. 비밀번호는 BCrypt로 저장한다. 로그인이 끊긴 화면 요청은 로그인 화면으로, AJAX 요청은 401로 응답해 화면이 다시 로그인하게 한다. 이메일 인증 전·자리 대기 같은 상태 안내는 비밀번호가 맞을 때만 보여 주고, 틀리면 같은 오류 문구를 보인다(남의 계정 상태가 드러나지 않게). 계정 잠김 안내만 예외다(1.5). |
| 운영자 심사 없음 | 체험 신청 즉시 업체·관리자 계정이 생기므로 운영자 화면에 계정 발급 기능은 없다. 운영자는 신청 현황에서 이메일 인증 상태(대기·완료)만 본다. |
| 업체 이용 상태 | 체험 중·유료·체험 만료·유료 만료 네 가지로 나눈다(만료 안내 문구가 체험과 유료에서 다르므로). 이메일 인증 전인지는 이메일 인증 일시가 비어 있는지로 보고, 만료 3개월이 지나 업무 자료를 지운 업체에는 자료 삭제 표시를 남긴다(OPS-08 재구매). 이용 상태는 결제·만료로 로그인 중에도 바뀌므로 세션에 담아 두지 않고 요청마다 DB에서 확인한다. 값을 저장할지 만료일로 계산할지와 코드 이름은 DB 리드가 정한다. |
| 요청 방식 | 데이터를 바꾸는 요청은 모두 POST로 보내고, GET 요청으로는 아무것도 바꾸지 않는다(인증 링크도 링크를 열면 확인 화면만 보이고 버튼이 POST로 인증한다). 만료 읽기 전용 검사는 GET이 아닌 요청을 쓰기로 보고 결제와 요구분석서 3.11의 예외만 통과시킨다. |

### 1.2 메일 발송

관련: 요구분석서 3.8

이메일(체험 인증, 문의 접수·답변, 결제 안내, 직원 인증 코드, 비밀번호 찾기 코드)은 서버가 Spring JavaMailSender와 SMTP(팀 공용 Gmail 계정, 앱 비밀번호)로 보낸다. 발송 전에 기록을 남기고 트랜잭션 밖에서 보낸 뒤 결과(완료·실패와 사유)를 기록하며, 계정 정보는 저장소에 올리지 않는 설정 파일에 둔다.

### 1.3 PWA 설치 안내

관련: 요구분석서 3.8

상품 홈페이지의 다운로드 버튼이 브라우저의 설치 창을 띄우지 못하면(이미 설치됨, 설치를 지원하지 않는 브라우저) 브라우저별 설치 방법을 안내한다. 설치한 앱 창 안에서 상품 소개·체험 신청·도입 문의 페이지가 열리면 로그인 화면으로 보낸다.

### 1.4 업체 코드 발급

관련: 요구분석서 ACC-03·3.11

- 업체 코드는 체험 신청 때 `ieum`+숫자 4자리(0001~9999)를 무작위로 뽑고, 결제해도 바꾸지 않는다. 이음 운영 업체는 `ieum0000`이다.
- 이미 있는 코드와 겹치면 다시 뽑는다(최대 10번).
- 업체 목록 정렬은 업체 코드가 아니라 내부 번호(`company_id`)·신청일로 한다.
- 업체 코드 컬럼에 고유 제약을 둔다(DB 담당 확인). 먼저 있는지 조회한 뒤 저장하는 방식은 동시 신청에서 겹칠 수 있어 쓰지 않고, 고유 제약에 걸리면 다시 뽑는다.
- 10번 모두 겹치면 새 신청을 받을 수 없다고 안내한다(번호 뽑는 부분을 바꿔 끼워 '계속 겹침'을 시험한다).
- 시연 데이터의 업체는 정해 둔 코드로 넣는다.

### 1.5 로그인 실패 제한

관련: 요구분석서 ACC-03

- 같은 계정(업체 코드 + 사번)의 비밀번호를 연속 5번 틀리면 그 계정을 10분 동안 잠근다. 잠긴 동안은 비밀번호가 맞아도 로그인되지 않고 남은 시간을 안내한다.
- 로그인에 성공하면 횟수를 0으로 되돌린다. 10분이 지나면 잠금이 풀리고 0부터 다시 센다.
- 없는 계정은 세지 않고 틀렸다고만 안내한다.
- 접속(IP) 기준의 제한은 두지 않는다.
- 구현: 사원 표에 실패 횟수·잠금 해제 시각 두 칸을 두고(DB 리드), Spring Security의 계정 잠금(`UserDetails.isAccountNonLocked()`)으로 잠김을 알리며, 로그인 실패·성공 처리기에서 횟수를 고친다.
- 잠김 안내는 1.1 '로그인'의 '상태 안내는 비밀번호가 맞을 때만' 규칙의 예외다. Spring Security는 잠긴 계정을 비밀번호를 확인하기 전에 거절하기 때문이다.
- 받아들이는 약점: 사번이 업체 안에서 순서대로라 동료가 일부러 5번 틀려 남의 계정을 10분 잠글 수 있고(10분 뒤 저절로 풀림), 잠김 안내로 그 계정이 있다는 것이 드러난다. 이 프로젝트 범위에서는 받아들인다.

### 1.6 업체 구분·개발 제약

관련: 요구분석서 1장·3.8·3.11

- 하나의 애플리케이션·DB에서 업체 코드로 소속과 자료를 구분한다. 서버는 업체를 로그인한 사용자 정보에서만 정하고 주소·입력값의 업체 값을 믿지 않는다(3장 업체 분리).
- 기존 Spring Framework·JSP·MyBatis·Oracle을 유지한다. 기술 스택과 코드 규칙은 AGENTS.md를 따른다.
- PWA 설치 구성·갱신 방식·웹 주소는 팀이 설계한다.
- 읽기 전용과 자료별 권한은 PWA 화면뿐 아니라 서버에서도 검사한다. 만료 중 차단은 API 우회 요청도 거절한다.

  - ③ 이메일을 적고 [인증 코드 받기]로 받은 코드를 맞힌다. 같은 이메일로 승인 대기 중이거나 계정이 있으면 코드를 보내기 전에 거절한다. 인증 코드는 6자리 숫자이고 10분 동안 쓸 수 있으며, 5번 틀리면 그 코드는 무효가 되어 새 코드를 받아야 한다. 코드 다시 받기는 1분에 한 번·하루 5번까지다.
  - ④ 이메일 인증을 마쳐야 맨 아래 [승인 요청] 버튼이 켜진다.
- [확인]의 횟수는 제한하지 않는다. 업체 코드를 알아도 할 수 있는 것은 승인 요청뿐이고, 계정은 업체 관리자·부서장이 1시간 안에 승인해야 생기며, 승인 전 요청은 자리를 세지 않는다.
- 요청한 지 1시간이 지난 요청은 승인 대기로 세지 않는다.
- 상태 확인·요청 취소·계정 생성은 요청할 때 받은 무작위 키(요청 키)로만 열 수 있다(요청 번호나 이메일만 알아서는 남의 요청을 볼 수 없게).
- 키를 잃으면(다른 PC 등) 승인 대기 요청은 요청 뒤 1시간, 계정 생성 전은 승인 뒤 1시간이 지나면 끝나므로 그 뒤 다시 요청한다(ACC-05).

#### ACC-05 계정 생성 승인

관련: 요구분석서 ACC-05

| 항목 | 내용 |
|---|---|
| 사용자·권한 | 업체 관리자(업체 전체), 부서장(본인 부서). 만료 중에는 승인할 수 없다(요구분석서 3.11). 부서장이 없는 부서는 업체 관리자만 승인한다. |
| 화면·주소 | 가입 승인. 관리 화면 주소 밖(업무 화면 주소)에 두고 요청마다 승인자가 맞는지 확인한다(1.1). 모듈과 세부 주소는 미정 |
| 입력 | 승인·반려, 역할(업체 관리자만, IT·인사 담당). 직원 쪽 계정 생성은 비밀번호·비밀번호 확인 |
| 처리 | 요청 뒤 1시간 안인지와 승인 한도(CFG-01)를 확인하고 쓰지 않은 다음 사번을 배정한다. 동시에 승인할 때 사번이 겹치지 않게 하는 방식은 미정. 직원이 비밀번호(8자 이상)를 정하면 `ACTIVE`, 자리 대기로 승인된 요청은 `WAITING`이 된다. 계정 생성은 승인 뒤 1시간 안에만 된다. |
| 결과·오류 | 요청 1시간이 지난 승인 거절, 승인 한도를 넘는 승인 거절, 반려하면 `REJECTED`. 승인 뒤 1시간이 지난 계정 생성 거절. |
| 상태 값 | `REQUESTED` → `REJECTED` 또는 `APPROVED` → `ACTIVE`·`WAITING`(1.7) |
| 확인 기준 | 가입 요청·승인, 승인 한도·자리 대기 |

세부

- 직원 화면에는 "승인 완료되었습니다"와 함께 잠긴 사번 칸, 비밀번호·비밀번호 확인칸이 나타나고 버튼이 "계정 생성"으로 바뀐다.
- 승인 요청은 그 부서의 부서장과 업체 관리자에게 함께 알린다(가입 승인 메뉴 배지).
- 승인 화면에는 요청자의 이름·부서·직급과 함께 인증된 이메일을 보여 준다(본인인지는 승인자가 판단하므로).
- 계정을 다 만들면 완료 화면에 로그인용 업체 코드와 사번을 보여 준다.

- 링크를 열면 바로 인증하지 않고 "인증하기" 버튼이 있는 화면을 보여 주며, 버튼을 눌러야 인증된다(메일 보안 검사가 링크를 먼저 열어도 인증이 쓰여 버리지 않게).

## 3. 처리 규칙과 확인 기준

| 문의 이메일 | WEB-02·03 | 접수 시 사용자에게 본인 문의 내용이 전달되고 운영자 문의관리에 등록되는지 확인한다. 운영자가 답변하면 사용자 이메일로 답변을 발송한다. 홈페이지 문의번호·비밀번호 조회는 제공하지 않는다. |

| 데모 인원 | DEM-01 | 신청과 변경 모두 관리자 포함 10명 이하로 제한하며 10명 이하 수정에 결제를 요구하지 않는다. 대상 교체 후 제외된 사용자의 접근을 차단한다. |
| 가입 요청·승인 | ACC-03·04·05 | 없는 업체 코드, 만료 업체, 인증 전 업체, 같은 이메일로 승인 대기 중이거나 계정이 있는 요청은 사유별로 거절한다. 승인하면 쓰지 않은 다음 사번이 순서대로 붙고, 동시에 승인해도 사번이 겹치지 않는다. 요청 뒤 1시간이 지나면 승인할 수 없고 다시 요청해야 한다. 부서장은 자기 부서 요청만, 업체 관리자는 전체를 승인한다. 승인 전·만료·자리 대기 계정의 로그인은 상태에 맞는 안내로 거절한다. 상태 안내는 비밀번호가 맞을 때만 보인다. 상태 확인·취소·계정 생성은 요청 때 받은 키 없이 열리지 않는다. 승인 화면에 요청자 이메일이 보인다. 업체 관리자가 계정 생성 전 계정을 취소하면 자리가 돌아오고 그 사번은 다시 쓰지 않는다. 이메일을 인증하지 않으면 [승인 요청]이 되지 않는다. 계정 생성은 승인 뒤 1시간 안에 비밀번호 8자 이상이면 되고, 1시간이 지나면 거절된다. 부서장이 없는 부서의 요청은 업체 관리자만 승인할 수 있다. |

| 문의 이메일 횟수 | WEB-02 | 같은 이메일로 여러 건을 접수해도 모두 저장·등록된다. 접수 메일 발송이 실패해도 문의는 남는다. |
| 만료 후 읽기 전용 | DEM-03, SUB-04, 3.11 | 데모·유료 모두 기존 활성 사용자 전원 로그인·자료별 조회·다운로드·기존 대화 열람과 만료 팝업을 확인한다. 관리자 결제 외 쓰기를 화면·API·채팅·시뮬레이터에서 거절하고 장애 문의 등록도 차단한다. 요구분석서 3.11의 예외(본인 비밀번호 변경·찾기, 관리자의 비활성화·계정 생성 전 취소)는 만료 중에도 된다. |
