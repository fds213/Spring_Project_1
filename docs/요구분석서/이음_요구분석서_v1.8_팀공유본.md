# 이음(IEUM) 요구분석서

수정일: 2026-10-28 · 버전: 1.8 · 상태: 팀 공유·검토용 — 팀장 결정(가입 키, 가입 키 [확인] 실패 제한, 업체 코드 무작위)과 제안(로그인 실패 제한, 계정 삭제 뒤 남기는 기록)을 반영

이전 버전: [v1.7 팀공유본](./이음_요구분석서_v1.7_팀공유본.md). v1.7 본문(제안 포함)은 그대로 두고, 10/28 저녁 팀 의논 뒤 팀장이 정한 세 가지와 빈 곳을 채운 제안 두 가지를 넣었다. ① 가입 키: 직원 계정 만들기는 업체 코드가 아니라 업체별 가입 키로 업체를 찾는다. 로그인·비밀번호 찾기는 업체 코드 그대로다(ACC-04·08). ② 가입 키 [확인]은 같은 IP에서 틀린 키가 10분 안에 5번이면 10분 거절한다(v1.7 제안의 '1분에 10번'을 바꿈). ③ 업체 코드는 신청 순서가 아니라 무작위 4자리다(ACC-03, 3.11). 제안은 로그인 실패 제한(3.12)과 계정 삭제 뒤 남기는 기록(OPS-06)이며, 기존 칸에 더한 새 제안은 "(v1.8 제안)"으로 표시했다. 바뀐 곳 전체는 5장에 있다.

> **확인**: 사용자와 합의한 요구사항. **제안**: v1.6~v1.8에서 비어 있던 곳을 채우거나 팀원 의견을 정리한 안으로, 팀 확인 전이다. 표 칸 안에서는 "(제안)" 뒤의 문장이 제안이다. ~~취소선~~은 v1.7 제안으로 바뀌는 기존 확인 문장이며, 팀이 제안을 확인하면 지운다. v1.8의 팀장 결정은 확정이라 취소선 없이 본문을 고쳤고, 이전 내용은 5장에 적었다. **계획안**: 기존 문서에서 가져온 검토 대상. **미확정**: 답변 후 결정할 정책. 구현 완료 여부를 의미하지 않는다. 기존 초안은 비교용으로 보존한다.

## 1. 목적과 전체 흐름

이음은 업체에 그룹웨어를 제공하고 데모·구독·이용 인원을 관리하는 서비스 운영 플랫폼이다. 개발 인원은 7명이며 AI를 적극 활용한다. 역할 분담은 프로젝트 계획서를 따른다(기능별로 화면부터 SQL까지 맡는 방식, 팀 합의).

**무료 체험 신청 정보 입력 → 신청 즉시 업체 코드·관리자 사번·계정 생성 및 14일 기간 시작 → 이메일 인증 → 체험 이용 → 데모 업체 관리자의 테스트 결제 → 기존 계정·데이터를 유지한 정식 구독 전환**

신청 정보는 업체명·이용 인원·이메일·관리자 이름·비밀번호다. 인증 완료 전에는 그룹웨어 이용을 차단하지만 14일 기간은 신청일부터 진행한다. 업체명은 입력값을 유지하며 문의는 체험 생성의 사전 승인 절차가 아닌 별도 기능이다.

| 구분 | 제공 내용 | 상태 |
|---|---|---|
| 상품 홈페이지 | 서비스·기능·구독 안내, 무료 체험 신청과 비회원 문의를 제공한다. 일반 회원 로그인·회원가입과 결제 메뉴는 제공하지 않는다. 체험 신청은 즉시 업체·관리자 생성으로 연결한다. | 확인 |
| PWA 그룹웨어 | 설치형 웹앱(PWA)으로 중앙 서버에 접속한다. Windows·macOS의 Chrome에서 설치·독립 창 실행과 핵심 업무를 확인한다. Chrome 확장 프로그램과 별도 네이티브 설치 파일·C++ 개발은 요구하지 않는다. | 확인 |
| 운영자 메뉴 | 그룹웨어 안에서 문의·업체·계정·데모·구독·증설·장애 대응을 관리한다. | 확인 |
| 업체 업무 메뉴 | 업체별 계정·조직·권한과 그룹웨어 업무 기능을 제공한다. | 확인 |

하나의 애플리케이션·DB에서 업체 코드로 소속과 자료를 구분한다. 주요 시연은 한 업체로 진행하고, 두 번째 업체의 최소 데이터로 업체 간 접근 제한을 확인하는 기존 계획을 유지한다.

## 2. 사용자와 권한

| 사용자 | 권한과 역할 |
|---|---|
| 홈페이지 방문자 | 무료 체험 신청과 이메일 인증, 서비스·가격 안내·문의 등록. 문의 접수 내용과 답변은 입력한 이메일에서 확인 |
| 이음 운영자 | 개발자라는 가정으로 서비스와 업체 계정을 운영한다. 이음 운영 업체(`ieum0000`) 소속 계정에 운영자 역할을 두며(3.12), 운영 전용 메뉴와 업체 기본 메뉴를 모두 제공받는다. 장애는 로그로 우선 파악하고, 업체 내부 자료는 지원 요청에 따른 허가 후 접근한다. |
| 업체 관리자 | 업체당 관리자 계정 1개. 무료 체험 신청 시 생성된다. 데모의 정식 전환 결제는 해당 관리자만 수행한다. 직원·조직·권한·구독·증설을 관리하며 업체의 퇴사·비활성화 처리 책임을 유지한다. |
| 업체 직원 | 업체·계정에 부여된 권한 안에서 업무 기능 사용. 데모 중에는 관리자가 부서·사용자로 지정한 대상만 사용하며 관리자 포함 최대 10명으로 제한 |
| 구독 관리 권한자 | 정식 구독 이용 중 부여받은 조회·결제·증설 권한을 사용한다. 추가 인원 결제와 기간 연장은 해당 권한자도 수행한다. 데모 최초 정식 전환과 데모·유료 만료 상태의 결제는 업체 관리자만 가능하다. |
| 부서장·결재자·IT·인사 담당자 | 업무별 권한에 맞춰 결재·IT 처리·근태·연차 등을 사용한다. 다른 업체 자료 접근은 허용하지 않는다. |

- 직원 계정 생성은 같은 업체의 업체 관리자 또는 부서장이 승인한다. 업체 관리자는 업체 내 모든 요청, 부서장은 본인 부서 요청만 처리한다. 인사 담당자라는 이유만으로 별도 승인 권한을 부여하지 않는다. 가입 요청자의 본인 확인은 권한 있는 승인자가 그 요청을 승인하고, 직원이 이메일을 인증하는 것으로 한다. (제안) 이메일 인증은 승인을 요청하기 전에 한다(ACC-04). 승인자는 인증된 이메일로 온 요청만 보게 된다.
- 부서장은 별도 역할이 아니라 부서 설정에서 지정한 사람이다. 부서장에게는 가입 승인 메뉴만 추가로 보이고, 그 밖의 메뉴는 본인 역할을 따른다.
- 운영자 메뉴 노출과 업체 내부 자료 접근 허가는 구분한다. 직원의 장애 문의를 확인한 운영자가 필요한 자료·조회/수정 범위를 요청하고 업체 관리자가 승인한다. 승인은 최대 24시간이며 지원 종료·허가 취소 시 즉시 차단한다.
- 개인 지도·개인 채팅 등 보호 자료는 업체 관리자 승인만으로 공개하지 않는다. 소유자·당사자의 추가 허가가 필요하며 기존 자료별 권한을 유지한다.
- 데모·유료 만료 후 계정 삭제 전까지 기존 활성 사용자는 전원 로그인해 권한 있는 자료를 조회·다운로드할 수 있다. 퇴사·비활성·미인증 계정 제한은 유지한다. 쓰기는 업체 관리자 결제만 예외로 허용하며 장애 문의 등록도 차단한다.

## 3. 기능 요구사항

### 3.1 상품 홈페이지·계정 발급

| ID | 기능 | 요구사항 | 상태 |
|---|---|---|---|
| WEB-01 | 소개·가격 안내 | 서비스·기능과 월간·연간 구독을 안내한다. 기본 단가는 1인 월 4,000원이다. 월간은 무할인, 최초 연간은 10%, 연간 만료 후 3개월 이내의 연간 연장은 총 20% 할인이다. 할인율은 누적하지 않는다. 설치비·도입비는 없고 부가세는 계산하지 않는다. | 확인 |
| WEB-02 | 비회원 문의 | 사용자가 이메일 정보를 포함해 문의하면 DB에 저장하고, 접수 완료 안내와 문의 내용을 메일 본문에 담아 사용자 이메일로 보낸다(첨부 파일 아님). 동시에 운영자가 확인할 수 있도록 문의를 전달·등록한다. 문의 접수만으로 체험 발급 승인을 기다리지 않는다. 같은 이메일 주소의 접수 횟수는 제한하지 않는다(업체가 담당자 한 사람의 메일로 문의를 모아 받을 수 있으므로). 접수 메일 발송이 실패해도 문의는 저장하고 운영자 화면에 등록한다. (제안) 운영자에게는 따로 메일을 보내지 않고, 운영자 화면(비회원 접수)에 등록하며 새 접수 수를 배지로 알린다. | 확인·일부 제안 |
| WEB-03 | 이메일 답변 | 운영자는 그룹웨어 문의관리에서 조회·답변한다. 답변은 사용자 이메일로 발송하고 DB에도 저장한다. 사용자는 이메일에서 확인하며 문의번호·비밀번호 조회 기능은 제거한다. | 확인 |
| ACC-01 | 무료 체험 즉시 생성 | 업체명·이용 인원(관리자 포함 10명 이하)·이메일·관리자 이름·비밀번호를 입력받아 업체와 관리자 계정 1개를 신청 즉시 생성한다. 운영자 검토·수동 발급·이메일 인증 완료를 생성 조건으로 두지 않는다. (제안) 신청 완료 화면과 인증 메일에 업체 코드와 관리자 사번을 보여 준다(모르면 로그인할 수 없으므로). 로그인한 뒤에는 업체 관리자 화면에서도 업체 코드를 볼 수 있다. (v1.8 제안) 같은 화면에서 직원에게 알려 줄 가입 키도 본다(ACC-08). 이미 업체를 만든 적이 있는 이메일(만료·삭제된 업체 포함)로는 새 체험을 신청할 수 없고, 인증 메일 다시 보내기나 결제(삭제된 업체는 OPS-08 재구매)를 안내한다. | 확인·일부 제안 |
| ACC-02 | 신청일 기준 체험 | 무료 체험 신청 즉시 14일 기간을 시작한다. 이메일 인증은 이용 허용 조건이며 인증 지연·첫 로그인·비밀번호 변경으로 기간을 다시 시작하지 않는다. | 확인 |
| ACC-03 | 자동 발급·사번 로그인 | 업체명은 입력값을 유지하고 업체 코드는 `ieum` 뒤에 0001~9999에서 무작위로 뽑은 4자리를 중복 없이 붙인다(`ieum0000`은 이음 운영 업체, 3.11). 관리자·직원 모두 발급 연도 4자리+업체별 일련번호 4자리로 사번을 자동 발급한다. 각 업체의 번호는 `0001`부터 증가하며 업체 코드+사번으로 로그인한다. 직원 사번은 가입을 승인할 때 아직 쓰지 않은 다음 번호로 붙고, 한 번 쓴 번호는 다시 쓰지 않는다. | 확인 |
| ACC-04 | 직원 계정 신청 | 관리자가 직원을 미리 등록하는 사전 등록은 두지 않는다. 직원은 그룹웨어 로그인 화면의 "계정 만들기"에서 업체 관리자에게 받은 가입 키(ACC-08)를 입력하고 이름·부서·직급·이메일을 적어 승인을 요청한다(상태 "승인 대기"). 직급은 목록에서 고른다(3.9의 직급별 경력과 같은 목록). ~~업체 코드 칸 오른쪽의 "승인 요청" 버튼은 업체 코드를 넣기 전에는 회색으로 비활성화되고, 넣으면 파란색으로 활성화된다.~~ 요청하면 "승인 요청을 하였습니다"를 표시하고 입력칸을 잠그며, 승인 전에는 요청을 취소할 수 있다. 맞지 않는 가입 키, 이용 기간이 끝난 업체, 이메일 인증 전 업체, 같은 이메일로 승인 대기 중이거나 계정이 있는 경우는 각각 사유를 알려 거절한다. (제안) 화면은 이 순서로 채운다. ① 가입 키를 넣고 [확인]을 누르면 서버가 그 키의 업체를 확인하고(맞지 않는 가입 키·이용 기간이 끝난 업체·이메일 인증 전 업체는 여기서 사유를 알려 거절) 그 업체의 부서 목록을 불러온다. 틀린 키의 횟수 제한은 ACC-08을 따른다. ② 이름을 적고 부서·직급을 목록에서 고른다. ③ 이메일을 적고 [인증 코드 받기]로 받은 코드를 맞힌다. 같은 이메일로 승인 대기 중이거나 계정이 있으면 코드를 보내기 전에 거절한다. 인증 코드는 6자리 숫자이고 10분 동안 쓸 수 있으며, 5번 틀리면 그 코드는 무효가 되어 새 코드를 받아야 한다. 코드 다시 받기는 1분에 한 번·하루 5번까지다. ④ 이메일 인증을 마쳐야 맨 아래 [승인 요청] 버튼이 켜진다. 요청한 지 1시간이 지난 요청은 승인 대기로 세지 않는다. 상태 확인·요청 취소·계정 생성은 요청할 때 받은 무작위 키로만 열 수 있다(요청 번호나 이메일만 알아서는 남의 요청을 볼 수 없게). 키를 잃으면(다른 PC 등) 승인 대기 요청은 요청 뒤 1시간, 계정 생성 전은 승인 뒤 1시간이 지나면 끝나므로 그 뒤 다시 요청한다(ACC-05). | 확인·일부 제안 |
| ACC-05 | 계정 생성 승인 | 같은 업체의 업체 관리자 또는 해당 부서 부서장이 요청 시점부터 1시간 이내 승인해야 계정을 사용할 수 있다. 업체 관리자는 업체 내 모든 요청을 처리하며 부서장은 본인 부서 요청만 처리한다. 1시간 초과 시 요청을 만료하고 다시 요청받으며, 반려하면 "반려"로 끝나 직원이 다시 요청한다. 승인하면 다음 사번이 순서대로 자동 배정되고(상태 "계정 생성 전"), 업체 관리자는 승인할 때 역할(IT·인사 담당)을 정할 수 있다. 부서장이 승인하면 역할 없는 일반 직원이다. 직원 화면에는 "승인 완료되었습니다"와 함께 잠긴 사번 칸, 비밀번호·비밀번호 확인~~·이메일 인증~~ 칸이 나타나고 버튼이 "계정 생성"으로 바뀐다. 비밀번호(8자 이상)~~와 이메일 인증~~을 정하고 계정 생성을 누르면 "사용 중"이 되고, 자리 대기로 승인된 요청은 "자리 대기"가 된다(3.6). 임시 비밀번호와 첫 로그인 비밀번호 변경은 두지 않는다. ~~승인 후 계정 생성에 1시간 제한을 두는 의미가 아니다.~~ (제안) 승인 요청은 그 부서의 부서장과 업체 관리자에게 함께 알린다(가입 승인 메뉴 배지). 부서장이 정해지지 않은 부서의 요청은 업체 관리자만 승인할 수 있다. 승인 화면에는 요청자의 이름·부서·직급과 함께 인증된 이메일을 보여 준다(본인인지는 승인자가 판단하므로). 이메일은 승인 요청 전에 인증했으므로(ACC-04) 계정을 만들 때는 비밀번호만 정한다. 승인 뒤 1시간 안에 계정을 만들어야 하며, 지나면 그 승인은 끝나 자리를 돌려주고(배정했던 사번은 다시 쓰지 않음) 직원은 다시 요청한다. 예: 10:00 요청 → 10:40 승인 → 11:40까지 계정 생성. 업체 관리자는 계정 생성 전 계정을 취소할 수 있다(CFG-02). (v1.8 제안) 계정을 만들면 완료 화면에 로그인할 때 쓸 업체 코드와 사번을 보여 준다(가입 키로는 로그인할 수 없으므로). | 확인·일부 제안 |
| ACC-06 | 이메일 인증 | 계정·기간 생성 후 신청 이메일로 인증을 진행하고 완료 전에는 그룹웨어 이용을 차단한다. 인증 메일은 일회용 링크이며, 다시 보내면 이전 링크는 무효가 된다. 인증 전 로그인 시도는 "이메일을 아직 인증하지 않았습니다" 안내와 함께 거절한다. 기존 IP 횟수 제한·추가 허용 정책은 제거한다. 인증 지연으로 만료를 늦추지 않으며 직원 승인·활성 인원 제한은 별도로 유지한다. (제안) 인증 링크는 24시간 동안 쓸 수 있다. 다시 보내기는 1분에 한 번·하루 5번까지이며, 신청 완료 화면과 인증 전 로그인 거절 화면(비밀번호가 맞았을 때)에서 할 수 있다. 링크를 열면 바로 인증하지 않고 "인증하기" 버튼이 있는 화면을 보여 주며, 버튼을 눌러야 인증된다(메일 보안 검사가 링크를 먼저 열어도 인증이 쓰여 버리지 않게). | 확인·일부 제안 |
| ACC-07 | 비밀번호 찾기·변경 | 비밀번호를 잊으면 로그인 화면의 "비밀번호 찾기"에서 업체 코드·사번을 넣고, 계정에 등록된 이메일로 받은 인증 코드(ACC-04와 같은 규칙)를 맞힌 뒤 본인이 새 비밀번호(8자 이상)를 정한다. 임시 비밀번호를 만들거나 관리자가 초기화하지 않는다. 계정이 있는지 드러나지 않도록 업체 코드·사번이 틀려도 같은 안내("등록된 이메일로 코드를 보냈습니다")를 보이며, 코드는 사용 중 계정에만 보낸다. 로그인한 사용자는 현재 비밀번호를 확인한 뒤 바꿀 수 있다. 둘 다 계정 보안이라 만료 중에도 허용한다(3.11). | 제안 |
| ACC-08 | 가입 키 | 직원 계정 만들기(ACC-04)는 업체 코드가 아니라 업체마다 따로 있는 가입 키로 업체를 찾는다. 가입 키는 가입에만 쓰고, 로그인과 비밀번호 찾기는 지금처럼 업체 코드 + 사번으로 한다. 화면의 칸 이름은 "업체 코드"와 "가입 키"로 분명히 나눈다. [확인]에서 같은 접속(IP)의 틀린 가입 키가 10분 안에 5번이 되면 그 IP의 [확인]을 10분 동안 거절하고 남은 시간을 보여 준다. 맞는 키는 세지 않으며, 횟수는 서버에서 센다. 가입 키는 관리자 화면에 계속 보여 줘야 하므로 해시가 아닌 원문으로 저장하고 업체끼리 겹치지 않게 한다(키가 새어도 할 수 있는 것은 승인 요청뿐이고, 계정은 승인자가 승인해야 생긴다). (제안) 가입 키는 4자씩 3묶음 12자리(예: `7KQF-3MXR-9TWD`)이고, 헷갈리는 글자 O·I·L·U는 쓰지 않는다. 입력은 하이픈·공백·대소문자를 무시하고 O는 0으로, I·L은 1로 바꿔 읽는다. 체험 신청으로 업체가 생길 때 함께 만들고(이음 운영 업체 `ieum0000`에는 없음), 업체 관리자 화면에서 보기·[키 복사]·[재발급]을 한다. 재발급하면 옛 키는 바로 쓸 수 없고, 이미 보낸 요청(승인 대기·계정 생성 전)은 그대로 둔다. 같은 사무실(같은 IP)에서 한 사람이 계속 틀리면 다른 직원도 10분 동안 막히므로, 입력 정리와 [키 복사]로 틀릴 일을 줄인다. | 확인·일부 제안 |

| SUB-05 | 월간→연간 전환 | 월간 이용 중 연간을 구매하면 기존 월간 만료일부터 연간 기간을 시작한다. 최초 연간 구매에는 10% 할인을 적용하고 이후 연간 연장은 할인 유지 기간 규칙을 따른다. 남은 월간 기간의 환불·차액 정산은 하지 않는다. | 확인 |
| SUB-06 | 결제 안내 메일 | 체험·유료 구독이 끝나기 7일·3일·1일 전과 마지막 날에 업체 관리자 이메일로 남은 기간과 결제 방법을 보낸다(서버가 매일 정해진 시각에 확인). 같은 날짜의 안내는 한 번만 보내고, 그사이 결제해 만료일이 바뀌면 이전 만료일 기준 안내는 보내지 않는다. 이메일 인증 전 업체에는 보내지 않는다. 우선순위는 팀 회의에서 정하며 안은 2순위다. | 제안 |
| SUB-07 | 연장·전환 때 인원 변경 | 연장(SUB-03)과 월간→연간 전환(SUB-05) 화면은 지금 구매 인원(증설 포함)을 기본값으로 보여 주며 인원을 바꿀 수 있다. 늘린 인원은 새 기간(기존 만료일 다음)부터 적용한다. 지금 바로 늘리려면 증설(CAP-01)을 쓴다. 줄일 때는 결제 시점의 사용 중 계정 수(계정 생성 전 포함) 이상으로만 고를 수 있고, 결제한 때부터 새로 활성화·승인할 수 있는 한도도 줄인 인원 기준이 된다(남은 기간 환불·차액 정산 없음). 인원 변경에는 운영자 승인이 필요 없다(새 기간을 사는 것이라 재구매와 같게 본다). 금액은 바뀐 인원으로 3.5에 따라 계산하고, 승인 한도(× 1.2)도 바뀐 인원으로 다시 센다. 예: 10명·12/31 만료 업체가 15명으로 연장하면 1/1부터 15명이다. 20명 구매·사용 중 12명 업체는 12명 이상으로만 연장할 수 있고, 15명으로 결제하면 그때부터 16번째 활성화는 막힌다. | 제안 |
| CAP-01 | 인원 증설 신청 | 정식 구독 이용 중 업체 관리자/증설 권한자 신청 → 운영자 승인·반려 → 승인된 추가 인원 결제 → 결제 승인 후 한도 증가 순서다. 양측에 현황을 표시하며 반려·결제 실패 시 한도를 늘리지 않는다. 만료 중 증설 신청 등 쓰기는 차단한다. (제안) 운영자 승인만으로는 한도가 늘지 않으므로, 승인만 받고 결제하지 않은 채 늘어난 인원을 쓸 수는 없다(4장 인원 증설). 승인 뒤 7일 안에 결제하지 않은 증설 건은 끝나며(한도는 그대로) 필요하면 다시 신청한다. 결제 금액의 남은 기간은 결제하는 날을 기준으로 센다(CAP-02). 순서를 '결제 → 운영자 승인'으로 바꾸면 운영자가 반려할 때 받은 돈을 돌려줘야 하므로(결제 취소는 범위 밖) 지금 순서를 유지한다. | 확인·일부 제안 |
| CAP-02 | 증설 요금 | 할인 없이 1인 월 4,000원으로 기존 만료일까지 남은 기간을 결제한다. 온전한 개월은 월 단가로, 나머지는 해당 구독 월의 실제 일수로 일할 계산하고 최종 총액의 원 미만은 버린다. 이후 연간 연장에는 증설 인원을 포함해 할인한다. | 확인 |
| CFG-01 | 업체 기초 설정 | 업체명·조직도·부서장·직원·권한을 설정한다. 직원 사번은 업체별로 자동 발급한다. 정식 구매 인원은 관리자 포함 사용 중 계정 한도이며 퇴사·비활성 계정과 승인 전 요청은 세지 않고, 승인했지만 아직 계정을 만들지 않은 직원은 자리를 차지한다. 가입 승인은 구매 인원 × 1.2(올림)까지 할 수 있고, 구매 인원을 넘겨 승인한 계정은 자리 대기가 된다(3.6). 정식 증설은 승인·결제와 연결하고 데모 인원은 10명 이하에서 자유롭게 수정한다. (제안) 승인 뒤 1시간이 지나 끝난 승인은 자리를 차지하지 않는다(ACC-05). | 확인·일부 제안 |
| CFG-02 | 계정 상태 관리 | 업체는 퇴사·비활성화 대상을 확인하고 처리해야 한다. 업체 관리자(또는 인사 담당)가 사원 관리에서 직원을 비활성화하면 그 직원은 로그인할 수 없고 기록은 남으며, 자리가 있을 때만 다시 사용으로 되돌릴 수 있다. 업체 관리자 계정과 본인 계정은 비활성화할 수 없다. 사용 중 계정 수가 구매 한도를 넘는 활성화·재활성화는 차단하고, 자리가 나면 업체 관리자가 자리 대기 계정 중에서 골라 활성화한다. 퇴사·비활성 계정의 수는 사용 한도에 영향을 주지 않는다. 업체의 미처리로 발생한 이용 문제의 관리 책임은 업체에 있다. (제안) 업체 관리자는 계정 생성 전 계정(승인했지만 직원이 아직 계정을 만들지 않은 계정)을 취소할 수 있다. 취소하면 반려로 끝나 자리를 돌려주며, 배정했던 사번은 다시 쓰지 않는다. 비활성화와 계정 생성 전 취소는 사용 중 계정을 줄이는 일이므로 만료 중에도 업체 관리자에게 허용한다(3.11). | 확인·일부 제안 |

(제안) 재발급하면 서버가 운영자가 확인한 관리자 이메일로 비밀번호 설정 링크를 보낸다(인증 링크와 같은 규칙: 일회용·24시간·다시 보내기 1분에 한 번·하루 5번). 관리자가 링크에서 비밀번호를 정하면 이메일 인증도 마친 것으로 본다. 재발급 관리자의 사번은 그 업체의 다음 번호이며, 메일에 업체 코드와 사번을 적는다. 재발급된 관리자는 만료 상태로 로그인해 결제할 수 있다. | 확인·일부 제안 |

첨부된 시뮬레이터 설명은 현재 브라우저 저장 기반 시안의 현황이다. 최종 근태는 앞서 합의한 서버 저장·중복 검증을 목표로 하며 현재 시안과의 차이를 3.10절에 구분했다. 소스·서버·DB를 실행해 검증한 결과는 아니다.

범위 구분: **반차·연차 자동 부여는 필수**, **초과근무·지도와 업무 자료 자동 연결·채팅 초대/강퇴/수정/삭제는 추가**, **네이티브 설치 파일 배포·C++ 개발·급여·회의실 예약·채팅 읽음/타이핑은 제외**다. Windows·macOS는 웹 방식의 지원 대상으로 확인한다.

지도 자동 승인 합의: 최초 열람은 직접 승인한다. 소유자가 묶음별 자동 승인을 켜면 기존 허가자에게 이후 추가 마커를 자동 공유한다. 끄면 이후 추가분부터 다시 승인하며 언제든 사람별 허가를 해제할 수 있다.

### 3.5 구독 가격 정책

아래는 이음 프로젝트의 합의된 요금이며 타사 가격을 의미하지 않는다. 부가세는 별도 계산하지 않는다.

| 구분 | 계산·혜택 | 1인 기준 | 상태 |
|---|---|---|---|
| 월간 | 인원 × 4,000원, 할인 없음 | 월 4,000원 | 확인 |
| 최초 연간 | 인원 × 4,000원 × 12개월 × 0.9 | 연 43,200원 | 확인 |
| 연간 연장·할인 유지 기간 내 재구매 | 인원 × 4,000원 × 12개월 × 0.8, 총 20% 할인 | 연 38,400원 | 확인 |
| 연간 만료 후 3개월 초과 재구매 | 인원 × 4,000원 × 12개월 × 0.9, 연간 기본 10% 할인 | 연 43,200원 | 확인 |
| 구독 중 인원 증설 | 할인 없이 월 4,000원으로 잔여 기간 계산. 부분 월은 실제 일수로 일할 계산하고 최종 총액 원 미만 버림 | 6개월 남으면 1인 24,000원 | 확인 |
| 설치비·도입비 | 청구하지 않으며 구현 범위에서 제외 | 없음 | 확인 |

최초 연간 구매는 10%, 이후 연간 연장은 총 20% 할인하며 횟수에 따라 할인율을 늘리지 않는다. 연간 구독 만료 후에도 달력 기준 3개월까지 20% 할인 자격을 유지한다. 직전 연간 만료 시각에 3개월을 더한 시각까지 결제 승인이 완료되면 유지 기간 안으로 판단한다. 3개월을 초과하면 연간 기본 10%를 적용하고, 그다음 연간 연장부터 다시 20%를 적용한다.

월간에서 처음 연간으로 전환할 때는 10% 할인한다. 증설 결제에는 할인을 적용하지 않으며 이후 연간 연장에는 증설 인원을 포함한 전체 구매 인원에 해당 할인율을 적용한다. 실패·중복 결제 요청은 새로운 구매 이력으로 집계하지 않는다.

구매·데모 인원에는 관리자 1명도 포함한다. 예: 10인 구매 시 관리자 1명 + 직원 9명. 연간 구독이 정확히 6개월 남았을 때 2명을 증설하면 2명 × 4,000원 × 6개월 = **48,000원**을 결제하며 기존 구독 만료일은 유지한다. 기존 인원이 10명이었다면 다음 연간 연장은 12명 × 4,000원 × 12개월 × 0.8 = **460,800원**이다.

증설의 부분 월 계산 예: 해당 구독 월이 30일이고 15일이 남았다면 2명 × 4,000원 × 15/30 = **4,000원**이다. 온전한 개월분과 부분 월분을 합산한 최종 결제 총액에서 원 미만을 버린다.

### 3.6 이용 기간·활성 계정 정책

| 항목 | 확정 규칙 |
|---|---|
| 구독 기준일 | 월간은 1개월, 연간은 1년을 달력 기준으로 계산한다. 대응 날짜가 없으면 해당 월 말일로 조정하며, 연장 계산에서는 최초 기준일을 유지한다. |
| 월말·윤년 예시 | 1월 31일 월간 시작 → 2월 말일 만료 → 계속 연장 시 3월 31일 만료. 2월 29일 연간 시작 → 다음 해 2월 28일 만료. |
| 전환·재시작 | 월간 이용 중 연간 구매는 월간 만료일부터 시작한다. 만료 후 재구매는 새 결제 승인 시점부터 기간을 다시 계산한다. |
| 활성 계정 한도 | 구매 10인이면 관리자 포함 사용 중 계정 10개까지만 사용한다. 퇴사·비활성 계정이 50개 있어도 활성 한도를 차지하지 않는다. 승인되지 않은 요청도 세지 않으며, 자리는 가입을 승인할 때 센다(승인했지만 아직 계정을 만들지 않은 직원 포함). (제안) 승인 뒤 1시간이 지나 끝난 승인은 세지 않는다(ACC-05). |
| 승인 한도와 자리 대기 | 유료 업체는 가입 승인을 구매 인원 × 1.2(소수점 올림, 10명이면 12명)까지 할 수 있다. 잘못 승인된 계정 때문에 다른 직원의 승인이 막히지 않게 둔 여유분이다. 구매 인원을 넘겨 승인한 계정은 "자리 대기"가 되어 로그인할 수 없고, 사용 중 계정은 언제나 구매 인원 안이다. 자리가 나면 업체 관리자가 가입 승인 화면에서 대기 계정을 골라 활성화한다. 승인 한도까지 차면 더 승인할 수 없다. 데모는 여유분 없이 관리자 포함 10명까지만 승인·사용한다. |
| 데모 인원 한도 | 신청·변경 인원 모두 관리자 포함 10명 이하이며 체험 중에는 한도 안에서 자유롭게 수정한다. 정식 전환 이후에는 구매 인원과 증설 결제 규칙을 적용한다. |
| 연장 때 인원 변경 (제안) | 연장·월간→연간 전환 때 인원을 늘리면 새 기간부터, 줄이면 결제한 때부터 한도에 적용한다. 줄일 때는 사용 중 계정 수보다 적게 고를 수 없다(SUB-07). |
| 계정 교체 | 활성 직원을 퇴사·비활성 처리하면 그만큼 다른 계정을 활성화할 수 있다. 이 처리만으로 구매 한도·금액이 줄거나 환불되지는 않는다. |
| 업체의 계정 관리 책임 | 업체는 퇴사·비활성화 대상과 계정 상태를 꼼꼼히 확인하고 처리해야 한다. 미처리로 발생한 이용 한도 부족·접근 유지 등 이용 문제의 관리 책임은 업체에 있다. |

### 3.7 승인·지원·보관 정책

| 항목 | 확정 규칙 |
|---|---|
| 관리자 생성과 직원 가입 구분 | 관리자 계정·14일 기간은 신청 즉시 생성하고 이메일 인증 후 이용을 허용한다. 직원은 계정 만들기로 승인을 요청하고, 1시간 안에 승인되면 자동 배정된 사번으로 비밀번호~~와 이메일 인증~~을 마쳐 계정을 만든다. (제안) 이메일 인증은 승인 요청 전에 하고, 계정은 승인 뒤 1시간 안에 비밀번호를 정해 만든다(ACC-04·05). |
| 직원 승인 유효기간 | 요청 시각부터 1시간 안에 승인해야 한다. 초과한 요청은 승인할 수 없으며 다시 요청해야 한다. 가입 키를 아는 것만으로 가입할 수 없고, 사번은 직원이 고르지 않고 승인 때 서버가 정한다. (제안) 승인 뒤에도 1시간 안에 계정을 만들어야 한다. |
| 승인자 범위 | 업체 관리자는 같은 업체 모든 요청, 부서장은 같은 업체의 본인 부서 요청만 승인한다. 부서장은 부서 설정에서 지정한 사람이고 별도 역할이 아니다. 승인하더라도 유료/데모 사용 인원 한도를 초과해 사용할 수 없다(초과 승인은 자리 대기, 3.6). |
| 문의 구분·확인 | 홈페이지 문의는 접수 내용·답변을 사용자 이메일로 전달하고 운영자는 그룹웨어 문의관리에서 처리한다. 업체 내부 IT 티켓과 운영자 장애 지원 문의는 구분한다. 이번 이메일 문의 변경을 내부 IT 티켓 댓글 전체에 적용하는 것은 아니다. |
| 지원 자료 접근 | 운영자 권한 요청 → 업체 관리자 범위 확인·승인 → 최대 24시간 지원 → 종료/취소 시 차단. 개인 지도·개인 채팅 등은 소유자·당사자 추가 허가가 필요하다. |
| 만료 후 업무 데이터 | 데모·유료 만료 후 달력 기준 3개월까지 유지한다. 만료 시각에 3개월을 더한 시각을 초과하면 업무 자료·사용자 계정·첨부파일과 관련 지원 이력을 삭제한다. 삭제 전에 유료 이용을 재개한 업체는 과거 만료를 이유로 삭제하지 않는다. |
| 유지할 업체 운영 기록 | 업체 식별 정보와 결제·구독 이력을 유지해 재구매 시 업체를 식별한다. 삭제된 자료는 복구하지 않는다. 운영자가 기존 업체 식별 정보를 기준으로 관리자 계정을 재발급한 뒤 재구매를 진행한다. |
| 오류 ZIP과 지원 이력 | 오류 ZIP은 2주, 장애 문의·접근 승인·지원 작업 이력은 업체 업무 데이터 삭제 시점까지 보관한다. 두 종류의 보관 기준을 혼용하지 않는다. |

### 3.8 개발·배포 기준

설치형 웹앱(PWA)으로 제공한다. 브라우저 설치 기능을 통해 앱 아이콘·독립 실행 창을 제공하며 기존 Chrome 확장 프로그램 제작·배포 요구는 제거한다. 별도 Windows/macOS 네이티브 설치 파일과 C++ 개발은 제외한다. PWA 설치 구성·갱신 방식·웹 주소는 팀이 설계한다.

기존 Spring Framework·JSP·MyBatis·Oracle와 실제 이메일 발송을 유지한다. 이메일(체험 인증, 문의 접수·답변, 결제 안내. v1.6 제안으로 직원 인증 코드·비밀번호 찾기 코드·재발급 관리자 비밀번호 설정을 더함)은 서버가 Spring JavaMailSender와 SMTP(팀 공용 Gmail 계정, 앱 비밀번호)로 보낸다. 발송 전에 기록을 남기고 트랜잭션 밖에서 보낸 뒤 결과(완료·실패와 사유)를 기록하며, 계정 정보는 저장소에 올리지 않는 설정 파일에 둔다. Windows·macOS의 Chrome에서 PWA 설치·독립 실행·로그인·결제·채팅·시뮬레이터 연동을 검증한다. 설치 가능하다는 이유만으로 오프라인 업무·모든 OS 호환을 구현한 것으로 간주하지 않는다. 읽기 전용과 자료별 권한은 PWA 화면뿐 아니라 서버에서도 검사한다.

PWA 설치 안내: 상품 홈페이지의 다운로드 버튼이 브라우저의 설치 창을 띄우지 못하면(이미 설치됨, 설치를 지원하지 않는 브라우저) 브라우저별 설치 방법을 안내한다. 설치한 앱 창 안에서 상품 소개·체험 신청·도입 문의 페이지가 열리면 로그인 화면으로 보낸다.

### 3.9 연차·반차 계산 규칙

연차는 이번 프로젝트에서 합의한 계산 규칙을 사용한다. 현재 업체 근속에 이전 직장 경력을 합산하며, 이전 경력은 직원 등록 시 직급별 시연용 임의 데이터로 설정·저장한다. 실제 직원의 경력을 직급만으로 판정하는 기능은 아니다.

| 항목 | 규칙 |
|---|---|
| 계산식 | 연차 = 15일 + 내림(총 완료 경력 연수 ÷ 3). 총 경력은 이전 경력 + 현재 업체 입사일부터의 근속이다. |
| 계산 예 | 총 경력 3년 미만 15일, 3년 이상 6년 미만 16일, 6년 이상 9년 미만 17일 |
| 최초 부여 | 직원 등록 시 현재 총 경력을 기준으로 부여한다. 이전 경력과 입사일을 직원 데이터에 저장한다. |
| 새 주기 | 매년 현재 업체 입사기념일에 총 경력으로 새 연차를 부여한다. 이전 주기 미사용 연차는 이월하지 않으며 사용 이력은 남긴다. |
| 중복 부여 방지 | 같은 직원·같은 연차 주기에 자동 부여가 중복되지 않도록 한다. |
| 반차 | 오전·오후를 구분하고 최종 승인 시 0.5일을 차감한다. 같은 날짜의 종일 연차·반차와 동일 시간대 반차는 중복 승인하지 않는다. |

직급별 이전 경력의 시연용 예시: 사원 0년, 주임 2년, 대리 4년, 과장 7년, 차장 10년, 부장 13년. 사용자 요청에 따라 작성한 임의 데이터이며 팀 시연 데이터에서 조정할 수 있다. 직원의 이후 직급 변경 때 저장된 이전 경력을 임의로 바꾸지는 않는다.

### 3.10 지문 시뮬레이터 현황과 최종 연동 목표

첨부 이미지에서 확인한 내용과 기존 합의된 목표를 구분한다. 이미지의 설명은 구현 참고 자료이며 이 문서 작성 중 실행 검증한 내용은 아니다.

| 구분 | 첨부 이미지의 현재 시안 | 최종 그룹웨어 연동 기준 |
|---|---|---|
| 기록 저장 | 브라우저 저장소의 `ieum-demo-punches`에 날짜·단말기 사용자 번호별 저장. 브라우저별로 분리되고 초기화로 삭제 가능 | 업체·직원에 연결된 서버/DB 근태 기록으로 저장. 브라우저 초기화가 서버 기록을 지우지 않음 |

서로 다른 탭·PWA 창·시뮬레이터의 저장소 범위와 데이터 전달은 실제 구성에 맞춰 검증한다. 브라우저 저장소를 서버 저장의 증거로 사용하지 않는다. 만료 업체의 시뮬레이터 이벤트도 서버에서 거절해 읽기 전용 제한을 우회하지 못하게 한다.

### 3.11 자동 식별자·이용 상태별 권한

| 항목 | 확정 규칙 |
|---|---|
| 업체명·업체 코드 | 업체명은 신청 입력값을 유지한다. 업체 코드는 `ieum` + 숫자 4자리이며, 0001~9999에서 무작위로 뽑는다(고객이 가입 순서·고객 수를 알 수 없고, 남의 업체 코드를 짐작하기 어렵게). `ieum0000`은 이음 운영 업체(운영자 소속)다. 업체 코드에 고유 제약을 두고, 저장할 때 겹치면 다시 뽑아 최대 10번까지 저장한다. 먼저 있는지 조회한 뒤 저장하는 방식은 동시 신청에서 겹칠 수 있어 쓰지 않는다. 10번 모두 겹치면 새 신청을 받을 수 없다고 안내한다. 삭제된 업체의 코드도 다시 쓰지 않는다(업체 식별 정보를 유지하므로). 내부 번호(`company_id`)는 순서대로 붙고, 운영자 화면은 신청일·내부 번호로 정렬한다. 시연 데이터의 업체는 정해 둔 코드로 넣는다. |
| 가입 키 | 업체마다 하나이며 직원 계정 만들기에만 쓴다. 실패 제한·형식·재발급·저장 방식은 ACC-08을 따른다. |
| 관리자·직원 사번 | 발급 연도 4자리+업체별 일련번호 4자리다. 각 업체는 `0001`부터 발급하며 관리자·직원 번호 중복을 막는다. |
| 발급 예 | `ieum4827`의 관리자 `20260001`, 다음 직원 `20260002`. 다른 업체 `ieum0315`도 자체 번호 `20260001`부터 쓴다. 업체 코드+사번으로 식별한다. |
| 신청 직후·인증 전 | 업체·관리자 계정·체험 시작/만료 정보를 생성하되 그룹웨어 이용을 차단한다. 인증 후에도 신청일부터 14일 기준을 유지한다. |
| 데모 이용 중 | 관리자 포함 10명 이하에서 인원·대상 수정 가능. 정식 전환 결제는 업체 관리자만 가능하다. |
| 정식 이용 중 | 구매 한도와 부여받은 권한 안에서 업무를 사용한다. 관리자·해당 권한자는 추가 인원 결제·기간 연장이 가능하다. |
| 데모·유료 만료 | 계정 삭제 전까지 기존 활성자의 로그인·자료별 조회·다운로드·기존 대화 열람을 허용한다. 팝업을 표시하고 관리자 결제 외 쓰기는 차단한다. |
| 만료 중 차단 예 | 작성·수정·삭제·업로드·채팅 전송·근태 저장·가입 승인·증설 신청·장애 문의 등록·지원 접근 승인·업체 자료 변경. API 우회 요청도 거절한다. |
| 만료 중 허용하는 쓰기 (제안) | 업체 관리자 결제 외에 본인 비밀번호 변경·찾기(업무 자료가 아니라 계정 보안), 로그아웃, 업체 관리자의 직원 비활성화·계정 생성 전 취소(사용 중 계정을 줄이는 쪽이라 안전하고, 더 적은 인원으로 재구매하려면 필요)는 허용한다. 2장·DEM-03·SUB-04·4장의 "관리자 결제 외 쓰기 차단"은 이 예외를 포함한 뜻이다. |

읽기 전용은 사용자 업무 요청의 제한이며 결제·보관·삭제·로그 수집 같은 서비스 운영 작업의 중단을 뜻하지 않는다. 기존 만료 후 3개월 초과 계정 삭제와 퇴사·비활성·자료별 접근 제한은 유지한다.

### 3.12 계정 상태·역할·주소 규칙 (팀 저장소 기준)

2026-10-28 프론트 공통 틀을 팀 저장소 `feature/authTest`에 맞추며 확인한 값이다(v1.5). v1.6에서 팀장 결정(운영자, 이용 결제 모듈)을 반영하고 빈 곳을 채웠으며, 팀 확인 전인 것은 "(제안)"으로 표시했다.

| 항목 | 확정 규칙 |
|---|---|
| 직원 계정 상태 | 승인 대기(`REQUESTED`, 요청 시각 보관) → 반려(`REJECTED`) 또는 계정 생성 전(`APPROVED`, 사번 배정) → 사용 중(`ACTIVE`) / 자리 대기(`WAITING`) → 비활성(`RETIRED`, 퇴사 등). 요청 만료는 저장하지 않고 요청 시각으로 판단한다. 저장소 DB에는 사용 중과 비활성만 있으므로 승인 대기·반려·계정 생성 전·자리 대기 값을 추가한다. 로그인은 사용 중 계정만 된다. (제안) 업체 관리자가 계정 생성 전 계정을 취소하면 반려(`REJECTED`)로 끝난다(CFG-02). 승인 뒤 1시간 안에 계정을 만들지 않은 계정 생성 전(`APPROVED`)은 끝난 것으로 보고 자리를 세지 않는다. 요청 만료처럼 값을 저장하지 않고 승인 시각으로 판단한다. |
| 역할 | 저장소 DB 값 직원·IT 담당·인사 담당·업체 관리자(`ROLE_EMP`, `ROLE_IT`, `ROLE_HR`, `ROLE_ADMIN`), 한 계정에 하나. 이음 운영자는 이음 운영 업체(`ieum0000`) 소속 계정에 운영자 역할(`ROLE_OPS`)을 둔다. 운영자 역할은 `ieum0000` 소속에만 줄 수 있고, 이음 운영 업체와 운영자 계정은 체험 신청이 아니라 초기 데이터로 만든다. 부서장과 결재자는 역할이 아니라 설정·상황으로 정한다. (제안) 업체가 역할 관리에서 줄 수 있는 역할은 직원·IT 담당·인사 담당뿐이다(업체 관리자는 업체당 1명, 운영자는 `ieum0000` 소속만). |
| 메뉴와 역할 | 직원 기본 메뉴에 IT 담당은 티켓 처리·자산 관리, 인사 담당은 사원 관리·근태·연차 관리·휴일 관리, 업체 관리자는 티켓 처리·사원 관리·가입 승인·부서 관리·역할 관리·이용 결제, 부서장은 가입 승인이 더 보인다. 운영자는 이음 운영 업체의 직원 기본 메뉴와 운영 전용 메뉴(업체 관리, 업체 계정, 신청 현황, 비회원 접수, 회원 접수, 운영 데이터)를 함께 쓴다(2장·OPS-02). 모든 직원의 기본 메뉴에는 이음 장애 문의가 있고, 업체 관리자에게는 지원 허가 승인이, 구독 권한을 받은 사람에게는 이용 결제(받은 권한만)가 더 보인다(OPS-04·SUB-01). (제안) 업체 관리자에게는 자산 관리·근태·연차 관리·휴일 관리·지점 관리도 보인다. 관리자 혼자이거나 IT·인사 담당을 아직 정하지 않은 업체도 이 기능을 쓸 수 있어야 하기 때문이다. |
| 화면 주소 | 업무 화면 `/<모듈>/<기능>`, 관리 화면 `/<모듈>/admin/<기능>`(관리 역할만), 운영자 `/ops/...`(운영자 역할만). 로그인 없이 여는 주소는 상품 소개(`/`), 체험 신청(`/trial`), 도입 문의(`/inquiry`), 로그인(`/login`), 직원 계정 만들기(`/join`: 승인 요청·상태 확인·계정 생성), 앱 설치 파일. 이용 결제 화면은 `subscription` 모듈에 둔다. (제안) `/`는 그 주소만 열고, 나머지 공개 주소는 하위 주소(인증 링크·다시 보내기·계정 생성 처리·비밀번호 찾기 등)까지 연다. 가입 승인(업체 관리자·그 부서 부서장)과 이용 결제(업체 관리자·구독 권한을 받은 사람)는 역할만으로 정해지지 않으므로 관리 화면 주소 밖(각 모듈의 업무 화면 주소)에 두고, 서버가 요청마다 그 사람이 맞는지 확인한다. |
| 로그인 | 업체 코드 + 사번 + 비밀번호. 같은 사번이 다른 업체에 있을 수 있으므로 업체 코드와 함께 사원을 찾는다. 비밀번호는 BCrypt로 저장한다. 로그인이 끊긴 화면 요청은 로그인 화면으로, AJAX 요청은 401로 응답해 화면이 다시 로그인하게 한다. (제안) 이메일 인증 전·자리 대기 같은 상태 안내는 비밀번호가 맞을 때만 보여 주고, 틀리면 같은 오류 문구를 보인다(남의 계정 상태가 드러나지 않게). (v1.8 제안) 같은 접속(IP)에서 같은 업체 코드+사번의 비밀번호가 10분 안에 5번 틀리면 그 IP에서 그 계정의 로그인을 10분 거절하고, 같은 IP에서 계정과 관계없이 10분 안에 20번 틀리면 그 IP의 로그인을 10분 거절한다. 막히면 남은 시간을 보여 준다. 맞는 로그인은 세지 않고, 없는 계정도 같은 방식으로 세어 계정이 있는지 드러나지 않게 한다. 계정 자체는 잠그지 않는다(업체 코드·사번만 알면 남이 일부러 틀려 동료 계정을 잠글 수 있으므로). 업체 코드가 무작위여도 직원은 모두 알고 있고 사번은 업체 안에서 순서대로라, 막지 않으면 비밀번호만 맞히면 된다. |
| 운영자 심사 없음 | 체험 신청 즉시 업체·관리자 계정이 생기므로 운영자 화면에 계정 발급 기능은 없다. 운영자는 신청 현황에서 이메일 인증 상태(대기·완료)만 본다. |
| 업체 이용 상태 (제안) | 체험 중·유료·체험 만료·유료 만료 네 가지로 나눈다(만료 안내 문구가 체험과 유료에서 다르므로). 이메일 인증 전인지는 이메일 인증 일시가 비어 있는지로 보고, 만료 3개월이 지나 업무 자료를 지운 업체에는 자료 삭제 표시를 남긴다(OPS-08 재발급 대상). 이용 상태는 결제·만료로 로그인 중에도 바뀌므로 세션에 담아 두지 않고 요청마다 DB에서 확인한다. 값을 저장할지 만료일로 계산할지와 코드 이름은 DB 리드가 정한다. |
| 요청 방식 (제안) | 데이터를 바꾸는 요청은 모두 POST로 보내고, GET 요청으로는 아무것도 바꾸지 않는다(인증 링크도 링크를 열면 확인 화면만 보이고 버튼이 POST로 인증한다). 만료 읽기 전용 검사는 GET이 아닌 요청을 쓰기로 보고 결제와 3.11의 예외만 통과시킨다. |


## 4. 처리 규칙과 확인 기준

| 구분 | 확인할 동작 |
|---|---|
| 업체 분리 | 다른 업체 코드·자료 ID로 결재·근태·티켓·지도·파일을 조회·변경하거나 채팅에 연결할 수 없다. 같은 업체에서도 사용자별 권한을 검사한다. 서버는 업체를 로그인한 사용자 정보에서만 정하고 주소·입력값의 업체 값을 믿지 않는다. |
| 체험 신청·자동 발급 | 동시·중복 신청에서도 업체 코드와 같은 업체의 관리자/직원 사번이 중복되지 않도록 한다. 다른 업체의 동일 사번은 허용한다. 업체별 `0001` 시작과 번호 형식을 확인하며 범위 밖 임의 발급은 하지 않는다. 업체 코드는 `ieum` + 무작위 4자리이고, 뽑은 번호가 이미 있으면 다시 뽑는다. 10번 모두 겹치면 신청을 받을 수 없다고 안내한다(번호 뽑는 부분을 바꿔 끼워 '계속 겹침'을 시험한다). (제안) 이미 업체를 만든 이메일의 새 신청은 거절한다. |
| 이메일 인증·직원 승인 | 신청 즉시 계정·기간이 생성되고 인증 전 이용은 거절된다. 인증 후에도 기간은 연장되지 않는다. IP 횟수 차단은 제거한다. 직원의 1시간 승인·부서장 범위·활성 인원 제한은 유지한다. (제안) 인증 링크는 24시간이 지나거나 다시 보낸 뒤에는 쓸 수 없고, 링크를 열기만 해서는 인증되지 않는다. 다시 보내기는 1분 안의 두 번째 요청과 하루 여섯 번째 요청을 거절한다. 직원 인증 코드는 10분이 지나거나 5번 틀리면 쓸 수 없다. (v1.7 제안) 직원은 이메일 인증을 마쳐야 승인을 요청할 수 있다. 승인 뒤 1시간이 지나면 계정을 만들 수 없고 그 자리는 다시 빈자리로 센다. |
| 문의 이메일 | 접수 시 사용자에게 본인 문의 내용이 전달되고 운영자 문의관리에 등록되는지 확인한다. 운영자가 답변하면 사용자 이메일로 답변을 발송한다. 홈페이지 문의번호·비밀번호 조회는 제공하지 않는다. |
| 데모 시작 | 신청일에 시작·만료 정보를 생성한다. 이메일 인증 완료가 다음 날이어도 신청일부터 계산한 만료일은 유지한다. 첫 로그인·인원 변경·인증 지연으로 14일을 다시 시작하지 않는다. |
| 데모 인원 | 신청과 변경 모두 관리자 포함 10명 이하로 제한하며 10명 이하 수정에 결제를 요구하지 않는다. 대상 교체 후 제외된 사용자의 접근을 차단한다. |
| 가입 요청·승인 | 맞지 않는 가입 키, 만료 업체, 인증 전 업체, 같은 이메일로 승인 대기 중이거나 계정이 있는 요청은 사유별로 거절한다. 승인하면 쓰지 않은 다음 사번이 순서대로 붙고, 동시에 승인해도 사번이 겹치지 않는다. ~~계정 생성은 승인된 요청에서 비밀번호 8자 이상과 이메일 인증 코드가 맞아야 된다.~~ 요청 뒤 1시간이 지나면 승인할 수 없고 다시 요청해야 한다. 부서장은 자기 부서 요청만, 업체 관리자는 전체를 승인한다. 승인 전·만료·자리 대기 계정의 로그인은 상태에 맞는 안내로 거절한다. 같은 IP에서 틀린 가입 키를 10분 안에 5번 넣으면 그 IP의 [확인]은 10분 동안 거절되고 남은 시간이 보인다. 맞는 키는 횟수에 들어가지 않는다. 가입 키로는 로그인되지 않는다. (제안) 상태 안내는 비밀번호가 맞을 때만 보인다. 상태 확인·취소·계정 생성은 요청 때 받은 키 없이 열리지 않는다. 승인 화면에 요청자 이메일이 보인다. 업체 관리자가 계정 생성 전 계정을 취소하면 자리가 돌아오고 그 사번은 다시 쓰지 않는다. (v1.7 제안) 이메일을 인증하지 않으면 [승인 요청]이 되지 않는다. 계정 생성은 승인 뒤 1시간 안에 비밀번호 8자 이상이면 되고, 1시간이 지나면 거절된다. 부서장이 없는 부서의 요청은 업체 관리자만 승인할 수 있다. (v1.8 제안) 가입 키를 재발급하면 옛 키의 [확인]은 거절되고 이미 보낸 요청은 남는다. 입력한 키의 하이픈·공백·대소문자와 O·I·L은 정리해 읽는다. 계정 생성 완료 화면에 업체 코드와 사번이 보인다. |
| 승인 한도·자리 대기 | 유료 10인 업체는 12번째 승인까지 되고 13번째는 거절한다. 11·12번째 승인 계정은 자리 대기로 로그인할 수 없다. 사용 중 1명을 비활성화하면 관리자가 자리 대기 중 1명을 활성화할 수 있고, 자리가 없으면 활성화를 거절한다. 데모는 11번째 승인부터 거절한다. |
| 문의 이메일 횟수 | 같은 이메일로 여러 건을 접수해도 모두 저장·등록된다. 접수 메일 발송이 실패해도 문의는 남는다. |
| 만료 후 읽기 전용 | 데모·유료 모두 기존 활성 사용자 전원 로그인·자료별 조회·다운로드·기존 대화 열람과 만료 팝업을 확인한다. 관리자 결제 외 쓰기를 화면·API·채팅·시뮬레이터에서 거절하고 장애 문의 등록도 차단한다. (제안) 3.11의 예외(본인 비밀번호 변경·찾기, 관리자의 비활성화·계정 생성 전 취소)는 만료 중에도 된다. |
| 구독 기간 | 최초 구매·만료 후 결제는 승인 시점부터, 만료 전 연장은 기존 만료 시점부터 계산한다. 월간→연간은 기존 월간 만료일부터 시작한다. 월말·윤년 조정 후에도 최초 기준일을 유지한다. 중복 기간 추가·데모 잔여 합산은 하지 않는다. |
| 결제·구독 | 결제 성공 화면만으로 구독을 활성화하지 않는다. 서버가 주문·업체·인원·월간/연간·할인·승인 금액을 검증하며 중복 요청에도 구독 반영은 한 번만 수행한다. 자동 갱신·자동 청구는 하지 않는다. |
| 할인 계산 | 1인 월간 4,000원·최초 연간 43,200원·할인 유지 기간 내 연간 연장 38,400원인지 확인한다. 만료 후 3개월 경계까지는 20%, 경계 초과는 10%이며 그다음 연간 연장은 다시 20%인지 확인한다. 할인율은 누적하지 않는다. |
| 인원 증설 | 운영자 승인만으로는 인원 한도를 늘리지 않는다. 승인된 인원·요금과 결제 결과를 확인하고 같은 증설 건의 중복 승인 요청에도 한도를 한 번만 증가시킨다. 증설 결제에 연간 할인을 적용하지 않으며 이후 연간 연장에는 증설 인원을 포함한다. (제안) 승인 뒤 7일 안에 결제하지 않은 증설 건은 결제할 수 없고 한도도 그대로다. |
| 증설 기간·요금 | 월간·연간 모두 기존 만료일까지 산정하고 기존 만료일을 유지한다. 6개월 잔여·2명 증설은 48,000원, 30일 구독 월 중 15일 잔여·2명 증설은 4,000원인지 확인한다. 최종 총액 원 미만 버림을 검증한다. |
| 활성 계정 집계 | 구매 10인·활성 10개·퇴사/비활성 50개 상태에서 기존 활성자는 이용 가능하고 11번째 활성화는 거절한다. 1개를 비활성화한 뒤 다른 1개를 활성화하면 허용하며 동시 활성화로 한도를 넘지 않아야 한다. |
| 전환 오류 | 외부 결제 승인과 내부 구독 저장 실패를 구분한다. 승인 후 저장 실패 시 운영자가 결제 결과를 확인해 기존 승인 건을 재반영하며 재결제·중복 구독 반영은 하지 않는다. |
| 데이터 보관·삭제 | 데모 중 결제 시 자료를 유지한다. 만료 후 3개월 초과 업체의 업무 자료·계정·첨부파일·지원 이력은 삭제하고 업체 식별·결제·구독 기록은 유지한다. 미만료 업체와 이미 이용을 재개한 업체는 삭제하지 않는다. (v1.8 제안) 삭제 뒤 업체 식별 정보에 남는 사람 정보는 신청 이메일뿐이고, 결제 이력에서는 결제한 사람의 이름·사번이 보인다. |
| 운영자 접근 | 미승인 자료·수정 권한 밖 작업을 거절한다. 승인 후 24시간 초과, 지원 종료, 허가 취소 시 차단하며 승인·작업 이력을 확인한다. 보호 자료는 당사자 추가 허가 없이는 접근할 수 없다. |
| 구독 관리 권한 | 데모 정식 전환은 관리자만, 정식 이용 중 추가 결제·연장은 해당 권한자도 허용한다. 데모·유료 만료 중에는 위임 결제 권한자의 요청도 거절하고 관리자 결제만 허용한다. |
| 오류 로그 | 오류가 있는 날만 자정 이후 전날 ZIP을 생성하고 오류가 없던 날은 생략한다. 2주 보관 정책에 따라 ZIP을 제거하되 지원 이력을 함께 지우지 않는다. 보관 탭은 운영자만 접근한다. |
| 근태 기록 | 시뮬레이터 체크를 서버 수신 시각으로 저장한다. 같은 날 출근·퇴근 각각 1건만 허용하고 중복·출근 없는 퇴근을 거절한다. 실제 지문 장비 연동으로 표시하지 않는다. |
| 연차·반차 | 이전 경력과 현재 근속을 합산해 3년 경계의 15→16일 등을 확인한다. 입사기념일 새 주기 부여·이월 없음·중복 부여 방지를 확인하고 반차 0.5일 차감·동일 시간대 중복을 검증한다. |
| PWA 지원·현황 구분 | Windows·macOS Chrome에서 설치·독립 실행·핵심 흐름을 확인한다. 시뮬레이터 브라우저 저장 시안과 서버/DB 결과를 구분하고 서버 연동이나 OS 호환 검증 없이 완료로 표시하지 않는다. |
| 지도·채팅 | 지도 요청 목록은 소유자·제목만 보이고 허가 전 주소·설명은 보이지 않는다. 채팅 10MB 제한·방 참여 권한·저장 대화 재접속을 확인하며 읽음·타이핑 기능은 요구하지 않는다. |
| 재구매 | 삭제된 업체는 기존 업체 식별·결제 기록으로 확인하고 관리자 재발급 후 재구매한다. 삭제된 자료가 복구되지 않으며 할인은 기존 확정 정책으로 계산한다. (제안) 재발급 관리자는 메일의 비밀번호 설정 링크로 비밀번호를 정한 뒤 로그인한다. 정식 전환·재구매 인원은 사용 중 계정 수보다 적게 고를 수 없다. |
| 지점 | 사용 중지한 지점은 새로 고르는 목록에서 빠지고 기존 기록에는 남는다. 자산을 다른 지점으로 옮겨도 이미 접수한 티켓의 지점은 그대로다. |
| 비밀번호 찾기 (제안) | 업체 코드·사번이 맞든 틀리든 같은 안내가 보이고, 코드는 사용 중 계정의 등록 이메일로만 간다. 코드가 맞아야 새 비밀번호가 저장되고, 그 뒤 이전 비밀번호로는 로그인되지 않는다. 만료 중에도 된다. |
| 연장 인원 변경 (제안) | 10명 업체가 15명으로 연장하면 기존 만료일 다음 날부터 15명이다. 사용 중 12명인 20명 업체는 11명 이하로 연장할 수 없고, 15명으로 결제한 뒤에는 16번째 활성화가 거절된다. 인원 변경 연장에는 운영자 승인이 없다. |
| 결제 안내 메일 (제안) | 만료 7·3·1일 전과 마지막 날에 한 번씩만 가고, 결제해 만료일이 바뀌면 이전 만료일 기준 안내는 가지 않는다. 인증 전 업체에는 가지 않는다. |
| 요청 방식 (제안) | GET 요청으로 바뀌는 자료가 없다. 만료 업체의 GET이 아닌 요청은 결제와 3.11의 예외 말고는 모두 거절된다. |
| 로그인 실패 제한 (v1.8 제안) | 같은 IP에서 한 계정의 비밀번호를 10분 안에 5번 틀리면 그 IP에서 그 계정의 로그인이 10분 거절되고, 다른 IP에서는 그 계정으로 로그인된다. 같은 IP에서 여러 계정을 합쳐 20번 틀리면 그 IP의 로그인이 10분 거절된다. 없는 계정을 넣어도 같은 방식으로 막힌다. |

| 가입 키 세부 | 없음 | 4자씩 3묶음 12자리(O·I·L·U 제외), 입력 정리(하이픈·공백·대소문자 무시, O→0, I·L→1), 체험 신청 때 발급(`ieum0000`은 없음), 업체 관리자 화면에서 보기·[키 복사]·[재발급](옛 키는 바로 무효, 보낸 요청은 유지) | 제안 | ACC-01·08, 3.4, 4장 |
| 업체 코드 붙이는 방식 | 신청 순서대로 `ieum0001`부터, `ieum9999`까지 다 쓰면 안내 | 0001~9999에서 무작위. 고유 제약에 걸리면 다시 뽑아 최대 10번, 모두 겹치면 새 신청을 받을 수 없다고 안내. 삭제 업체의 코드는 다시 쓰지 않음. 내부 번호는 순서대로이고 운영자 화면은 신청일·내부 번호로 정렬. 시연 데이터 업체는 정해 둔 코드. 이유: 고객이 가입 순서·고객 수를 알 수 없고 남의 업체 코드를 짐작하기 어렵게(순서대로의 관리 편의는 내부 번호가 줌) | 팀장 결정 | ACC-03, 3.11, 4장 |
| 발급 예의 업체 코드 | `ieum0001`, `ieum0002` | `ieum4827`, `ieum0315`(무작위 예) | 문서 맞춤 | 3.11 |
| 계정 생성 완료 화면 | 없음 | 로그인할 때 쓸 업체 코드와 사번을 보여 줌(가입 키로는 로그인할 수 없으므로) | 제안 | ACC-05, 4장 |
| 로그인 실패 제한 | 없음 | 같은 IP·같은 계정이 10분 안에 5번 틀리면 그 IP에서 그 계정을 10분 거절, 같은 IP 전체가 10분 안에 20번 틀리면 그 IP를 10분 거절. 없는 계정도 같게 셈. 계정 자체는 잠그지 않음(남이 일부러 틀려 동료 계정을 잠그지 못하게) | 제안 | 3.12, 4장 |
| 계정 삭제 뒤 남기는 기록 | 업체 식별 정보·결제·구독 이력 유지(남기는 범위는 정하지 않음) | 사람 정보는 신청 이메일만 남기고 관리자 이름 등은 계정과 함께 지움. 결제 이력에 결제한 사람의 이름·사번을 결제 당시 값으로 남김 | 제안 | OPS-06, 4장 |

## 6. 팀의 설계·구현·검증 작업

회의 변경 사항과 후속 답변을 본문에 반영했다. 아래는 추가 정책 Q&A가 아닌 팀의 구현 설계 작업이다.

| 영역 | 작업 |
|---|---|
| PWA | 설치 구성·독립 실행·갱신, 중앙 웹 주소, Windows/macOS Chrome 호환과 만료 권한 검사 |
| 자동 발급 | 업체별 사번의 동시 발급·중복 방지, 업체 코드 무작위 뽑기(고유 제약, 다시 뽑기 최대 10번, 실패 안내. 뽑는 부분은 테스트에서 바꿔 끼울 수 있게 분리), 가입 키 발급·재발급, 신청·가입 승인 시 번호 연결(직원 사번은 승인 때 순차 배정, 재사용 없음). 업체별 일련번호와 발급 연도 처리 규격을 설계에 명시 |
| 이메일·문의 | 인증·접수 사본·답변 발송과 실패 재처리, 문의 DB 저장·운영자 관리. 사용자 이메일 전송 실패가 문의 자체를 유실시키지 않도록 설계. 직원 인증 코드·비밀번호 찾기·재발급 비밀번호 설정 메일, 결제 안내 메일 스케줄러, 다시 보내기 횟수 제한 |
| 업무·운영 | 증설 승인 뒤 7일 결제 기한, 연장·전환 때 인원 변경(SUB-07), 시뮬레이터 서버 연동, 토스 승인 재반영, 오류 ZIP·보관·만료 데이터 삭제(v1.8 제안: 삭제 뒤 남기는 업체 정보와 결제자 이름·사번, DB 리드), 연차·반차 경계 검증, 지점 목록과 근무·배치·수령·접수 지점 연결 |
| 공통 설정(담당 1) | 직접 만든 로그인 화면, 업체 코드+사번 조회, 로그인 없이 여는 주소(하위 주소 포함), 인사·IT 관리 화면 규칙(업체 관리자 포함), AJAX 401, 앱 설치 파일 경로, 화면 공통 값(업체명·부서·직급, 부서장 여부, 업체 이용 상태, 오늘 출퇴근), 배지 API, 계정 상태 값 추가, 쓰기 요청 POST 통일과 만료 읽기 전용 공통 검사(3.11 예외 포함). v1.8 제안: 로그인 실패 제한(IP·계정별 10분 5번, IP 전체 10분 20번) |
| 가입 승인·자리 | 승인 요청·상태 확인·요청 취소·이메일 인증 코드·계정 생성 API(로그인 없이, 요청 키로), 승인(역할 포함)·반려·만료 API, 승인 한도(× 1.2)와 자리 대기 전이, 자리 대기 활성화, 계정 생성 전 취소, 부서장 지정 값. 가입 키 확인(부서 목록) API와 틀린 키 횟수 제한(IP별 10분 5번). v1.7 제안: 승인 요청 전 이메일 인증, 승인 뒤 1시간 계정 생성 기한. v1.8 제안: 계정 생성 완료 화면의 업체 코드·사번 |

이번에 변경하지 않은 요금·연차·반차·로그 보관·구독 기간(직접 연장, 자동 갱신 없음)·증설·권한 위임은 기존 합의를 유지한다. PWA 기술 규격은 구현 설계에서 정하며(인증 링크 유효시간·재전송 횟수는 v1.6에서 ACC-06에 제안으로 정했다) 인증 지연으로 체험 기간을 늘리지 않는다. 월간·연간 선택과 토스 테스트 결제, 인원 증설, 구독 권한 위임은 프론트 시안에 아직 없다.
