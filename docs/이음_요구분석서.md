# 이음(IEUM) 요구분석서

작성일: 2026-10-29 · 짝 문서: [기능명세서](./이음_기능명세서.md)

> **두 문서의 구분**: 요구분석서는 사용자 입장에서, 기능명세서는 개발자 입장에서 적는다. 요구분석서는 누가 무엇을 왜 쓰는지, 업무 정책(가격·기간·인원 한도·권한·보관), 범위와 제약을 적는다. 기능명세서는 그 요구를 화면과 서버에서 어떻게 처리하는지 적는다. 화면 구성·입력 순서·안내 문구, 입력 검증(인증 코드·링크 유효 시간, 횟수 제한), 계정 상태 값·역할 값·화면 주소·요청 방식, 메일 발송 방식, 개발 환경, 상태 값·정기 작업, 지문 시뮬레이터 연동 기준, 확인 기준, 구현 설계 작업이 기능명세서에 있다. 두 문서는 같은 요구 ID(ACC-04 등)를 쓴다.

## 1. 목적과 전체 흐름

이음은 업체에 그룹웨어를 제공하고 데모·구독·이용 인원을 관리하는 서비스 운영 플랫폼이다. 개발 인원은 7명이며 AI를 적극 활용한다. 역할 분담은 프로젝트 계획서 9장을 따른다.

**무료 체험 신청 정보 입력 → 신청 즉시 업체 코드·관리자 사번·계정 생성 및 14일 기간 시작 → 이메일 인증 → 체험 이용 → 데모 업체 관리자의 테스트 결제 → 기존 계정·데이터를 유지한 정식 구독 전환**

신청 정보는 업체명·이용 인원·이메일·관리자 이름·비밀번호다. 인증 완료 전에는 그룹웨어 이용을 차단하지만 14일 기간은 신청일부터 진행한다. 업체명은 입력값을 유지하며 문의는 체험 생성의 사전 승인 절차가 아닌 별도 기능이다.

| 구분 | 제공 내용 |
|---|---|
| 상품 홈페이지 | 서비스·기능·구독 안내, 무료 체험 신청과 비회원 문의를 제공한다. 일반 회원 로그인·회원가입과 결제 메뉴는 제공하지 않는다. 체험 신청은 즉시 업체·관리자 생성으로 연결한다. |
| PWA 그룹웨어 | 설치형 웹앱(PWA)으로 중앙 서버에 접속한다. Windows·macOS의 Chrome에서 설치·독립 창 실행과 핵심 업무를 확인한다. Chrome 확장 프로그램과 별도 네이티브 설치 파일·C++ 개발은 요구하지 않는다. |
| 운영자 메뉴 | 그룹웨어 안에서 문의·업체·계정·데모·구독·증설·장애 대응을 관리한다. |
| 업체 업무 메뉴 | 업체별 계정·조직·권한과 그룹웨어 업무 기능을 제공한다. |

주요 시연은 한 업체로 진행하고, 두 번째 업체의 최소 데이터로 업체 간 접근 제한을 확인하는 기존 계획을 유지한다. 여러 업체가 한 서비스를 함께 쓰되, 업체마다 소속과 자료가 나뉘어 다른 업체의 자료는 볼 수 없다(구현 기준은 기능명세서 1.6).

## 2. 사용자와 권한

| 사용자 | 권한과 역할 |
|---|---|
| 홈페이지 방문자 | 무료 체험 신청과 이메일 인증, 서비스·가격 안내·문의 등록. 문의 접수 내용과 답변은 입력한 이메일에서 확인 |
| 이음 운영자 | 개발자라는 가정으로 서비스와 업체 계정을 운영한다. 이음 운영 업체(`ieum0000`) 소속 계정에 운영자 역할을 두며(기능명세서 1.1), 운영 전용 메뉴와 업체 기본 메뉴를 모두 제공받는다. 장애는 로그로 우선 파악하고, 업체 내부 자료는 지원 요청에 따른 허가 후 접근한다. |
| 업체 관리자 | 업체당 관리자 계정 1개. 무료 체험 신청 시 생성된다. 데모의 정식 전환 결제는 해당 관리자만 수행한다. 직원·조직·권한·구독·증설을 관리하며 업체의 퇴사·비활성화 처리 책임을 유지한다. |
| 업체 직원 | 업체·계정에 부여된 권한 안에서 업무 기능 사용. 데모 중에는 관리자가 부서·사용자로 지정한 대상만 사용하며 관리자 포함 최대 10명으로 제한 |
| 구독 관리 권한자 | 정식 구독 이용 중 부여받은 조회·결제·증설 권한을 사용한다. 추가 인원 결제와 기간 연장은 해당 권한자도 수행한다. 데모 최초 정식 전환과 데모·유료 만료 상태의 결제는 업체 관리자만 가능하다. |
| 부서장·결재자·IT·인사 담당자 | 업무별 권한에 맞춰 결재·IT 처리·근태·연차 등을 사용한다. 다른 업체 자료 접근은 허용하지 않는다. |

- 직원 계정 생성은 같은 업체의 업체 관리자 또는 부서장이 승인한다. 업체 관리자는 업체 내 모든 요청, 부서장은 본인 부서 요청만 처리한다. 인사 담당자라는 이유만으로 별도 승인 권한을 부여하지 않는다. 가입 요청자의 본인 확인은 권한 있는 승인자가 그 요청을 승인하고, 직원이 이메일을 인증하는 것으로 한다. 이메일 인증은 승인을 요청하기 전에 한다(ACC-04). 승인자는 인증된 이메일로 온 요청만 보게 된다.
- 부서장은 별도 역할이 아니라 부서 설정에서 지정한 사람이다. 부서장에게는 가입 승인 메뉴만 추가로 보이고, 그 밖의 메뉴는 본인 역할을 따른다.
- 운영자 메뉴 노출과 업체 내부 자료 접근 허가는 구분한다. 직원의 장애 문의를 확인한 운영자가 필요한 자료·조회/수정 범위를 요청하고 업체 관리자가 승인한다. 허가는 문제가 해결될 때까지 이어지고, 운영자가 지원을 종료하거나 업체 관리자가 허가를 취소하거나 문의가 해결됨으로 닫히면 즉시 차단한다.
- 개인 지도·개인 채팅 등 보호 자료는 업체 관리자 승인만으로 공개하지 않는다. 소유자·당사자의 추가 허가가 필요하며 기존 자료별 권한을 유지한다.
- 데모·유료 만료 후 업무 자료를 지우기 전까지(만료 뒤 3개월, 3.7) 기존 활성 사용자는 전원 로그인해 권한 있는 자료를 조회·다운로드할 수 있다. 퇴사·비활성·미인증 계정 제한은 유지한다. 쓰기는 업체 관리자 결제만 예외로 허용하며 장애 문의 등록도 차단한다.

## 3. 기능 요구사항

요구 ID마다 구현 명세(사용자·권한, 화면·주소, 입력, 처리, 결과·오류, 상태 값, 확인 기준)가 기능명세서 2장에 같은 ID로 있다. 3.4 업무 기능은 기능명세서 2.4가 통합 계획서와 연결한다. 계정 상태·역할·화면 주소·로그인·메일 발송·업체 코드 발급·로그인 실패 제한·상태 값·정기 작업 같은 공통 규칙은 기능명세서 1장에 있다.

위 표 밖의 기능으로, 프로젝트 구현을 모두 마친 뒤 또는 자기 파트를 다 끝낸 사람이 맡는다(10/29·10/30 회의). 자료실과 익명 게시판은 이 장에 요구 ID가 없고 아래 줄이 요구사항이다.

|---|---|

| ID | 기능 | 요구사항 |
|---|---|---|
| WEB-01 | 소개·가격 안내 | 서비스·기능과 월간·연간 구독을 안내한다. 기본 단가는 1인 월 4,000원이다. 월간은 무할인, 최초 연간은 10%, 연간 만료 후 3개월 이내의 연간 연장은 총 20% 할인이다. 할인율은 누적하지 않는다. 설치비·도입비는 없고 부가세는 계산하지 않는다. |
| WEB-02 | 비회원 문의 | 사용자가 이메일 정보를 포함해 문의하면 접수 완료 안내와 문의 내용을 메일 본문에 담아 사용자 이메일로 보낸다(첨부 파일 아님). 동시에 운영자가 확인할 수 있도록 문의를 전달·등록한다. 문의 접수만으로 체험 발급 승인을 기다리지 않는다. 같은 이메일 주소의 접수 횟수는 제한하지 않는다(업체가 담당자 한 사람의 메일로 문의를 모아 받을 수 있으므로). |
| WEB-03 | 이메일 답변 | 운영자는 그룹웨어 문의관리에서 조회·답변한다. 답변은 사용자 이메일로 발송한다. 사용자는 이메일에서 확인하며 문의번호·비밀번호 조회 기능은 제거한다. |
| ACC-01 | 무료 체험 즉시 생성 | 업체명·이용 인원(관리자 포함 10명 이하)·이메일·관리자 이름·비밀번호를 입력받아 업체와 관리자 계정 1개를 신청 즉시 생성한다. 운영자 검토·수동 발급·이메일 인증 완료를 생성 조건으로 두지 않는다. 이미 업체를 만든 적이 있는 이메일(만료·자료 삭제된 업체 포함)로는 새 체험을 신청할 수 없다. |
| ACC-02 | 신청일 기준 체험 | 무료 체험 신청 즉시 14일 기간을 시작한다. 이메일 인증은 이용 허용 조건이며 인증 지연·첫 로그인·비밀번호 변경으로 기간을 다시 시작하지 않는다. |
| ACC-03 | 자동 발급·사번 로그인 | 업체명은 입력값을 유지하고 업체 코드는 체험 신청 때 `ieum`+숫자 4자리를 무작위로 중복 없이 붙이고, 결제해도 바꾸지 않는다(`ieum0000`은 이음 운영 업체, 3.11). 관리자·직원 모두 발급 연도 4자리+업체별 일련번호 4자리로 사번을 자동 발급한다. 각 업체의 번호는 `0001`부터 증가하며 업체 코드+사번으로 로그인한다. 직원 사번은 가입을 승인할 때 아직 쓰지 않은 다음 번호로 붙고, 한 번 쓴 번호는 다시 쓰지 않는다. 같은 계정의 비밀번호를 연속 5번 틀리면 그 계정을 10분 동안 잠근다. 10분이 지나면 저절로 풀린다(기능명세서 1.5). |
| ACC-04 | 직원 계정 신청 | 관리자가 직원을 미리 등록하는 사전 등록은 두지 않는다. 업체 관리자(고른 부서)나 부서장(자기 부서)이 정한 시간 동안 가입을 열어 둔 부서로만 요청할 수 있고, 그 시간이 지나면 저절로 닫힌다. 직원은 그룹웨어 로그인 화면의 "계정 만들기"에서 업체 관리자에게 받은 업체 코드를 입력하고 이름·부서·직급·이메일을 적어 승인을 요청한다(상태 "승인 대기"). 승인 전에는 요청을 취소할 수 있다. 없는 업체 코드, 이용 기간이 끝난 업체, 이메일 인증 전 업체, 가입이 열려 있지 않은 부서, 같은 이메일로 승인 대기 중이거나 계정이 있는 경우는 각각 사유를 알려 거절한다. 이메일 인증은 승인을 요청하기 전에 한다. |
| ACC-05 | 계정 생성 승인 | 같은 업체의 업체 관리자 또는 해당 부서 부서장이 요청 시점부터 1시간 이내 승인해야 계정을 사용할 수 있다. 업체 관리자는 업체 내 모든 요청을 처리하며 부서장은 본인 부서 요청만 처리한다. 1시간 초과 시 요청을 만료하고 다시 요청받으며, 반려하면 "반려"로 끝나 직원이 다시 요청한다. 승인하면 다음 사번이 순서대로 자동 배정되고(상태 "계정 생성 전"), 업체 관리자는 승인할 때 역할(IT·인사 담당)을 정할 수 있다. 부서장이 승인하면 역할 없는 일반 직원이다. 비밀번호(8자 이상)를 정하고 계정 생성을 누르면 "사용 중"이 되고, 자리 대기로 승인된 요청은 "자리 대기"가 된다(3.6). 임시 비밀번호와 첫 로그인 비밀번호 변경은 두지 않는다. 부서장이 정해지지 않은 부서의 요청은 업체 관리자만 승인할 수 있다. 이메일은 승인 요청 전에 인증했으므로(ACC-04) 계정을 만들 때는 비밀번호만 정한다. 승인 뒤 1시간 안에 계정을 만들어야 하며, 지나면 그 승인은 끝나 자리를 돌려주고(배정했던 사번은 다시 쓰지 않음) 직원은 다시 요청한다. 예: 10:00 요청 → 10:40 승인 → 11:40까지 계정 생성. 업체 관리자는 계정 생성 전 계정을 취소할 수 있다(CFG-02). |
| ACC-06 | 이메일 인증 | 계정·기간 생성 후 신청 이메일로 인증을 진행하고 완료 전에는 그룹웨어 이용을 차단한다. 접속(IP) 기준의 횟수 제한은 두지 않는다. 인증 지연으로 만료를 늦추지 않으며 직원 승인·활성 인원 제한은 별도로 유지한다. |
| ACC-07 | 비밀번호 찾기·변경 | 비밀번호를 잊으면 계정에 등록된 이메일로 받은 인증 코드를 맞힌 뒤 본인이 새 비밀번호를 정한다. 임시 비밀번호를 만들거나 관리자가 초기화하지 않는다. 로그인한 사용자는 현재 비밀번호를 확인한 뒤 바꿀 수 있다. 둘 다 계정 보안이라 만료 중에도 허용한다(3.11). |

### 3.2 데모·결제·구독·증설

| ID | 기능 | 요구사항 |
|---|---|---|
| DEM-01 | 데모 인원 수정 | 체험 신청에서 10명 이하로 인원을 입력하고 데모 중에도 관리자 포함 10명 이내에서 인원과 대상을 자유롭게 수정한다. 데모 안에서는 증설 결제를 요구하지 않으며 인원 변경으로 만료일을 연장하지 않는다. |
| DEM-02 | 만료 안내 | 매일 최초 로그인 팝업에 남은 데모 일수를 표시한다. 업체 관리자는 즉시 구매 버튼, 일반 직원은 관리자 문의 안내를 표시한다. 위임받은 결제 권한은 별도 구독 메뉴에서 적용한다. |
| DEM-03 | 데모 만료·읽기 전용 | 만료 후 기존 활성 사용자는 전원 로그인해 권한 있는 자료 조회·다운로드·기존 대화 열람만 할 수 있다. 만료·읽기 전용 팝업을 표시하고 관리자 결제 외 모든 쓰기와 장애 문의 등록을 차단한다. 만료 뒤 3개월이 지나면 업무 자료를 지우고 계정을 비활성화하는 정책(3.7)을 따른다. |
| PAY-01 | 상태별 테스트 결제 | 데모의 정식 전환은 데모 관리자만, 정식 이용 중 추가 인원 결제·연장은 업체 관리자와 해당 권한자에게 허용한다. 데모·유료 만료 중 결제는 위임 권한과 관계없이 업체 관리자만 가능하다. 토스 테스트 환경으로 실제 대금 없이 진행한다. 정식 전환·만료 후 재구매에서 고르는 인원은 결제 시점의 사용 중 계정 수(계정 생성 전 포함) 이상이어야 한다. 더 적게 사려면 먼저 비활성화·계정 생성 전 취소로 줄인다(만료 중에도 허용, CFG-02). |
| PAY-02 | 유료 전환 | 기존 업체·관리자·직원 계정과 데이터를 유지하고 유료 구독으로 전환한다. 데모 중 구매해도 결제 승인일부터 유료 기간을 시작하며 남은 데모 기간은 더하지 않는다. 결제 실패 시 유료 권한을 부여하지 않는다. 결제 성공 화면만으로는 바뀌지 않고, 결제가 실제로 승인된 것이 확인되어야 유료 구독으로 바뀐다. |
| SUB-01 | 구독 현황 | 결제일·구독 시작일·만료일·구매 인원·이용 상태를 조회한다. 업체 관리자와 구독 조회 권한을 부여받은 부서 인원만 조회한다. 조회·결제·증설 권한은 각각 검사한다. |
| SUB-02 | 구독 통계 | 월별 결제 금액, 구매 인원 대비 활성 계정 수 그래프를 제공한다. 결제일·구독 시작일·만료일·요금제는 현황에 표시한다. |
| SUB-03 | 구독 기간·연장 | 최초 구매는 결제 승인일부터 시작한다. 만료 전 연장은 기존 만료일부터 기간을 추가하고 만료 후 결제는 승인일부터 다시 시작한다. 월간은 달력 기준 1개월, 연간은 1년이며 기준일이 없는 달은 말일로 조정한다. 자동 갱신·청구 없이 직접 연장한다. 할인 자격은 3.5절을 따른다. |
| SUB-04 | 유료 구독 만료 | 데모와 동일하게 기존 활성 사용자 전원 로그인·읽기 전용·만료 팝업을 적용한다. 조회·다운로드만 허용하고 관리자 결제 외 쓰기는 모두 차단한다. 위임받은 권한자도 만료 중에는 결제할 수 없다. |
| SUB-05 | 월간→연간 전환 | 월간 이용 중 연간을 구매하면 기존 월간 만료일부터 연간 기간을 시작한다. 최초 연간 구매에는 10% 할인을 적용하고 이후 연간 연장은 할인 유지 기간 규칙을 따른다. 남은 월간 기간의 환불·차액 정산은 하지 않는다. |
| SUB-06 | 결제 안내 메일 | 체험·유료 구독이 끝나기 7일·3일·1일 전과 마지막 날에 업체 관리자 이메일로 남은 기간과 결제 방법을 보낸다. |
| SUB-07 | 연장·전환 때 인원 변경 | 연장(SUB-03)과 월간→연간 전환(SUB-05) 화면은 지금 구매 인원(증설 포함)을 기본값으로 보여 주며 인원을 바꿀 수 있다. 늘린 인원은 새 기간(기존 만료일 다음)부터 적용한다. 지금 바로 늘리려면 증설(CAP-01)을 쓴다. 줄일 때는 결제 시점의 사용 중 계정 수(계정 생성 전 포함) 이상으로만 고를 수 있고, 결제한 때부터 새로 활성화·승인할 수 있는 한도도 줄인 인원 기준이 된다(남은 기간 환불·차액 정산 없음). 인원 변경에는 운영자 승인이 필요 없다(새 기간을 사는 것이라 재구매와 같게 본다). 금액은 바뀐 인원으로 3.5에 따라 계산하고, 승인 한도(× 1.2)도 바뀐 인원으로 다시 센다. 예: 10명·12/31 만료 업체가 15명으로 연장하면 1/1부터 15명이다. 20명 구매·사용 중 12명 업체는 12명 이상으로만 연장할 수 있고, 15명으로 결제하면 그때부터 16번째 활성화는 막힌다. |
| CAP-01 | 인원 증설 신청 | 정식 구독 이용 중 업체 관리자/증설 권한자의 추가 인원 결제 → 운영자 승인·반려 → 승인하면 한도 증가, 반려하면 그 결제를 취소해 환불(토스 테스트 환경) 순서다. 양측에 현황을 표시하며 결제 실패·반려 시 한도를 늘리지 않는다. 결제만으로는 한도가 늘지 않고 운영자가 승인해야 늘어난다(기능명세서 3장 '인원 증설'). 만료 중 증설 결제 등 쓰기는 차단한다. 결제 금액의 남은 기간은 결제하는 날을 기준으로 센다(CAP-02). |
| CAP-02 | 증설 요금 | 할인 없이 1인 월 4,000원으로 기존 만료일까지 남은 기간을 결제한다. 온전한 개월은 월 단가로, 나머지는 해당 구독 월의 실제 일수로 일할 계산하고 최종 총액의 원 미만은 버린다. 이후 연간 연장에는 증설 인원을 포함해 할인한다. |
| CFG-01 | 업체 기초 설정 | 업체명·조직도·부서장·직원·권한을 설정한다. 업체 관리자는 부서와 직급을 추가·이름 변경·순서 변경·삭제한다. 사람이 남아 있는 부서·직급은 지울 수 없고, 이름을 바꾸면 그 부서·직급 직원의 정보에도 바뀐 이름이 보인다. 직원 사번은 업체별로 자동 발급한다. 정식 구매 인원은 관리자 포함 사용 중 계정 한도이며 퇴사·비활성 계정과 승인 전 요청은 세지 않고, 승인했지만 아직 계정을 만들지 않은 직원은 자리를 차지한다. 가입 승인은 구매 인원 × 1.2(올림)까지 할 수 있고, 구매 인원을 넘겨 승인한 계정은 자리 대기가 된다(3.6). 정식 증설은 승인·결제와 연결하고 데모 인원은 10명 이하에서 자유롭게 수정한다. 승인 뒤 1시간이 지나 끝난 승인은 자리를 차지하지 않는다(ACC-05). |
| CFG-02 | 계정 상태 관리 | 업체는 퇴사·비활성화 대상을 확인하고 처리해야 한다. 업체 관리자(또는 인사 담당)가 사원 관리에서 직원을 비활성화하면 그 직원은 로그인할 수 없고 기록은 남으며, 자리가 있을 때만 다시 사용으로 되돌릴 수 있다. 업체 관리자 계정과 본인 계정은 비활성화할 수 없다. 사용 중 계정 수가 구매 한도를 넘는 활성화·재활성화는 차단하고, 자리가 나면 업체 관리자가 자리 대기 계정 중에서 골라 활성화한다. 퇴사·비활성 계정의 수는 사용 한도에 영향을 주지 않는다. 업체의 미처리로 발생한 이용 문제의 관리 책임은 업체에 있다. 업체 관리자는 계정 생성 전 계정(승인했지만 직원이 아직 계정을 만들지 않은 계정)을 취소할 수 있다. 취소하면 반려로 끝나 자리를 돌려주며, 배정했던 사번은 다시 쓰지 않는다. 비활성화와 계정 생성 전 취소는 사용 중 계정을 줄이는 일이므로 만료 중에도 업체 관리자에게 허용한다(3.11). |

### 3.5 구독 가격 정책

아래는 이음 프로젝트의 합의된 요금이며 타사 가격을 의미하지 않는다. 부가세는 별도 계산하지 않는다.

| 구분 | 계산·혜택 | 1인 기준 |
|---|---|---|
| 월간 | 인원 × 4,000원, 할인 없음 | 월 4,000원 |
| 최초 연간 | 인원 × 4,000원 × 12개월 × 0.9 | 연 43,200원 |
| 연간 연장·할인 유지 기간 내 재구매 | 인원 × 4,000원 × 12개월 × 0.8, 총 20% 할인 | 연 38,400원 |
| 연간 만료 후 3개월 초과 재구매 | 인원 × 4,000원 × 12개월 × 0.9, 연간 기본 10% 할인 | 연 43,200원 |
| 구독 중 인원 증설 | 할인 없이 월 4,000원으로 잔여 기간 계산. 부분 월은 실제 일수로 일할 계산하고 최종 총액 원 미만 버림 | 6개월 남으면 1인 24,000원 |
| 설치비·도입비 | 청구하지 않으며 구현 범위에서 제외 | 없음 |

최초 연간 구매는 10%, 이후 연간 연장은 총 20% 할인하며 횟수에 따라 할인율을 늘리지 않는다. 연간 구독 만료 후에도 달력 기준 3개월까지 20% 할인 자격을 유지한다. 직전 연간 만료 시각에 3개월을 더한 시각까지 결제 승인이 완료되면 유지 기간 안으로 판단한다. 3개월을 초과하면 연간 기본 10%를 적용하고, 그다음 연간 연장부터 다시 20%를 적용한다.

월간에서 처음 연간으로 전환할 때는 10% 할인한다. 증설 결제에는 할인을 적용하지 않으며 이후 연간 연장에는 증설 인원을 포함한 전체 구매 인원에 해당 할인율을 적용한다. 실패·중복 결제 요청은 새로운 구매 이력으로 집계하지 않는다.

구매·데모 인원에는 관리자 1명도 포함한다. 예: 10인 구매 시 관리자 1명 + 직원 9명. 연간 구독이 정확히 6개월 남았을 때 2명을 증설하면 2명 × 4,000원 × 6개월 = **48,000원**을 결제하며 기존 구독 만료일은 유지한다. 기존 인원이 10명이었다면 다음 연간 연장은 12명 × 4,000원 × 12개월 × 0.8 = **460,800원**이다.

증설의 부분 월 계산 예: 해당 구독 월이 30일이고 15일이 남았다면 2명 × 4,000원 × 15/30 = **4,000원**이다. 온전한 개월분과 부분 월분을 합산한 최종 결제 총액에서 원 미만을 버린다.

### 3.6 이용 기간·활성 계정 정책

| 항목 | 확정 규칙 |
|---|---|
| 구독 기준일 | 월간은 1개월, 연간은 1년을 달력 기준으로 계산한다. 대응 날짜가 없으면 해당 월 말일로 조정하며, 연장 계산에서는 최초 기준일을 유지한다. |
| 월말·윤년 예시 | 1월 31일 월간 시작 → 2월 말일 만료 → 계속 연장 시 3월 31일 만료. 2월 29일 연간 시작 → 다음 해 2월 28일 만료. |
| 전환·재시작 | 월간 이용 중 연간 구매는 월간 만료일부터 시작한다. 만료 후 재구매는 새 결제 승인 시점부터 기간을 다시 계산한다. |
| 활성 계정 한도 | 구매 10인이면 관리자 포함 사용 중 계정 10개까지만 사용한다. 퇴사·비활성 계정이 50개 있어도 활성 한도를 차지하지 않는다. 승인되지 않은 요청도 세지 않으며, 자리는 가입을 승인할 때 센다(승인했지만 아직 계정을 만들지 않은 직원 포함). 승인 뒤 1시간이 지나 끝난 승인은 세지 않는다(ACC-05). |
| 승인 한도와 자리 대기 | 유료 업체는 가입 승인을 구매 인원 × 1.2(소수점 올림, 10명이면 12명)까지 할 수 있다. 잘못 승인된 계정 때문에 다른 직원의 승인이 막히지 않게 둔 여유분이다. 구매 인원을 넘겨 승인한 계정은 "자리 대기"가 되어 로그인할 수 없고, 사용 중 계정은 언제나 구매 인원 안이다. 자리가 나면 업체 관리자가 가입 승인 화면에서 대기 계정을 골라 활성화한다. 승인 한도까지 차면 더 승인할 수 없다. 데모는 여유분 없이 관리자 포함 10명까지만 승인·사용한다. |
| 데모 인원 한도 | 신청·변경 인원 모두 관리자 포함 10명 이하이며 체험 중에는 한도 안에서 자유롭게 수정한다. 정식 전환 이후에는 구매 인원과 증설 결제 규칙을 적용한다. |
| 연장 때 인원 변경 | 연장·월간→연간 전환 때 인원을 늘리면 새 기간부터, 줄이면 결제한 때부터 한도에 적용한다. 줄일 때는 사용 중 계정 수보다 적게 고를 수 없다(SUB-07). |
| 계정 교체 | 활성 직원을 퇴사·비활성 처리하면 그만큼 다른 계정을 활성화할 수 있다. 이 처리만으로 구매 한도·금액이 줄거나 환불되지는 않는다. |
| 업체의 계정 관리 책임 | 업체는 퇴사·비활성화 대상과 계정 상태를 꼼꼼히 확인하고 처리해야 한다. 미처리로 발생한 이용 한도 부족·접근 유지 등 이용 문제의 관리 책임은 업체에 있다. |

### 3.7 승인·지원·보관 정책

| 항목 | 확정 규칙 |
|---|---|
| 관리자 생성과 직원 가입 구분 | 관리자 계정·14일 기간은 신청 즉시 생성하고 이메일 인증 후 이용을 허용한다. 직원은 계정 만들기로 승인을 요청하고, 1시간 안에 승인되면 자동 배정된 사번으로 비밀번호 설정을 마쳐 계정을 만든다. 이메일 인증은 승인 요청 전에 하고, 계정은 승인 뒤 1시간 안에 비밀번호를 정해 만든다(ACC-04·05). |
| 직원 승인 유효기간 | 요청 시각부터 1시간 안에 승인해야 한다. 초과한 요청은 승인할 수 없으며 다시 요청해야 한다. 업체 코드를 아는 것만으로 가입할 수 없고, 사번은 직원이 고르지 않고 승인 때 서버가 정한다. 승인 뒤에도 1시간 안에 계정을 만들어야 한다. |
| 승인자 범위 | 업체 관리자는 같은 업체 모든 요청, 부서장은 같은 업체의 본인 부서 요청만 승인한다. 부서장은 부서 설정에서 지정한 사람이고 별도 역할이 아니다. 승인하더라도 유료/데모 사용 인원 한도를 초과해 사용할 수 없다(초과 승인은 자리 대기, 3.6). |
| 문의 구분·확인 | 홈페이지 문의는 접수 내용·답변을 사용자 이메일로 전달하고 운영자는 그룹웨어 문의관리에서 처리한다. 업체 내부 IT 티켓과 운영자 장애 지원 문의는 구분한다. 이번 이메일 문의 변경을 내부 IT 티켓 댓글 전체에 적용하는 것은 아니다. |
| 지원 자료 접근 | 운영자 권한 요청 → 업체 관리자 범위 확인·승인 → 해결될 때까지 지원 → 지원 종료·허가 취소·문의 해결 시 차단. 개인 지도·개인 채팅 등은 소유자·당사자 추가 허가가 필요하다. |
| 만료 후 업무 데이터 | 데모·유료 만료 후 달력 기준 3개월까지 유지한다. 만료 시각에 3개월을 더한 시각을 초과하면 업무 자료(결재·게시판·채팅·일정·근태·자산·티켓·지도·알림)·첨부파일과 지원 이력을 삭제하고, 업체 관리자를 뺀 계정은 비활성으로 바꾼다. 계정은 지우지 않는다. 삭제 전에 유료 이용을 재개한 업체는 과거 만료를 이유로 삭제하지 않는다. |
| 유지할 업체 운영 기록 | 업체 정보·부서·직급·계정과 결제·구독 이력은 남긴다. 업체 관리자는 그대로 로그인해 재구매하고(OPS-08), 삭제된 자료는 복구하지 않는다. 비활성 직원이 다시 가입하려 하면 같은 이메일의 계정이 있어 거절되므로, 업체 관리자에게 다시 사용으로 돌려 달라고 요청한다. 실제 서비스라면 떠난 업체의 개인정보는 일정 기간 뒤 지우거나 가리지만, 이 프로젝트의 범위 밖이다. |
| 오류 ZIP과 지원 이력 | 오류 ZIP은 2주, 장애 문의·접근 승인·지원 작업 이력은 업체 업무 데이터 삭제 시점까지 보관한다. 두 종류의 보관 기준을 혼용하지 않는다. |

### 3.8 제공 방식·지원 환경

설치형 웹앱(PWA)으로 제공한다. 브라우저 설치 기능을 통해 앱 아이콘·독립 실행 창을 제공하며 기존 Chrome 확장 프로그램 제작·배포 요구는 제거한다. 별도 Windows/macOS 네이티브 설치 파일과 C++ 개발은 제외한다.

실제 이메일 발송을 유지한다. 이메일 발송 방식은 기능명세서 1.2에 있다. Windows·macOS의 Chrome에서 PWA 설치·독립 실행·로그인·결제·채팅·시뮬레이터 연동을 검증한다. 설치 가능하다는 이유만으로 오프라인 업무·모든 OS 호환을 구현한 것으로 간주하지 않는다. 개발 환경과 서버 검사 기준은 기능명세서 1.6에 있다. 읽기 전용과 자료별 권한은 화면 밖의 방법으로 접근해도 똑같이 적용된다.

PWA 설치 안내 화면의 동작은 기능명세서 1.3에 있다.

### 3.9 연차·반차 규칙

연차는 모든 직원이 기본 15일이다. 이전 직장 경력·근속 연수·직급으로 일수를 바꾸지 않고, 더 필요하면 업체 관리자나 인사 담당(업체 관리자가 역할을 준 사람, 기능명세서 1.1)이 더 부여한다.

| 항목 | 규칙 |
|---|---|
| 최초 부여 | 직원 등록 시 15일을 부여한다. 입사일을 직원 데이터에 저장한다. |
| 추가 부여 | 업체 관리자와 인사 담당이 같은 업체 직원에게 연차를 더 부여한다. |
| 새 주기 | 매년 현재 업체 입사기념일에 15일로 새 연차를 부여한다. 이전 주기 미사용 연차는 이월하지 않으며 사용 이력은 남긴다. |
| 중복 부여 방지 | 같은 직원·같은 연차 주기에 자동 부여가 중복되지 않도록 한다. |
| 반차 | 오전·오후를 구분하고 최종 승인 시 0.5일을 차감한다. 같은 날짜의 종일 연차·반차와 동일 시간대 반차는 중복 승인하지 않는다. |

### 3.10 지문 시뮬레이터 연동

현재 시안과 최종 연동 기준의 비교(기록 저장 위치·업체 식별·체크 판정 등)는 기능명세서 1.9에 있다. 아래는 그 최종 연동 기준을 사용자 입장에서 적은 것이다.

- 출퇴근 기록은 업체·직원별로 이음에 남는다. 브라우저를 초기화해도 기록은 지워지지 않는다.
- 업체가 달라도 같은 단말기 사용자 번호 때문에 다른 사람의 기록으로 섞이지 않는다.
- 출근·퇴근은 같은 날 각 1건이며 중복 체크와 출근 없는 퇴근은 거절한다(3.4).
- 직원은 그룹웨어의 링크로 시뮬레이터를 열고, 체크한 결과는 그룹웨어의 본인 근태 표시에 반영된다. 다른 업체·다른 직원의 근태는 볼 수 없다.
- 근태 기록은 승인된 휴가·휴일과 구분해 보여 주고 연차·반차와 연결한다.
- 이용 기간이 끝난 업체의 체크는 받지 않는다(3.11).
- 실제 지문 장비와 연결한 것으로 안내하지 않는다.

### 3.11 자동 식별자·이용 상태별 권한

| 항목 | 확정 규칙 |
|---|---|
| 업체명·업체 코드 | 업체명은 신청 입력값을 유지한다. 업체 코드는 체험 신청 때 `ieum`+숫자 4자리를 무작위로 붙이며(예: `ieum4827`, `ieum0315`) 동시에 신청해도 겹치지 않는다. 결제해도 바꾸지 않으므로 직원은 같은 코드로 계속 로그인한다. 시연 데이터의 업체는 정해 둔 코드로 넣는다. 신청 순서를 따르지 않으므로 고객이 몇 번째 고객인지 알 수 없고, 남의 업체 코드를 짐작하기 어렵다. `ieum0000`은 이음 운영 업체(운영자 소속)다. 업무 자료가 삭제된 업체도 업체 정보는 남으므로 그 코드는 다른 업체에 다시 주지 않으며, 네 자리 번호를 다 쓰면 새 신청을 받지 않고 안내한다. |
| 관리자·직원 사번 | 발급 연도 4자리+업체별 일련번호 4자리다. 각 업체는 `0001`부터 발급하며 관리자·직원 번호 중복을 막는다. |
| 발급 예 | `ieum4827`의 관리자 `20260001`, 다음 직원 `20260002`. 다른 업체 `ieum0315`는 자체 번호 `20260001`부터 가능하다. 업체 코드+사번으로 식별한다. |
| 신청 직후·인증 전 | 업체·관리자 계정·체험 시작/만료 정보를 생성하되 그룹웨어 이용을 차단한다. 인증 후에도 신청일부터 14일 기준을 유지한다. |
| 데모 이용 중 | 관리자 포함 10명 이하에서 인원·대상 수정 가능. 정식 전환 결제는 업체 관리자만 가능하다. |
| 정식 이용 중 | 구매 한도와 부여받은 권한 안에서 업무를 사용한다. 관리자·해당 권한자는 추가 인원 결제·기간 연장이 가능하다. |
| 데모·유료 만료 | 업무 자료를 지우기 전까지 기존 활성자의 로그인·자료별 조회·다운로드·기존 대화 열람을 허용한다. 팝업을 표시하고 관리자 결제 외 쓰기는 차단한다. |
| 만료 중 차단 예 | 작성·수정·삭제·업로드·채팅 전송·근태 저장·가입 승인·증설 신청·장애 문의 등록·지원 접근 승인·업체 자료 변경. 화면을 거치지 않는 방법으로 요청해도 똑같이 거절한다. |
| 만료 중 허용하는 쓰기 | 업체 관리자 결제 외에 본인 비밀번호 변경·찾기(업무 자료가 아니라 계정 보안), 로그아웃, 업체 관리자의 직원 비활성화·계정 생성 전 취소(사용 중 계정을 줄이는 쪽이라 안전하고, 더 적은 인원으로 재구매하려면 필요)는 허용한다. 2장·DEM-03·SUB-04·기능명세서 3장의 "관리자 결제 외 쓰기 차단"은 이 예외를 포함한 뜻이다. |

읽기 전용은 사용자 업무 요청의 제한이며 결제·보관·삭제·로그 수집 같은 서비스 운영 작업의 중단을 뜻하지 않는다. 만료 후 3개월 초과 업무 자료 삭제·계정 비활성화(3.7)와 퇴사·비활성·자료별 접근 제한은 유지한다.
