이음은 여러 업체에 그룹웨어를 제공하고, 무료 체험·구독·이용 인원을 관리하는 서비스 운영 플랫폼이다. 업체는 상품 홈페이지에서 무료 체험을 신청해 바로 업체 코드와 관리자 계정을 받고, 이메일 인증 뒤 그룹웨어(PWA)를 쓰다가 테스트 결제로 정식 구독으로 바꾼다. 업체 안에서 직원은 업체 코드와 사번으로 로그인해 휴가·장비 지급을 신청하고, 자신의 장비에서 발생한 장애를 접수한다. 결재자는 신청을 승인·반려한다. IT 담당자는 접수된 요청을 처리하고 장비 지급·회수 이력을 남긴다. 직원 간 대화는 그룹웨어 채팅에서 진행한다. 이음 운영자는 운영자 메뉴에서 업체·문의·결제·장애 지원을 관리한다.

## 3. 필수 업무 흐름

### A. 휴가 신청과 근태·일정 반영

1. 직원이 휴가 종류(종일 연차·오전 반차·오후 반차)·날짜·사유와 결재자 최대 2명을 순서대로 입력한다.
2. 임시저장하거나 상신한다. 상신 시 잔여 연차와 날짜 중복(같은 날짜의 종일 연차·반차, 같은 시간대 반차)을 확인한다.
3. 첫 결재자가 승인하면 다음 결재자에게 넘어간다. 현재 순번의 결재자만 처리할 수 있다.
4. 최종 승인 시 결재 완료·연차 사용 내역(종일 1일, 반차 0.5일)·개인 휴가 일정·결과 알림을 함께 저장한다.
5. 반려하면 사유를 저장한다. 재기안은 원본을 복사한 새 문서로 작성해 이전 결재 이력을 보존한다.

### B. 장비 지급 신청과 IT 처리

1. 직원이 장비 종류·수량 1개·사용 목적·수령 지점을 입력해 결재를 요청한다.
2. 최종 승인되면 연결된 IT 지급 티켓 1건을 자동 생성한다.
3. IT 담당자가 재고 장비를 선택해 직원에게 지급한다.
4. 자산의 지급 대상·상태와 지급 이력을 저장하고 티켓을 처리 완료로 변경한다.
5. 직원이 수령을 확인하면 티켓을 종료한다. 재고가 없으면 사유를 남기고 처리 중으로 유지한다.

### C. 지점 장비 장애 접수와 처리

1. 직원이 본인에게 지급된 장비를 선택하고 장애 내용·우선순위·사진을 등록한다. 자산이 없는 계정·네트워크 문의도 등록할 수 있다.
2. IT 담당자 또는 관리자가 처리자를 배정한다.
3. IT 담당자는 티켓에서 접수 지점의 주소와 층·좌석(텍스트)을 확인한다.
4. 처리 내용을 댓글로 남기고 해결 결과를 입력해 처리 완료로 변경한다.
5. 요청자가 해결을 확인하면 종료하고, 해결되지 않았으면 사유와 함께 재요청한다.
6. 자산 상세에서 해당 장비의 지급·회수·장애 내역을 조회한다.

### D. 업체 도입과 직원 가입

요구분석서 1장의 전체 흐름이다. 세부 규칙은 괄호 안의 요구사항 ID를 따른다.

1. 방문자가 상품 홈페이지에서 업체명·이용 인원(관리자 포함 10명 이하)·이메일·관리자 이름·비밀번호로 무료 체험을 신청한다(ACC-01).
2. 서버가 한 트랜잭션에서 업체(업체 코드는 `ieum` + 무작위 4자리, 가입 키도 함께)·관리자 계정(사번은 발급 연도 + `0001`)·14일 체험 기간을 만들고, 커밋 뒤 인증 메일을 보낸다(ACC-02·03·06).
3. 관리자가 메일의 인증 링크로 이메일을 인증한다. 인증 전 로그인은 거절하고, 인증이 늦어도 체험 기간은 신청일부터 센다.
4. 관리자가 업체 코드·사번·비밀번호로 로그인해 부서·부서장을 정하고, 관리자 화면의 가입 키를 직원에게 알린다(ACC-08).
5. 직원이 계정 만들기(`/join`)에서 가입 키·이름·부서·직급·이메일로 승인을 요청한다. 요청 뒤 1시간 안에 업체 관리자나 그 부서 부서장이 승인하면 다음 사번이 배정되고, 직원이 비밀번호를 정해 계정을 만든다. 이메일 인증 시점과 승인 뒤 계정 생성 기한은 ACC-04·05를 따른다.
6. 체험 중 업체 관리자가 토스 테스트 결제로 정식 구독으로 바꾼다. 서버가 승인 결과를 확인한 뒤 기존 계정·자료를 그대로 두고 결제 승인일부터 유료 기간을 시작한다(PAY-01·02).
7. 체험·유료 기간이 끝나면 업체는 읽기 전용이 되고, 업체 관리자만 결제할 수 있다(DEM-03, SUB-04, 3.11).

### E. 이음 장애 문의와 운영자 지원

1. 이용 중인 업체의 직원이 이음 장애 문의를 등록한다. 만료 중에는 등록할 수 없다(OPS-04).
2. 운영자는 오류 로그로 먼저 원인을 찾는다(OPS-03·05).
3. 업체 자료를 봐야 하면 운영자가 필요한 자료와 조회·수정 범위를 정해 접근 허가를 요청한다.
4. 업체 관리자가 범위를 확인해 승인하면 운영자는 최대 24시간 그 범위 안에서 지원한다. 개인 지도·개인 채팅 같은 보호 자료는 소유자·당사자의 추가 허가가 있어야 한다.
5. 지원 종료·허가 취소·24시간 경과 때 바로 차단하고, 요청·승인·작업 이력을 남긴다(OPS-06).

## 4. 필수 기능과 완료 기준

기능 범위는 요구분석서 3장을 따른다. 운영 플랫폼(홈페이지·체험·결제·구독·증설·운영자) 기능의 범위와 확인 기준은 요구분석서 3.1~3.3, 3.5~3.7, 3.11과 4장에 있고, 아래 표는 그룹웨어 업무 기능의 구현 범위와 완료 기준이다.

| 영역 | 구현 범위 | 완료 기준 |
|---|---|---|
| 사원·조직 | 직원 가입(승인 요청·1시간 안 승인·사번 자동 배정·계정 생성), 부서·직급·부서장 지정, 조직도, 사원 검색, 비활성화 | 관리자의 사전 등록과 공개 회원가입은 없다. 비활성 계정은 로그인·기존 연결을 사용할 수 없다. 승인 한도·자리 대기는 요구분석서 3.6을 따른다. |
| 로그인·권한 | 업체 코드+사번 로그인, 로그아웃, 이메일 인증, 비밀번호 찾기(ACC-07)·변경, 본인 정보 | 비밀번호를 해시로 저장한다. 이메일 인증 전·승인 전·자리 대기 계정은 로그인할 수 없다. URL과 ID를 바꿔 요청해도 다른 업체나 권한 밖의 자료는 조회되지 않는다. |
| 전자결재 | 양식 2종, 임시저장, 첨부, 순차 결재, 승인·반려·재기안, 결재함 | 현재 순번만 처리하며, 중복 승인 요청에도 연차 차감·티켓 생성이 한 번만 발생한다. |
| 근태·연차 | 지문 시뮬레이터의 출근·퇴근 이벤트 수신, 본인 월별 기록, 지각·조퇴 집계, 연차 자동 부여·잔여량, 반차 | 서버가 받은 시각을 쓴다. 사원·날짜당 출근·퇴근 각 1건이며 중복 체크와 출근 없는 퇴근은 거절한다. 만료 업체의 이벤트도 거절한다. |
| IT 티켓 | 접수·첨부·댓글·검색·페이징, 배정·상태 변경·이력 | 요청자·담당자·관리자별 범위를 검사하고 상태·배정 변경 전후 값을 기록한다. |
| IT 자산 | 자산번호·종류·모델·상태, 지급·회수, 자산별 장애 이력 | 같은 장비를 두 직원에게 동시에 지급하지 않는다. 이력이 있는 자산은 삭제 대신 사용 중지·폐기로 처리한다. |
| 지점 | 지점 등록·수정·사용 중지, 사원 근무 지점·자산 배치 지점·티켓 접수 지점 선택 | 자산이 다른 지점으로 이동해도 과거 티켓의 접수 지점은 바뀌지 않는다. |
| 지도 | 공통·개인 지도, 주소 검색, 마커(제목·주소·위치·설명) 등록·수정·삭제, 열람 요청·승인·묶음별 자동 승인·해제 | 요청 목록에는 소유자·제목만 보이고 주소·설명은 허가 뒤에 보인다. 재조회해도 같은 위치·내용으로 표시된다. 지도에 장애가 나도 다른 기능은 사용할 수 있다. |
| 일정 | 개인·부서·전사 일정, 휴가 일정 표시 | 개인 일정은 본인, 부서 일정은 해당 부서원, 전사 일정은 재직자가 조회한다. 일반 일정 등록·수정도 공개 범위 권한을 검사한다. |
| 게시판 | 공지·부서 게시판, 댓글, 검색·페이징 | 공지는 운영 권한자만 작성하고 부서 글은 같은 부서원만 조회한다. 자유 게시판은 추가 기능이다. |
| 사내 채팅 | 1:1·사용자 생성 그룹방, 텍스트·이미지, 이전 대화·재접속 | 방에 속한 재직자에게만 전달한다. 새로고침 후 저장된 대화를 볼 수 있다. 읽음·타이핑은 제외하고, 전사·부서 자동 채팅방은 추가 기능이다. |
| 업무 알림 | 결재 요청·결과, 티켓 배정·처리 결과, 읽음 처리 | 알림을 DB에 저장하고 본인 알림만 조회한다. 헤더에서 15초 간격으로 조회하며 WebSocket 연결이 없어도 확인할 수 있다. |
| 메인·관리 | 결재 대기, 내 일정·티켓·자산·알림, 체험 남은 일수·만료 읽기 전용 팝업, 역할별 관리 메뉴(요구분석서 3.12) | 카드별 수치를 실제 목록 조회 조건과 일치시킨다. 복잡한 차트 대신 건수와 목록을 우선 제공한다. 만료 중에는 알림 읽음 저장 같은 쓰기도 막는다. |

화면 시안은 이 범위에 맞춰 고친다: 쪽지 메뉴는 채팅으로, 결재 문서 종류는 휴가·장비 지급 2종으로, 메인 카드는 위 '메인·관리'의 항목으로 바꾼다.

### 근태·휴가의 시연 기준

- 기본 근무 시각은 09:00~18:00으로 고정하고 초과근무·급여 계산은 제외한다.
- 종일 연차와 오전·오후 반차가 필수다. 병가·승인 후 취소는 추가 기능이다.
- 연차는 이전 경력과 현재 근속을 합쳐 자동으로 부여한다(요구분석서 3.9). 이전 경력은 직급별 시연용 데이터다.
- 휴가 일수는 주말과 DB에 등록된 휴일을 제외한다. 휴일 초기 데이터에 포함된 기간만 신청하도록 제한한다.
- 휴일 API 자동 동기화는 추가 기능이며, 필수 시연은 등록된 휴일 데이터로 재현할 수 있게 한다.
- 휴가 여부와 출퇴근·지각·조퇴를 별도로 조회해 한 상태값에 서로 다른 정보를 덮어쓰지 않는다.

## 5. 권한과 상태 변경 규칙

### 역할

- **직원:** 본인 근태·결재·티켓·지급 자산을 조회하고, 허용된 일정·게시판·채팅을 사용한다.
- **결재자:** 해당 문서 결재선에 지정된 직원이다. 직급이 높다는 이유만으로 모든 문서를 볼 수 없다.
- **IT 담당자:** IT 티켓과 자산을 조회·처리한다. 결재 원문은 문서 관계자일 때만 열람한다.
- **인사 담당자:** 사원(목록·비활성화)·근태·연차·휴일을 관리한다. 비밀번호 원문이나 관계없는 채팅은 조회할 수 없다.
- **업체 관리자:** 업체당 1명이며 체험 신청 때 생긴다. 직원 가입 승인, 사원·부서·역할·지점 관리, 티켓 배정, 이용 결제·구독·증설, 운영자 지원 허가 승인을 맡는다(메뉴는 요구분석서 3.12). 관리자라는 이유만으로 개인 채팅·결재 원문을 자동 공개하지 않는다.
- **부서장:** 역할이 아니라 부서 설정에서 지정한 사람이다. 본인 부서의 가입 요청을 승인한다.
- **구독 관리 권한자:** 정식 구독 중 업체 관리자가 조회·결제·증설 권한을 따로 준 사람이다. 권한마다 따로 검사하고, 만료 중에는 결제할 수 없다.
- **이음 운영자:** 이음 운영 업체(`ieum0000`) 소속 계정이다. 운영 메뉴와 업체 기본 메뉴를 쓰고, 고객 업체의 내부 자료는 지원 허가 범위 안에서만 본다(흐름 E).

역할은 한 계정에 하나다(`ROLE_EMP`·`ROLE_IT`·`ROLE_HR`·`ROLE_ADMIN`·`ROLE_OPS`, 요구분석서 3.12). 부서장 여부, 구독 권한, 문서별 결재 권한은 역할과 따로 판단한다.

### 관리자 메뉴와 계정 발급

- 관리 기능은 별도 관리자 사이트를 만들지 않고 같은 사이트 안의 관리자 메뉴로 둔다. 관리 역할이 있는 사원에게만 메뉴가 보인다.
- 관리 화면 URL은 `/<모듈>/admin/**`로 만들고 Spring Security에서 관리 역할만 통과시킨다. 운영자 화면은 `/ops/**`로 만들고 `ROLE_OPS`만 통과시킨다. 메뉴를 숨기는 것만으로 권한을 처리하지 않는다.
- 가입 승인과 이용 결제는 역할만으로 정해지지 않으므로 관리 화면 주소 밖에 두고, Service가 요청마다 그 사람이 맞는지(업체 관리자 또는 그 부서 부서장, 업체 관리자 또는 구독 권한자) 확인한다.
- 공개 회원가입과 관리자의 사전 등록은 없다. 업체와 업체 관리자 계정은 체험 신청으로 바로 생기고, 직원은 계정 만들기로 승인을 요청한다(흐름 D).
- 초기 데이터로 만드는 것은 이음 운영 업체(`ieum0000`)와 운영자 계정뿐이다. 운영자 화면에는 계정 발급 기능이 없고, 자료가 삭제된 업체의 관리자 재발급(OPS-08)만 있다.
- 임시 비밀번호와 첫 로그인 비밀번호 변경은 두지 않는다. 비밀번호를 잊으면 비밀번호 찾기로 본인이 다시 정한다(ACC-07).
- 구독·결제는 토스 테스트 환경으로 구현한다(요구분석서 3.2·3.5).

### 직원 가입

계정 상태 코드는 AGENTS.md '상태 코드'에 있다. 세부 규칙은 요구분석서 ACC-04·05, 3.6, CFG-02를 따른다.

| 변경 | 실행자·조건 |

| 승인 대기 → 계정 생성 전 | 같은 승인자. 요청 뒤 1시간 안이고 승인 한도(유료는 구매 인원 × 1.2 올림, 체험은 10명) 안일 때. 다음 사번을 배정한다. |

| 비활성 → 사용 중 | 업체 관리자 또는 인사 담당. 자리가 있을 때. |

### 업체 이용 상태와 만료 읽기 전용

- 업체 이용 상태는 체험 중·유료·체험 만료·유료 만료다(요구분석서 3.12). 이메일 인증 전에는 그룹웨어를 쓸 수 없고, 만료 3개월이 지나 자료를 지운 업체는 운영자가 관리자를 재발급한 뒤 재구매한다(OPS-08).
- 이용 상태는 결제·만료로 로그인 중에도 바뀌므로 세션에 담지 않고 요청마다 DB에서 확인한다.
- 만료 업체는 로그인·조회·다운로드·기존 대화 열람만 된다. 공통 검사가 GET이 아닌 요청을 쓰기로 보고 거절하며, 업체 관리자 결제와 로그아웃, 요구분석서 3.11의 '만료 중 허용하는 쓰기'만 통과시킨다. 채팅 전송과 단말기 API도 같은 검사를 한다.
- 결제는 서버가 토스 승인 결과와 주문(업체·인원·월간/연간·할인·금액)을 확인한 뒤에만 반영한다. 같은 승인 건은 한 번만 반영하고, 승인 뒤 저장에 실패하면 운영자가 같은 승인 건으로 다시 반영한다(OPS-07).

### 결재

- 문서 상태는 `임시저장 → 진행 → 완료/반려`로 제한한다. 진행 문서의 본문·결재선은 수정할 수 없다.
- 기안자 본인과 퇴사자는 결재자로 선택할 수 없고 같은 결재자를 중복 지정할 수 없다.
- 문서 처리 시 현재 상태·현재 순번을 검사하고 문서를 잠근 뒤 변경한다. 변경 이력도 함께 저장한다.
- 휴가 최종 승인 시 연차 잔여량·기간 중복을 다시 검사한다. 연차 잔여 행을 잠가 다른 휴가 문서와의 동시 차감을 막는다.
- 완료 상태 변경·업무 반영·DB 알림은 같은 트랜잭션으로 묶는다. 실패 시 모두 취소한다.
- 생성 티켓과 휴가 사용 내역은 원본 결재 문서 ID에 고유 제약을 적용해 중복 반영을 막는다.
- 장비 승인 알림과 IT 티켓에는 지급에 필요한 정보만 포함하고 문서 첨부 전체를 공개하지 않는다.

### 티켓

| 변경 | 실행자·조건 |
|---|---|
| 접수 → 배정 | 관리자가 IT 담당자를 지정하거나, IT 담당자가 미배정 건을 본인에게 배정한다. |
| 배정 → 처리 중 | 현재 담당자 또는 관리자 |
| 처리 중 → 처리 완료 | 현재 담당자 또는 관리자. 해결 결과 입력 필수. 지급 건은 자산 지급 완료 필요. |
| 처리 완료 → 종료 | 요청자가 해결·수령 확인 |
| 처리 완료 → 처리 중 | 요청자가 재요청 사유 입력. 장비 지급 건은 별도 장애 티켓으로 접수해 중복 지급을 막는다. |
| 접수 → 취소 | 요청자가 직접 등록한 장애·문의 건만 가능. 승인된 장비 지급 건은 취소하지 않고 처리한다. |
| 접수 → 반려 | IT 담당자 또는 관리자. 사유 입력 필수. |

- 재배정은 종료·취소·반려 전 상태에서 관리자만 수행하고 이전·새 담당자를 기록한다.
- 승인된 장비 지급 건에 IT 처리가 불가능한 경우 사유를 남겨 반려할 수 있다. 완료된 결재는 유지하고 지급 실패 결과를 요청자에게 알린다.
- 상태 변경·이력은 같은 트랜잭션에서 저장한다. `version` 조건으로 동시 변경을 감지하고 충돌 시 새로고침을 안내한다.
- 자산 지급은 자산 행 잠금 후 재고 상태를 다시 확인하고 지급·이력·티켓 상태를 함께 저장한다.

## 6. 지점과 지도

지점은 사원·자산·티켓의 위치를 구분하는 주소 목록이며 지도와 연결하지 않는다. 지도는 요구분석서 3.4의 공통·개인 지도다.

### 지점

- 업체 관리자가 지점명·주소를 등록한다. 쓰지 않는 지점은 삭제하지 않고 사용 중지로 처리한다.
- 사원의 근무 지점, 자산의 배치 지점, 장비 지급 신청의 수령 지점, 티켓의 접수 지점을 이 목록에서 고른다.
- 장애 접수 시 자산의 지점을 기본값으로 채우고 실제 장애 지점을 확인받아 티켓에 저장한다. 이후 자산이 이동해도 기존 티켓 지점은 바뀌지 않는다.
- 자산이 없는 문의는 사원의 근무 지점을 기본값으로 사용한다.
- 기본 시연 데이터는 본사·지점 2곳 이상과 각 지점의 장비·티켓을 준비한다.

### 지도

- 공통 지도와 개인 지도에 마커(제목·주소·위치·설명)를 등록·수정·삭제한다. 위치는 장소·주소 검색으로 찾는다.
- 다른 사람의 개인 지도는 열람을 요청하고 소유자가 승인해야 본다. 요청 목록에는 소유자·제목만 보이고 주소·설명은 허가 뒤에 보인다.
- 마커는 묶음으로 나눈다. 처음 열람은 소유자가 직접 승인한다. 소유자가 묶음별 자동 승인을 켜면 이미 허가한 사람에게 그 묶음에 새로 더한 마커도 공유되고, 끄면 그 뒤에 더한 마커부터 다시 승인한다. 사람별 허가는 언제든 해제할 수 있다.
- 개인 지도는 보호 자료다. 업체 관리자나 운영자의 승인만으로 공개하지 않는다.
- TODO(회의): 공통 지도에 누가 마커를 등록·수정할 수 있는지는 요구분석서에 없다. 지도 담당이 정해 이 줄에 적는다.
- 마커의 위치와 내용은 DB에 저장해 재조회해도 같게 표시한다.
- 지도는 직원의 현재 위치를 수집하지 않는다. 실내 좌석도·GPS 추적·자체 길찾기는 필수 범위에서 제외한다.
- 지도 API가 실패해도 지점·자산·티켓 기능은 사용할 수 있게 한다. 지도와 지점·자산·티켓의 자동 연결은 추가 기능이다.

## 7. WebSocket 채팅과 알림

- 직원 검색으로 1:1 방 또는 그룹방을 만든다. 동일한 두 직원의 1:1 방은 기존 방을 다시 사용한다.
- 그룹방의 참여자는 생성 시 확정한다. 이후 초대·강퇴·방장 위임은 추가 기능으로 둔다.
- 로그인 사용자와 방 참여 여부를 연결 시·메시지 전송 시·대화 조회 시 검사한다.
- 작성자와 전송 시각은 서버가 정한다. 메시지를 DB에 저장한 뒤 참여자의 연결로 전달한다.
- 메시지 ID로 재접속 누락분을 조회하고, 화면에서 같은 메시지의 중복 표시를 막는다.
- 읽음 표시와 타이핑 표시는 만들지 않는다(요구분석서 3.4).
- 이미지는 HTTP 업로드 후 첨부 ID를 메시지에 연결한다. JPG·PNG, 메시지당 1장·10MB를 허용하고 서버에서 실제 파일 형식과 방 권한을 검사한다.
- 만료 업체의 메시지 전송은 이미 열린 연결에서도 메시지마다 거절한다. 기존 대화 열람은 된다.
- 채팅·결재·티켓의 첨부파일은 업로드·다운로드마다 해당 자료 접근 권한을 검사한다.
- 로그아웃·퇴사·방 탈퇴 시 기존 연결을 정리한다. 발신자 문자열만 신뢰하는 수업 예제를 그대로 인증 처리로 사용하지 않는다.
- 업무 알림은 DB 저장 후 화면에서 조회한다. 실시간 업무 알림 푸시는 추가 기능이며 채팅과 별개다.

## 8. 기술 스택 이미지의 채택·조정 사항

| 참고 이미지의 항목 | 이번 적용 방식 |
|---|---|
| Spring Security와 프런트 라우트 가드 | Spring Security와 JSP 화면을 사용한다. SPA용 라우트 가드는 도입하지 않는다. Service에서 데이터별 권한을 검사한다. |
| SSE·스트림 티켓·연결 제한 | 필수에서 제외한다. 채팅은 WebSocket, 업무 알림은 DB 조회로 처리해 두 통신 체계를 동시에 만들지 않는다. |
| `AFTER_COMMIT` 이벤트 | 실시간 푸시를 추가한다면 DB 커밋 후 전송한다. DB에 저장할 업무 알림은 원본 업무와 같은 트랜잭션에서 기록한다. |
| 폴링 보조 | 업무 알림 조회는 앞 요청 완료 후 다음 요청을 예약해 겹치지 않게 하고, 숨긴 탭에서는 중지한다. |
| JPA `PESSIMISTIC_WRITE` | JPA를 추가하지 않는다. MyBatis의 Oracle `SELECT ... FOR UPDATE` 또는 조건부 UPDATE로 필요한 충돌을 처리한다. |
| S3 호환 저장소 | 필수는 서버 로컬 저장소다. 중앙 서버의 WAR·Tomcat 밖 폴더에 업체별로 나눠 두고(`{루트}/{company_id}/{모듈}/{UUID}`, 오류 ZIP은 따로), 파일당 10MB·요청당 30MB까지 받으며 남은 공간이 1GB 아래면 거절한다. 파일용 공간은 5GB를 잡는다. 파일 메타정보는 Oracle에 저장하고 저장소 경로는 git에 올리지 않는 설정 파일로 분리한다. 파일 저장은 인터페이스 하나로 감싸고, S3는 추가 기능이다. |
| 자동 퇴근·정정·배치 | 출퇴근은 지문 시뮬레이터가 보낸 이벤트로 기록하고, 자동 18시 퇴근 처리는 하지 않는다. 미퇴근은 그대로 표시한다. 정정·초과근무는 추가 기능이다. 필수 배치는 `@Scheduled`로 만드는 세 가지다: 입사기념일 연차 부여(3.9), 전날 오류 로그 ZIP 생성과 2주 지난 ZIP 정리(OPS-05), 만료 3개월이 지난 업체 자료 삭제(3.7). |
| 공휴일 자동 동기화 | 필수는 DB 초기 데이터·관리자 등록이다. 외부 API 자동 수집은 추가 기능이다. |
| 답장·수정·삭제·고정·오디오·모듈 캐시 | 채팅의 필수는 텍스트·이미지·재접속이다(읽음·타이핑은 제외). 이미지에 있는 나머지 기능은 추가 기능으로 둔다. |
| 감사 로그 | 작게 둔다. 결재·티켓·자산은 각자의 처리·상태·지급 이력이 감사 기록을 대신하고, 따로 남기는 것은 역할 변경과 운영자 지원 작업(OPS-06)이다. 실행자·대상·전후 값·시각을 남기며 비밀번호·토큰·채팅 원문은 복사하지 않는다. |

### 개발 환경

- Java 11, Spring Framework 5.3 계열 XML 설정, Spring Security, JSP·JSTL, JavaScript·jQuery·Ajax, MyBatis, Oracle, Maven, WAR·Tomcat 9를 기준으로 한다. Spring Boot·React·JPA는 추가하지 않는다.
- 버전은 Java 11·Spring 5.3.39·Security 5.8.16·Tomcat 9·Oracle XE 21c로 확정했다. 실제 사용할 전체 의존성은 10월 28일까지 전원 실행·DB 접속으로 확인해 고정한다.
- DB는 공용 Oracle 서버 한 대에 모두 접속한다. 테이블 변경은 DDL 스크립트로 Git에 올리고 DB 리드가 공용 DB에 반영한다. 공용 DB를 둘 곳은 회의에서 정한다.
- WebSocket은 수업의 `@ServerEndpoint` 방식으로 한다. `SpringConfigurator`를 상속한 Configurator로 Service를 주입받고, 핸드셰이크 때 서버의 인증 정보에서 로그인 사용자를 넘긴다. `SpringConfigurator`는 root context의 bean을 찾으므로 Service·DAO는 `root-context.xml`에서 스캔한다.
- 채팅 담당이 11장의 사전 구현에서 인증 사용자·Service 주입·DB 저장을 확인하고 공통 예제로 공유한다. 이 방식이 안 되면 Spring `WebSocketHandler`로 바꾼다. `spring-websocket` 의존성은 담당 1이 추가한다.
- 필수 외부 연동은 카카오 지도, 토스페이먼츠 테스트 결제, 이메일 발송(Spring `JavaMailSender` + SMTP, 팀 공용 Gmail 앱 비밀번호)이다. 메일 발송 의존성(`spring-context-support`, `javax.mail`)과 `@Scheduled` 설정은 담당 1이 추가한다. 일정 UI는 FullCalendar를 검토하되 버전을 고정하고 JSP에서 조회·등록 동작을 먼저 확인한다. 구독 통계(SUB-02)에는 그래프가 필요하고, 리치 에디터는 필수가 아니다.
- 그룹웨어는 PWA로 제공한다(`manifest.json`, 서비스 워커, 아이콘). 설치는 HTTPS 주소나 `localhost`에서만 되므로 중앙 서버의 고정 HTTPS 주소를 공용 DB 자리와 함께 정한다. 서비스 워커는 정적 파일만 캐시한다.
- 패키지는 모듈 15개(`employee`, `approval`, `attendance`, `ticket`, `asset`, `location`, `schedule`, `board`, `chat`, `notification`, `site`, `subscription`, `ops`, `support`, `common`)로 나누고 내부에 `controller/service/dao/mapper/dto`를 구분한다. 모듈별 맡는 일은 AGENTS.md에 있다. MyBatis는 Mapper 인터페이스 방식으로 쓰고, DAO 클래스가 Mapper 인터페이스를 감싸 Service는 DAO만 호출한다. Mapper XML은 `src/main/resources/mapper/<Mapper 인터페이스 이름>.xml`에 둔다.
- 업체 구분은 공유 테이블 + `company_id`다. 업체 ID는 로그인 사용자에게서만 꺼내 모든 SQL에 조건을 붙이고, 사번 고유 제약은 `(company_id, 사번)`이다(AGENTS.md 'DB·MyBatis').
- 토스 시크릿 키·SMTP 앱 비밀번호·단말기 키·DB 비밀번호는 저장소에 올리지 않는다. 브라우저 지도 JavaScript 키는 클라이언트에 전달되는 키이므로 개발·발표 도메인 제한을 적용한다.

## 10. DB 설계·연동 계약

ERD 확정 전에 아래 데이터 묶음과 생성 규칙을 합의한다. 테이블 설계는 DB 리드가 업체 구분 방식(8장, AGENTS.md 'DB·MyBatis')에 맞춰 하고, 업체 자료 테이블에는 모두 `company_id`를 둔다.

| 데이터 | 핵심 내용 |
|---|---|
| 업체 | `company_id`(시퀀스 PK, 운영자 화면 정렬에 씀)·업체 코드(고유, 0001~9999 무작위. 겹치면 다시 뽑기 최대 10번)·가입 키(고유, 원문 저장)·업체명·이용 상태와 체험/구독 만료일·이메일 인증 일시·자료 삭제 표시·사번 마지막 일련번호. `ieum0000`은 이음 운영 업체. 이용 상태를 저장할지 만료일로 계산할지는 DB 리드가 정한다. |
| 사원·부서·직급·역할 | 모든 기능에서 동일한 사원 ID 사용. 업체 ID, 사번(`(company_id, 사번)` 고유), 이메일, 계정 상태, 역할 1개, 이전 경력·입사일, 근무 지점, 부서장 지정. 비활성이 되어도 과거 결재·처리 이력 유지. |
| 가입 요청·이메일 인증 | 요청 시각·상태·요청 키(해시), 인증 링크·인증 코드(해시)·유효 시각·틀린 횟수·다시 보내기 횟수. |
| 결제·구독·증설 | 주문 번호(고유)·토스 승인 결과·금액·인원·월간/연간·할인·기간, 증설 신청·승인·결제. 업체 자료를 지운 뒤에도 남긴다. |

| 파일·알림·감사 이력 | 파일의 소속 업무·업로더·저장명, 알림 수신자·연결 대상·읽은 시각, 역할 변경·운영자 작업의 전후 값. |

- 파일 업로드·알림 생성·로그인 사용자 DTO·페이징 응답 규격은 공통으로 사용한다.
- 결재 완료·연차 반영·티켓 생성·자산 지급은 Controller를 서로 호출하지 않고 Service 간 메서드로 연결한다.
- 결재·근태·일정·티켓 연동은 같은 Oracle DB·같은 트랜잭션 관리자를 사용한다. 업무 반영과 WebSocket 전송을 한 성공 조건으로 묶지 않는다.
- 테이블·컬럼·상태 코드·메서드 입력/반환값을 문서에 적고 변경 전에 관련 담당자가 확인한다.

## 13. 검증·협업·제출

### 필수 검증

- 현재 순번이 아닌 결재자가 승인하면 거절한다. 같은 승인 버튼을 두 번 눌러도 업무 반영은 한 번이다.
- 동시에 들어온 휴가 승인에서 연차가 음수가 되지 않고, 장비 하나가 두 직원에게 지급되지 않는다.
- 원본 결재를 반려·재기안해도 이전 문서와 결재 이력이 남는다.
- 티켓의 허용되지 않은 상태 변경·본인 외 티켓 열람·다른 방 채팅·파일 접근을 거절한다.
- 채팅을 새로고침·재접속해도 메시지가 누락·중복 표시되지 않는다.
- 계정 비활성화·로그아웃 후 기존 채팅 전송과 업무 API 접근을 거절한다. 만료 업체는 열린 연결에서도 채팅 전송이 거절된다.
- 다른 업체의 자료 ID로 결재·근태·티켓·지도·파일을 조회·변경하거나 채팅에 연결하면 거절한다.
- 자산을 다른 지점으로 이동해도 과거 티켓의 접수 지점은 유지된다.
- 지도 API가 실패해도 지점·자산·티켓 기능은 사용할 수 있다. 준비 영상은 보조 자료로 표시하며 실제 연동 성공으로 기록하지 않는다.
- 관리 역할이 없는 계정으로 `/<모듈>/admin/**`에, 운영자가 아닌 계정으로 `/ops/**`에 접근하면 거절한다.
- 이메일 인증 전 업체의 로그인은 거절되고, 인증이 늦어도 체험 만료일은 바뀌지 않는다.
- 만료 업체의 쓰기 요청을 화면·API·채팅·단말기 어느 쪽으로 보내도 거절하고, 업체 관리자 결제와 요구분석서 3.11의 예외만 된다.
- 업체 코드·사번을 동시에 발급해도 겹치지 않고, 가입을 두 번 승인해도 계정은 하나다.
- 결재 단계·티켓 상태 전이·동시 반영·금액과 기간 계산·발급은 JUnit·Spring Test로 검증하고(AGENTS.md '테스트'), 지도·채팅·파일·메일·결제·PWA·발표 흐름은 두 브라우저 수동 검증 결과를 기록한다. 그 밖의 확인 기준은 요구분석서 4장이다.

### 협업

- 작업 브랜치(`feature/<모듈>-<기능>-<이니셜>` 등, AGENTS.md 'Git') → `develop` → `main` 순서로 PR을 사용한다. 다른 팀원 1명 이상 검토 후 병합한다.
- 시작 전 원격 변경을 확인하고 작업 브랜치에 최신 `develop`을 반영한다. 로컬 `develop`만 갱신해도 기능 브랜치가 바뀌지는 않는다.
- PR에 동작 확인·DB 변경·연동 영향·관련 문서 변경을 적는다. 공통 파일 변경은 주담당·보조가 검토하며 한 사람 부재로 전원이 멈추지 않게 한다.
- 매일 진행 기능·남은 결함·다음 병합 대상을 공유한다. 본인이 구현한 결함은 본인이 수정한다.

### 제출·발표

- 학교 양식을 우선해 계획서, 요구분석서, 기능·화면 목록, ERD·테이블 정의서, 화면설계서, 아키텍처, 테스트 결과, 역할·AI 사용 기록, 실행 안내, 발표자료·시연 영상을 준비한다.
- 소스, DDL·시연 데이터, 설정 예시, 계정별 권한표를 함께 준비한다. 실제 비밀번호·비밀키는 제출 저장소에서 제외한다.
- 시연 계정은 업체 관리자·직원·1차 결재자·최종 결재자·IT 담당자·인사 담당자와 이음 운영자로 준비하고 본사·지점 데이터와 재고/지급 장비를 넣는다. 업체 간 접근 제한을 보이기 위해 두 번째 업체의 최소 데이터도 넣는다.
- 발표는 업체 도입(체험 신청→인증 메일→로그인→직원 가입), 휴가 승인→근태·일정 반영, 장비 승인→IT 티켓→지급, 지점 장비 장애 접수→처리, 두 계정 채팅, 테스트 결제로 정식 전환의 순서로 구성한다. 발표 제한 시간을 확인한 뒤 각 시나리오 분량을 확정한다.
