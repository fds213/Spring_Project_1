# 사내 그룹웨어 프로젝트 계획서

> 전자결재 중심 사내 그룹웨어
> 팀 인원: 7명 · 기간: 3주 · 작성일: 2026-10-26

---

## 1. 프로젝트 개요

### 1.1 주제
회사 직원들이 결재, 근태, 일정, 게시판, 쪽지를 하나의 시스템에서 처리할 수 있는 **사내 그룹웨어**를 개발한다.
전자결재를 중심으로 각 모듈이 서로 연동되어, 결재 결과가 근태·일정·알림에 자동으로 반영되는 구조를 목표로 한다.

### 1.2 기획 배경
- 많은 회사가 결재·근태·공지·사내 소통을 종이 문서, 메일, 엑셀 등 서로 다른 방식으로 처리해 정보가 흩어진다.
- 휴가 결재 후 연차 차감, 일정 등록처럼 **하나의 업무가 여러 단계와 부서를 거치는 흐름**을 하나의 시스템으로 묶을 필요가 있다.
- 국내 SI 프로젝트에서 자주 다루는 사내 업무 시스템 도메인을 직접 설계·구현해 본다.

### 1.3 프로젝트 목표
1. 기안 → 결재선 → 승인/반려로 이어지는 **순차 결재 흐름** 구현
2. 결재 결과가 근태·일정·알림 등 **다른 모듈에 자동 반영**되는 연동 구조 구현
3. 직급·부서별 **권한에 따른 접근 제어** 구현
4. 공휴일·지도·메일 등 **외부 API 연동** 경험
5. 3주 안에 시연 가능한 **완성도 있는 통합 시나리오** 확보

## 5. 핵심 시나리오 (시연용)

### 시나리오 A: 휴가 신청 (모듈 연동)
1. 사원이 휴가 신청서 기안 → 기간 입력 시 주말·공휴일을 제외한 휴가 일수 표시
2. 조직도에서 결재선(팀장 → 부장) 지정 → 상신
3. 팀장 결재 대기함과 메인 대시보드에 알림
4. 팀장 승인 → 부장에게 넘어감
5. 부장 최종 승인 → **연차 자동 차감 + 일정 캘린더에 휴가 자동 등록 + 기안자에게 쪽지**

### 시나리오 B: 반려와 재기안
1. 사원이 지출 결의서 기안 (영수증 첨부)
2. 팀장이 "영수증 누락" 사유로 반려 → 기안자에게 쪽지
3. 기안자가 반려함에서 문서를 열어 수정 후 재상신
4. 최종 승인 → 완료함으로 이동

### 시나리오 C: 권한에 따른 접근 제어
1. 일반 사원이 다른 부서의 결재 문서 URL로 직접 접근 → 차단
2. 관리자만 공지사항 작성, 사원 관리 화면 접근 가능
3. 부서 게시판은 해당 부서원만 조회 가능

## 6. 모듈 간 연동 포인트

| 출발 | 이벤트 | 도착 | 처리 |
|---|---|---|---|
| 전자결재 | 휴가 신청 최종 승인 | 근태 | 연차 잔여일 차감 |
| 전자결재 | 휴가 신청 최종 승인 | 일정 | 개인 일정에 휴가 등록 |
| 전자결재 | 결재 요청·승인·반려 | 쪽지 / 대시보드 | 알림 표시 |
| 조직도 | 결재선 지정 | 전자결재 | 결재자 선택 |
| 조직도 | 쪽지 보내기 | 쪽지 | 받는 사람 선택 |
| 근태 / 결재 / 게시판 | 데이터 누적 | 관리자 통계 | 월별·부서별 집계 |

> 연동이 일어나는 메서드는 **하나의 트랜잭션**으로 묶는다. (예: 결재 상태 변경 + 연차 차감 + 일정 등록이 모두 성공하거나 모두 실패)

## 7. 데이터베이스 설계 (핵심 테이블)

> 상세 ERD는 1주차에 확정한다. 아래는 초안이다.

### 사원·조직
| 테이블 | 주요 컬럼 |
|---|---|
| DEPT | dept_id, dept_name, parent_dept_id |
| POSITION | position_id, position_name, position_level |
| EMP | emp_id(사번), name, password, dept_id, position_id, role, email, phone, address, hire_date, status(재직/휴직/퇴사) |

### 전자결재
| 테이블 | 주요 컬럼 |
|---|---|
| APPROVAL_FORM | form_id, form_name, form_type, use_yn |
| APPROVAL_DOC | doc_id, form_id, writer_id, title, content, status(임시/진행/완료/반려), current_step, created_at |
| APPROVAL_LINE | line_id, doc_id, step_order, approver_id, status(대기/승인/반려), comment, acted_at |
| LEAVE_DETAIL | doc_id, leave_type(연차/반차/병가), start_date, end_date, days |
| EXPENSE_DETAIL | doc_id, amount, use_date, purpose |
| ATTACH | attach_id, ref_type, ref_id, origin_name, saved_name, file_size |

### 근태
| 테이블 | 주요 컬럼 |
|---|---|
| ATTENDANCE | att_id, emp_id, work_date, check_in, check_out, status(정상/지각/조퇴/휴가) |
| LEAVE_BALANCE | emp_id, year, total_days, used_days |

### 일정
| 테이블 | 주요 컬럼 |
|---|---|
| SCHEDULE | sch_id, emp_id, dept_id, type(개인/부서/전사), title, place, start_at, end_at, ref_doc_id |
| ROOM | room_id, room_name, capacity |
| ROOM_RESERVATION | res_id, room_id, emp_id, title, start_at, end_at |

### 게시판·쪽지
| 테이블 | 주요 컬럼 |
|---|---|
| BOARD | board_id, board_type(공지/부서/자유), dept_id, writer_id, title, content, pinned_yn, views, created_at |
| BOARD_COMMENT | comment_id, board_id, writer_id, content, created_at |
| MESSAGE | msg_id, sender_id, receiver_id, title, content, read_yn, sent_at, deleted_by_sender, deleted_by_receiver |

**결재선 처리 규칙**
- `APPROVAL_DOC.current_step`이 가리키는 순번의 결재자만 승인/반려 가능
- 승인 시 `current_step + 1`, 마지막 순번이면 문서 상태를 `완료`로 변경
- 반려 시 문서 상태를 `반려`로 변경하고 이후 결재선은 처리하지 않음
- 재기안 시 결재선 상태를 모두 `대기`로 초기화하고 `current_step`을 1로 되돌림

- 브랜치: `main`(배포용) ← `develop`(통합) ← `feature/모듈명` (예: `feature/approval`)
- `main`, `develop`에 직접 push 금지, Pull Request로만 병합
- PR은 최소 1명 리뷰 후 병합
- 커밋 메시지: `[모듈] 작업 내용` (예: `[approval] 결재선 순차 승인 처리`)
- 매일 작업 시작 전 `develop` 최신 내용을 pull

### 코드 컨벤션
- 패키지: `controller` / `service` / `dao(mapper)` / `dto(vo)` 모듈별로 분리
- 클래스명: `ApprovalController`, `ApprovalService`, `ApprovalDAO`, `ApprovalDTO`
- URL: `/모듈/기능` (예: `/approval/list`, `/attendance/checkin`)
- DB 컬럼: 스네이크 케이스(`emp_id`), Java 필드: 카멜 케이스(`empId`)

### 보안
- API 키, 메일 계정 비밀번호, DB 비밀번호는 **별도 설정 파일**에 두고 `.gitignore`에 등록
- 비밀번호는 평문 저장 금지 (해시 처리)
- 결재·관리자 기능 URL에서 서버 측 권한 체크

### 소통
- 매일 오전 스탠드업 10분: 어제 한 일 / 오늘 할 일 / 막힌 부분
- 테이블 구조 변경은 반드시 팀 전체 공유 후 반영
